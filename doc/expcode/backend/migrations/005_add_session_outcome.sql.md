# backend/migrations/005_add_session_outcome.sql

## 1. หน้าที่ของไฟล์

เพิ่ม 2 คอลัมน์ในตาราง `sessions` เก็บ "ผลลัพธ์ที่ผู้ใช้กรอก" ตอนการตรวจจบแล้ว (หน้าสถานะสิ้นสุด): `outcome_text` (ข้อความอิสระ เช่น "ทำตามแล้วแอร์กลับมาทำงานปกติ") และ `outcome_at` (เวลาที่บันทึก) เป็นข้อมูลบันทึกอย่างเดียว เหมือน `confidence` — กลไกเครื่องสถานะไม่อ่าน ไม่ใช้ตัดสินขั้นถัดไปหรือด่านความปลอดภัย ไม่ใช้ในระบบค้นหา และไม่ใช้คำนวณความแม่นยำใดๆ

- **ใครเรียกใช้**: `scripts/run-migrations.js`
- **ใครใช้คอลัมน์**: `session.store.ts` (`saveOutcome`, `findOutcome`), `scripts/show-session-history.js` (ดูข้อมูล)
- **เรียกใช้**: ตาราง `sessions` จาก migration 002/004

## 2. อธิบายทีละบล็อก

### บล็อก A — คอมเมนต์ (บรรทัด 1–42) — เหตุผลการออกแบบ
- `NULL` = ผู้ใช้ยังไม่กรอก (ไม่บังคับ) **ห้ามใช้สตริงว่างแทน NULL** เพราะแยก "ยังไม่กรอก" กับ "กรอกว่าง" ไม่ออก (ตัวตรวจ body ไม่ให้เก็บข้อความว่างอยู่แล้ว)
- `outcome_text TEXT`: ความยาวที่ API รับจำกัดที่ฝั่งแอป (1,000 ตัวอักษร) ใน utf8mb4 ตัวละสูงสุด 4 ไบต์ → ไม่เกิน 4,000 ไบต์ ต่ำกว่าขีดจำกัด 65,535 ไบต์ของ TEXT
- `outcome_at DATETIME`: ตั้งด้วย `NOW()` ใน SQL ตามข้อตกลงของ `SessionStore`; ใช้ `DATETIME` ต่างจาก `created_at`/`expires_at` (TIMESTAMP) ตรงที่ไม่แปลงตาม time zone ตอนอ่าน และไม่ถูกเอาไปเทียบกับคอลัมน์เวลาอื่น จึงไม่กระทบการหมดอายุ
- **ข้อควรรู้ด้านข้อมูล** (คอมเมนต์ 25–30): ผู้ใช้อาจพิมพ์ข้อมูลส่วนตัวเอง หน้าจอจึงมีคำเตือน; ยังไม่มีตัวกวาดแถวหมดอายุ ข้อความจึงอยู่ในตารางต่อไปแม้ session หมดอายุแล้ว; `updated_at` (ON UPDATE CURRENT_TIMESTAMP) จะเปลี่ยนตามการบันทึก แต่ไม่กระทบ `expires_at`
- **ลำดับขึ้นระบบ** (คอมเมนต์ 32–37): รัน migration ก่อน แล้วค่อย deploy โค้ดใหม่ — เพราะโค้ดเก่าระบุชื่อคอลัมน์เองทุกคำสั่ง ไม่ใช้ `SELECT *` จึงยังทำงานได้กับตารางที่มีคอลัมน์เพิ่ม แต่โค้ดใหม่ที่ SELECT คอลัมน์นี้จะพังถ้า DB ยังไม่มีคอลัมน์
- ใช้ `ALTER TABLE` คำสั่งเดียวเพิ่มสองคอลัมน์ เพราะตัวรัน migration ไม่ครอบ transaction และ MySQL 8 ทำ DDL แบบ atomic ต่อคำสั่ง (คอมเมนต์ 39–42)

### บล็อก B — `ALTER TABLE sessions` (บรรทัด 44–50)
- `ADD COLUMN outcome_text TEXT NULL COMMENT '…' AFTER confidence`
- `ADD COLUMN outcome_at DATETIME NULL COMMENT '…' AFTER outcome_text`


## 4. จุดที่ควรระวัง

- **ข้อมูลส่วนบุคคลที่ผู้ใช้อาจพิมพ์** ถูกเก็บในตารางต่อไปแม้ session หมดอายุ (ยังไม่มีตัวกวาด) — เป็นประเด็นนโยบายข้อมูลที่ควรพิจารณา
- ค่าของเพดาน 1,000 ตัวอักษรกำหนดที่ฝั่งแอป (`MAX_OUTCOME_LENGTH`) ไม่ใช่ constraint ของฐานข้อมูล
- ใช้ `DATETIME` ตรงนี้ ต่างจากคอลัมน์เวลาอื่นของตารางที่เป็น `TIMESTAMP` — ต้องระวังเมื่อนำไปเทียบเวลาข้ามคอลัมน์
