## 1. หน้านี้ประกอบชิ้นส่วน ไม่ได้ตัดสินใจ

หลักการสำคัญที่สุดของโครงงานคือ **เครื่องสถานะเป็นผู้ตัดสินว่าขั้นถัดไปคืออะไร** หน้าจอไม่มีสิทธิ์นั้น หน้านี้จึงแบ่งความรับผิดชอบไว้ชัดเจน

| เรื่อง | ใครรู้ |
|---|---|
| ตอนนี้อยู่สถานะไหน | เซิร์ฟเวอร์ (`useSession`) |
| ตอบแล้วไปสถานะไหนต่อ | เซิร์ฟเวอร์ (`resolveNextNode`) หน้าจอแค่ส่ง action ไปแล้วรับสถานะใหม่มาแสดง |
| ขั้นที่ผ่านมาแล้วมีอะไรบ้าง | หน้าจอเก็บเอง ใช้แสดงผลอย่างเดียว |

สิ่งที่**ห้าม**ทำในหน้านี้ และเหตุผล

- **ห้ามคำนวณเองว่าขั้นถัดไปคืออะไร** — ถ้าทำ จะมีจุดตัดสินใจสองจุด แล้วข้ออ้างว่าเครื่องสถานะเป็นผู้ตัดสินจะไม่จริงอีกต่อไป
- **ห้ามมีปุ่มย้อนกลับ** — กลไกควบคุมเครื่องสถานะไม่มีคำสั่งย้อน ถ้าหน้าจอทำปุ่มย้อนเอง จะกลายเป็นหน้าจอจำลองสถานะขึ้นมาเองโดยเซิร์ฟเวอร์ไม่รู้
- **ห้ามใส่ `nodeId` ลงใน URL** — ปุ่ม back ของเบราว์เซอร์จะพาผู้ใช้ไปขั้นที่เซิร์ฟเวอร์ผ่านไปแล้ว หน้าจอกับเซิร์ฟเวอร์จะไม่ตรงกัน
- **ห้ามตรวจรูปแบบรหัสที่ผู้ใช้กรอก** — การตัดสินว่ารหัสถูกหรือผิดเป็นการเปลี่ยนสถานะ (`on_invalid`) ซึ่งเป็นงานของเครื่องสถานะ

## 2. เส้นทางการตรวจ — ข้อมูลที่หน้าจอเก็บเอง

เซิร์ฟเวอร์ส่งมาแค่ **สถานะปัจจุบัน** ไม่ได้ส่งประวัติว่าเดินมาทางไหน เส้นทางที่เห็นทางซ้ายจึงเป็นของที่หน้าจอบันทึกเองใน `useState<TrailEntry[]>`

จังหวะการบันทึกสำคัญ: เติมรายการใหม่ใน `onSuccess` ของ `useSubmitAction` เท่านั้น คือหลังเซิร์ฟเวอร์รับ action แล้ว **ไม่ใช่ตอนกดปุ่ม** เพราะถ้าเซิร์ฟเวอร์ปฏิเสธ เช่นด่านความปลอดภัย เส้นทางต้องไม่มีรายการนั้น

และต้องใช้สถานะ **ก่อน** ส่ง คู่กับ action ที่เพิ่งส่ง

```ts
const nodeBefore = session.data.node   // จำไว้ก่อน
submit.mutate(action, {
  onSuccess: () => setTrail((previous) => [...previous, toTrailEntry(nodeBefore, action)]),
})
```

ถ้าเผลอใช้สถานะที่เซิร์ฟเวอร์เพิ่งตอบกลับมา เส้นทางจะแสดงคำถามถัดไปคู่กับคำตอบของคำถามก่อนหน้า

**ข้อจำกัดที่ยอมรับแล้ว (D7):** กด F5 แล้วเส้นทางหายหมด เหลือแต่ขั้นปัจจุบัน เพราะข้อมูลนี้อยู่ในหน่วยความจำของหน้าเว็บเท่านั้น เราเลือกทางนี้เพราะทางเลือกอื่นแย่กว่า

- เก็บใน `localStorage` — เสี่ยงหลุดจากความจริง ถ้าเซิร์ฟเวอร์ลบ session ไปแล้ว เส้นทางเก่าจะยังอยู่
- ให้เซิร์ฟเวอร์ส่งประวัติมาด้วย — ต้องแก้สัญญา API และเก็บประวัติในฐานข้อมูล ซึ่งเกินขอบเขตของขั้นนี้

การหายไปของเส้นทางไม่กระทบความถูกต้อง เพราะเส้นทาง**ไม่ได้ใช้ตัดสินใจอะไรเลย** สถานะจริงอยู่ที่เซิร์ฟเวอร์เสมอ

## 3. `key` สองที่ที่ต้องมี

### `key={node.nodeId}` ที่ `StepView`

ผังขั้นตอน `samsung_ac_ar70h_indicator_blinking` มีสถานะที่ต้องยืนยันคำเตือนสองสถานะติดกัน (`n_power_off` แล้ว `n_power_back_on`) ทั้งสองใช้กล่องแบบเดียวกัน ถ้าไม่มี key React จะใช้กล่องเดิมซ้ำ ช่องติ๊กจะค้างเป็นติ๊กมาจากสถานะแรก ผู้ใช้จะกดยืนยันสถานะที่สองได้ทันทีโดยไม่ได้อ่านคำเตือนใหม่

(รายละเอียดเต็มอยู่ในเอกสารขั้น 6 ข้อ 5)

แผงสาธิตก็ใส่ key เดียวกัน เพื่อให้ผลการสาธิตของขั้นก่อนไม่ค้างมาที่ขั้นใหม่

### `key={sessionId}` ที่ `SessionView`

หน้านี้แยกเป็นสองชั้น ชั้นนอก `SessionPage` อ่าน `sessionId` จาก URL แล้วส่งต่อให้ `SessionView` พร้อม key

เหตุผล: ตอนกด "เริ่มอาการนี้ใหม่" URL เปลี่ยนเป็น session ใหม่ แต่ React ใช้ component ตัวเดิม เส้นทางของ session เก่าจะค้างมาด้วย key ที่เปลี่ยนตาม `sessionId` บังคับให้สร้างใหม่ทั้งหมด state จึงเริ่มจากศูนย์

## 4. การกันกดเบิ้ล — ทำไม `isPending` อย่างเดียวไม่พอ

หน้านี้ส่ง `isPending` ของ mutation ลงไปให้ `StepView` ทุกปุ่มจะปิดตัวเอง **แต่ยังไม่พอ**

`isPending` เป็น state ของ React ซึ่งมีผลกับหน้าจอหลังจาก render รอบถัดไป ถ้าผู้ใช้ดับเบิลคลิกเร็วมาก คลิกที่สองอาจเกิดขึ้นก่อนปุ่มถูกปิด

**ทดสอบแล้วว่าเกิดจริง:** ลองเอาตัวกันออกชั่วคราว แล้วดับเบิลคลิก "ใช่" ที่คำถามแรกของอาการ "แอร์ไม่ทำงาน" ผลคือหน้าจอไปโผล่ที่ขั้น "สับเบรกเกอร์กลับขึ้น" เพราะคลิกที่สองไปตอบคำถาม "เบรกเกอร์ตัดอยู่หรือไม่?" ที่ผู้ใช้ยังไม่เคยเห็น

ทางแก้คือ `useRef` ซึ่งเปลี่ยนค่าทันทีโดยไม่ต้องรอ render

```ts
if (isSendingRef.current || session.data === undefined) return
isSendingRef.current = true
```

> **ปัญหาที่ลึกกว่าหน้าจอ**
> เรื่องนี้แสดงช่องโหว่ของสัญญา API คือ action ที่ส่งไปไม่ได้บอกว่าตั้งใจตอบ**สถานะไหน** เซิร์ฟเวอร์จึงแยกไม่ออกว่า "ใช่" ที่ได้รับเป็นคำตอบของคำถามปัจจุบัน หรือคำตอบค้างของคำถามก่อนหน้า
> ตอนนี้หน้าจอกันไว้แล้ว แต่ถ้ายิง HTTP ตรงก็ยังเกิดได้ ทางแก้ที่ควรพิจารณาตอนทำ REST API คือให้ action ส่ง `nodeId` ที่คาดไว้มาด้วย แล้วเซิร์ฟเวอร์ตอบ 409 ถ้าไม่ตรง — ยังไม่ได้ทำ เพราะต้องแก้ทั้งสัญญา API และกลไกควบคุมเครื่องสถานะ

ด้วยเหตุผลเดียวกัน ปุ่ม "ลองอีกครั้ง" ตอนเกิดข้อผิดพลาด**ไม่ได้ส่ง action เดิมซ้ำ** แต่ดึงสถานะล่าสุดจากเซิร์ฟเวอร์มาแทน ถ้าเน็ตหลุดหลังเซิร์ฟเวอร์รับคำตอบไปแล้ว การส่งซ้ำจะไปตอบคำถามถัดไป

## 5. การจัดการข้อผิดพลาด

`describeError()` แปลงข้อผิดพลาดเป็นสี่อย่าง: หัวข้อ คำอธิบาย สิ่งที่ทำต่อได้ (`recovery`) และรหัส (เฉพาะกรณี 500)

**ใช้ `code` ไม่ใช้ `message` จากเซิร์ฟเวอร์** เพราะ `message` ของกลไกควบคุมเครื่องสถานะเขียนไว้ให้นักพัฒนาอ่าน มีรหัสสถานะภาษาอังกฤษปนอยู่ ผู้ใช้ทั่วไปอ่านไม่เข้าใจ

| สถานการณ์ | หัวข้อ | `recovery` | ปุ่มที่ขึ้น |
|---|---|---|---|
| `NETWORK_ERROR` | เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ | `retry` | ลองอีกครั้ง |
| 400 `SAFETY_CONFIRMATION_REQUIRED` | เซิร์ฟเวอร์ไม่ให้ข้ามขั้นตอนนี้ | `stay` | ไม่มี — ผู้ใช้ติ๊กยืนยันที่กล่องเดิมได้เลย |
| 400 `INVALID_ACTION` | หน้าจอไม่ตรงกับเซิร์ฟเวอร์ | `reload-session` | ดึงขั้นตอนล่าสุด |
| 409 `SESSION_COMPLETED` | การตรวจนี้จบไปแล้ว | `reload-session` | ดึงขั้นตอนล่าสุด |
| 404 `SESSION_NOT_FOUND` | ไม่พบการตรวจนี้ | `back-to-symptoms` | เลือกอาการใหม่ |
| 404 `GRAPH_NOT_FOUND` | ไม่พบอาการนี้ | `back-to-symptoms` | เลือกอาการใหม่ |
| 500 `GRAPH_NODE_MISSING` / `GRAPH_SCHEMA_UNSUPPORTED` | ข้อมูลขั้นตอนของอาการนี้ไม่สมบูรณ์ | `back-to-symptoms` | เลือกอาการใหม่ + แสดงรหัส |
| อื่นๆ | เกิดข้อผิดพลาดที่ระบบไม่รู้จัก | `retry` | ลองอีกครั้ง |

แถว 500 เป็นกรณีที่ข้อมูลในฐานข้อมูลผิด ระบบ**หยุดไว้แทนการเดาขั้นตอนต่อ** ซึ่งตรงกับหลักการของโครงงานที่ไม่แต่งขั้นตอนขึ้นเอง และแสดงรหัสให้ผู้ใช้แจ้งผู้ดูแลระบบ

`describeError` แยกเป็นฟังก์ชันล้วนเพื่อให้เทสได้โดยไม่ต้องวาดหน้าจอ และ `errors.ts` ใช้ `switch` ที่มี `default` เพราะรหัสจากเซิร์ฟเวอร์เป็น string อะไรก็ได้ ต่างจาก `trail.ts` ที่ไม่มี `default` เพราะ `TraversalAction` เป็น type ปิด — ถ้าวันหนึ่งมี action แบบใหม่ TypeScript จะแจ้งว่าฟังก์ชันคืนค่าไม่ครบ

## 6. แผงสาธิตด่านความปลอดภัย และข้อจำกัดที่ต้องพูดตอนสอบ

แผงนี้เห็นเฉพาะเมื่อ URL มี `?demo=1` ไม่มีลิงก์ในเมนู กดปุ่มแล้วทำสามอย่าง

1. ส่ง `{ type: 'continue' }` ไปที่สถานะที่ต้องยืนยันคำเตือน โดยไม่ผ่านช่องติ๊กเลย
2. เรียก `getSession` ถามเซิร์ฟเวอร์ใหม่ว่าตอนนี้อยู่สถานะไหน — ไม่เชื่อค่าที่หน้าจอถืออยู่ เพราะสิ่งที่ต้องพิสูจน์คือสถานะ**ฝั่งเซิร์ฟเวอร์**ไม่ขยับ
3. แสดงสถานะ HTTP, `code`, และ `nodeId` ก่อนกับหลัง

บรรทัดสรุปขึ้นสีเขียว "ถูกปฏิเสธ และสถานะไม่ขยับ" เฉพาะเมื่อได้ 400 **และ** `nodeId` ก่อนกับหลังเท่ากัน ถ้าไม่ใช่ ขึ้นสีแดงว่าด่านอาจไม่ทำงาน แผงต้องรายงานตามจริงเสมอ ไม่ใช่ขึ้นเขียวตายตัว

### 🔴 ข้อจำกัด — แผงนี้ยังพิสูจน์ข้ออ้างหลักไม่ได้

ข้ออ้างหลักของโครงงานคือ **"ต่อให้ผู้ใช้แก้โค้ดหน้าเว็บ ก็ข้ามด่านความปลอดภัยไม่ได้ เพราะด่านอยู่ที่เซิร์ฟเวอร์"**

ตอนนี้ยังไม่มี REST API ระบบรันด้วยเซิร์ฟเวอร์จำลองที่อยู่ในเบราว์เซอร์ **โค้ดที่ปฏิเสธคำขอจึงอยู่ในเบราว์เซอร์เดียวกับคนกด** ผลที่แผงแสดงพิสูจน์ได้แค่ว่ากลไกควบคุมเครื่องสถานะปฏิเสธถูกต้อง ซึ่งเทสของกลไก 82 ข้อก็พิสูจน์ไว้แล้ว

กรรมการแย้งได้ทันทีว่า "ถ้าโค้ดที่ปฏิเสธอยู่ในเบราว์เซอร์ ก็แก้โค้ดนั้นทิ้งแล้วข้ามได้สิ"

**การสาธิตที่นับได้จริงต้องทำในขั้น 10.2** คือยิง HTTP request ตรงเข้าเซิร์ฟเวอร์บน Render โดยไม่ผ่านหน้าเว็บเลย แล้วให้เห็นว่าถูกปฏิเสธ

แผงจึงแสดงคำเตือนนี้เองทุกครั้งที่อยู่ในโหมดจำลอง เพื่อไม่ให้ใครเผลอเอาภาพหน้าจอตอนนี้ไปใส่รายงานเป็นหลักฐาน

## 7. แผงอุปกรณ์

รายการอุปกรณ์ผูกกับ**ประเภทเครื่อง** ไม่ได้ผูกกับอาการ ทุกอาการของแอร์จึงได้ 7 รายการเดียวกัน ใต้หัวข้อเขียนบอกไว้ตรงๆ ว่า "รายการเดียวกันสำหรับทุกอาการของเครื่องประเภทนี้" ผู้ใช้จะได้ไม่เข้าใจว่าอาการนี้ต้องใช้ครบทุกชิ้น

ทุกชิ้นบอกที่มาเสมอ ตามหลักการที่ห้ามอ้างว่าคู่มือพูดสิ่งที่ไม่ได้พูด

| เงื่อนไข | ที่มาที่แสดง |
|---|---|
| มี `sourcePage` | ไอคอนหนังสือ + "คู่มือหน้า 43" |
| ไม่มี แต่มี `authorNote` | ไอคอนดินสอ + "ผู้พัฒนาแนะนำเพิ่ม" |
| ไม่มีทั้งคู่ (ผิดสัญญา API) | ไม่แสดงอะไร — ดีกว่าเดาที่มาให้ |

ของแอร์มี 7 รายการ อ้างคู่มือได้ 2 รายการ ที่เหลือผู้พัฒนาเพิ่มเอง

บนมือถือแผงพับไว้ เพราะถ้ากาง 7 รายการ คำถามแรกจะถูกดันออกนอกจอ ใช้คลาส `md:hidden` กับ `md:block` สลับกัน ไม่ต้องเขียนโค้ดตรวจขนาดจอเอง

## 8. เส้นทางการตรวจ (`PathRail`) — ส่วนเดียวที่ดีไซน์ตั้งใจให้โดดเด่น

| รายการ | สัญลักษณ์ |
|---|---|
| ขั้นที่ผ่านแล้วทั่วไป | วงกลมกลวง |
| ขั้นที่ยืนยันคำเตือนแล้ว | ไอคอนสวิตช์ปิด |
| ขั้นปัจจุบันทั่วไป | วงกลมทึบสีหลัก |
| ขั้นปัจจุบันที่ต้องยืนยันคำเตือน | ไอคอนสวิตช์เปิดสีแดง |
| สถานะสิ้นสุด | สี่เหลี่ยมเล็ก สีตาม `outcomeKind` |

สวิตช์เปิดสีแดงที่กลายเป็นสวิตช์ปิดหลังยืนยัน ทำให้ผู้ใช้เห็นย้อนหลังได้ว่าผ่านขั้นอันตรายมาแล้วกี่ขั้น

การจัดวาง: เส้นและจุดวางด้วย `absolute` โดยกึ่งกลางอยู่ที่ 12px จากซ้ายเท่ากัน เส้นแบ่งเป็นท่อน รายการละท่อน ระยะห่างระหว่างรายการจึงต้องใช้ `padding` ไม่ใช่ `margin` ไม่งั้นเส้นจะขาดตรงช่องว่าง จุดมีพื้น `bg-canvas` ทับเส้นด้านหลัง

`key` ของรายการใช้ลำดับประกอบกับ `nodeId` เพราะ `nodeId` ซ้ำได้จริง — กรอกรหัสผิดแล้ววนกลับมาที่ `n_record_code` อีกรอบ

## 9. การตัดสินใจระหว่างทำที่ไม่ได้อยู่ในแผน

| เรื่อง | ทำอะไร | เหตุผล |
|---|---|---|
| สีเส้นของ `PathRail` | เปลี่ยนจาก `bg-line` เป็น `bg-ink-faint/50` | ถ่ายภาพหน้าจอดูแล้วเส้นกลืนไปกับพื้นจนแทบมองไม่เห็น ขัดกับที่ดีไซน์ตั้งใจ |
| แยก `SessionPage` เป็นสองชั้น | เพิ่ม `SessionView key={sessionId}` | เส้นทางของ session เก่าค้างตอนกด "เริ่มอาการนี้ใหม่" |
| กันกดเบิ้ลด้วย `useRef` | เพิ่มจาก `isPending` | ทดสอบแล้วว่า `isPending` อย่างเดียวกันไม่ได้ (ข้อ 4) |
| ปุ่ม "ยกเลิกการตรวจ" | กลับหน้าเลือกอาการเสมอ แม้เซิร์ฟเวอร์ลบไม่สำเร็จ | ผู้ใช้ตั้งใจออกแล้ว session ที่ค้างหมดอายุเองฝั่งเซิร์ฟเวอร์ |
| ปุ่ม "ลองอีกครั้ง" | ดึงสถานะล่าสุด ไม่ส่ง action เดิมซ้ำ | กันการตอบซ้ำเมื่อเน็ตหลุดหลังเซิร์ฟเวอร์รับไปแล้ว |
