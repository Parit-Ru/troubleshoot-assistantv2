# ขั้น 8 — หน้าแรก

ขั้นนี้เปลี่ยนหน้า `/` จากฉบับชั่วคราวให้เป็นหน้าจริง หน้านี้เป็นหน้าแรกที่ผู้ใช้และกรรมการเห็น หน้าที่คือบอกด้วยภาษาผู้ใช้ทั่วไปว่าระบบทำอะไร และต่างจากการถาม AI ตรงไหน

| ไฟล์ | หน้าที่ |
|---|---|
| `src/pages/HomePage.tsx` | หน้าแรก (แทนที่ฉบับชั่วคราวของขั้น 4) |
| `docs/explained/08-home-page.md` | เอกสารนี้ |

เทสรวมยังเป็น 43 ข้อ ไม่เพิ่ม เพราะหน้านี้ไม่มีตรรกะของตัวเอง ส่วนที่เป็นตรรกะ (`groupSymptoms`, `toTrailEntry`, `formatSourceLine`) มีเทสอยู่แล้วจากขั้นก่อนหน้า

> **ศัพท์:** เอกสารนี้ใช้คำว่า ผังขั้นตอนการวินิจฉัย / เครื่องสถานะ / สถานะ / การเปลี่ยนสถานะ ตาม `PROJECT_CONTEXT.md` ข้อ 3

## 1. หน้านี้มีอะไรบ้าง

| ส่วน | เนื้อหา | มาจากไหน |
|---|---|---|
| ข้อความแนะนำ | หัวข้อสองบรรทัด ย่อหน้าอธิบาย ปุ่ม "เลือกอาการที่พบ" ไป `/symptoms` | เขียนในหน้านี้ |
| รองรับตอนนี้ | ชื่อประเภทเครื่อง ยี่ห้อ รุ่น และจำนวนอาการ | `useGraphs()` + `groupSymptoms()` |

```
      ↓ toTrailEntry()
PathRail             ← ภาพตัวอย่าง (ภาพนิ่ง)
```

## 2. ทำไมไม่มีตัวเลขสถิติ

ดีไซน์ใน Figma มีกล่องตัวเลข เช่น จำนวน chunk จำนวนคู่มือ และค่าความมั่นใจเฉลี่ย ขั้นนี้ตัดออกทั้งหมด

- **ไม่มีข้อมูลจริงรองรับ** ระบบตอนนี้ไม่มีตัวนับ chunk ไม่มีการคำนวณความมั่นใจ (การจับคู่อาการด้วยภาษาธรรมชาติยังไม่ได้ทำ) และมีคู่มือเดียว ตัวเลขเหล่านั้นจึงเป็นตัวเลขที่แต่งขึ้น
- **ขัดกับหลักของโครงงาน** ระบบนี้ขายเรื่อง "ไม่แต่งข้อมูลขึ้นเอง" ถ้าหน้าแรกโชว์ตัวเลขที่ไม่จริง กรรมการถามข้อเดียวก็เสียความน่าเชื่อถือของทั้งระบบ
- **ไม่ใช้ศัพท์เทคนิค** ไม่มีคำว่า RAG หรือชื่อวิธีใดๆ หน้านี้เขียนให้ผู้ใช้ทั่วไปอ่าน ส่วนกลไกภายในอธิบายในเอกสารโครงงานและตอนสอบ

ไม่มีลิงก์ไปหน้า `/gallery` เพราะเป็นหน้าสำหรับนักพัฒนา

## 3. ทำไม "รองรับตอนนี้" ดึงจากข้อมูลจริง

ข้อความ "เครื่องปรับอากาศ Samsung AR70H\*\*D1\*\*\* / 13 อาการ" ไม่ได้พิมพ์ตายตัวในหน้า แต่สร้างจาก `useGraphs()` แล้วส่งเข้า `groupSymptoms()` ตัวเดียวกับที่หน้าเลือกอาการใช้ จำนวนอาการคือ `group.symptoms.length`

เหตุผลมีสองข้อ

1. **ไม่มีทางโกหก** ถ้าพิมพ์ตายตัวว่า "13 อาการ" แล้ววันหนึ่งข้อมูลเปลี่ยน หน้าแรกจะบอกสิ่งที่ไม่จริงโดยไม่มีใครรู้ตัว
2. **เพิ่มเครื่องใหม่แล้วขึ้นเอง** เมื่อทำผังขั้นตอนของตู้เย็น เครื่องซักผ้า หรือโทรทัศน์เสร็จ (งานข้อ 5 ในแผน) หน้านี้แสดงเพิ่มเองโดยไม่ต้องแก้โค้ด

จัดกลุ่มด้วย ประเภทเครื่อง + ยี่ห้อ + รุ่น เหมือนหน้าเลือกอาการ (ดูขั้น 5) รุ่นแสดงด้วย `font-mono` เพราะเป็นรหัส

## 4. ภาพตัวอย่าง: ทำไมเป็นภาพนิ่ง และทำไมไม่ใช้ `StepView`

ภาพตัวอย่างมีไว้ให้ผู้ใช้เห็นว่าเมื่อใช้ระบบแล้วจะเจออะไร: ถามทีละข้อ มีเส้นทางบอกว่าผ่านอะไรมาแล้ว มีคำเตือนก่อนขั้นอันตราย และมีที่มา

### เส้นทางที่แสดง เป็นเส้นทางจริงของข้อมูล

```
n1 เครื่องได้รับไฟฟ้าอยู่หรือไม่? (ตรวจปลั๊ก/เต้ารับ)   → ตอบ ใช่
n2 เบรกเกอร์ไฟฟ้า (circuit breaker) ตัดอยู่หรือไม่?      → ตอบ ใช่
n_fix_breaker สับเบรกเกอร์กลับขึ้น แล้วลองเปิดเครื่องใหม่  ← ขั้นที่ต้องยืนยันคำเตือน
```

ข้อความทุกข้อคัดลอกจาก `data/manuals/samsung_ac_ar70h.json` ตรงๆ

### สถานะ n1 สร้างในหน้านี้

`fixtures.ts` มี `n2` (`checkpointNode`) กับ `n_fix_breaker` (`safetyGateNode`) แต่ไม่มี `n1` ถ้าใช้ `checkpointNode` สองครั้ง ข้อความจะซ้ำกัน หน้านี้จึงสร้าง `POWER_CHECKPOINT` ขึ้นจาก `checkpointNode` โดยเปลี่ยนแค่รหัสกับข้อความ

```ts
const POWER_CHECKPOINT: RenderedNode = {
  ...checkpointNode,
  nodeId: 'n1',
  text: 'เครื่องได้รับไฟฟ้าอยู่หรือไม่? (ตรวจปลั๊ก/เต้ารับ)',
}
```

ส่วนที่มา (คู่มือหน้า 43) ใช้ของ `checkpointNode` ต่อได้ เพราะตรวจแล้วว่า `n1` อยู่หน้า 43 เหมือนกัน

เลือกไม่แก้ `fixtures.ts` เพราะเป็นไฟล์ของขั้น 4–6 ที่ปิดไปแล้ว และหน้า gallery ใช้ไฟล์นี้ถ่ายภาพลงรายงาน

### สองขั้นที่ผ่านมา สร้างด้วย `toTrailEntry` ตัวเดิม

คำว่า "ตอบ ใช่" ไม่ได้พิมพ์ในหน้านี้ มาจาก `toTrailEntry` ตัวเดียวกับที่หน้าตรวจอาการใช้ ถ้าวันหนึ่งเปลี่ยนคำ ภาพตัวอย่างเปลี่ยนตามเอง

### ทำไมไม่ใช้ `StepView` หรือ `StepCard`

- `StepView` มีปุ่มที่กดได้จริง แต่กดแล้วไม่มีอะไรเกิดขึ้น ผู้ใช้จะงง
- `StepCard` ใส่ `ReferenceLine` ให้อัตโนมัติ ซึ่งมีปุ่ม "ดูรหัสเอกสาร" ที่กดได้ ในภาพที่ควรเป็นภาพนิ่ง

จึงเขียนกล่องอ่านอย่างเดียวในไฟล์นี้เอง ขอบแดง (`border-2 border-danger`) และระยะห่างเหมือน `StepCard` ที่ใช้ `tone="danger"` ส่วนเส้นทางทางซ้ายใช้ `PathRail` ตัวจริง เพราะ `PathRail` แสดงผลอย่างเดียวอยู่แล้ว ไม่มีปุ่ม

ภาพตัวอย่างห่อด้วย `<figure>` และมี `<figcaption>` "ตัวอย่างจากอาการ แอร์ไม่ทำงาน เปิดไม่ติด" เพื่อให้โปรแกรมอ่านหน้าจอรู้ว่าเป็นตัวอย่าง ไม่ใช่การตรวจที่กำลังทำอยู่

### ภาพตัวอย่างไม่ได้พิสูจน์ด่านความปลอดภัย

ภาพนี้แสดงแค่ว่าผู้ใช้จะเห็นอะไร ไม่ได้พิสูจน์ว่าระบบบังคับด่านได้ การบังคับจริงอยู่ที่ `resolveNextNode` ฝั่งเซิร์ฟเวอร์ พิสูจน์ได้จากเทสของกลไกควบคุมเครื่องสถานะ และจะสาธิตกับเซิร์ฟเวอร์จริงในขั้น 10.2

### ข้อความในภาพที่ผู้พัฒนาเขียนเอง

- **คำเตือนความปลอดภัยของ `n_fix_breaker`** ผู้พัฒนาเขียนเอง ไม่มีในคู่มือต้นฉบับ (มี `author_note` กำกับในข้อมูล) เหมือนที่เอกสารขั้น 6 อธิบายไว้ บรรทัดที่มาจึงใช้คำว่า "ที่มาของขั้นตอนนี้" ซึ่งผูกกับตัวขั้นตอน ไม่ได้บอกว่าคำเตือนมาจากคู่มือ
- **บรรทัด "ต้องยืนยันว่าอ่านคำเตือนแล้ว จึงจะไปขั้นต่อไปได้"** ผู้พัฒนาเขียนขึ้นเพื่ออธิบายภาพตัวอย่าง แทนช่องติ๊กและปุ่มจริง ไม่ได้มาจากข้อมูล

## 5. ทำไมโหลดข้อมูลไม่สำเร็จแล้วซ่อนเงียบๆ

| กรณี | ส่วน "รองรับตอนนี้" |
|---|---|
| กำลังโหลด | แสดงหัวข้อกับข้อความ "กำลังโหลด" ส่วนอื่นของหน้าแสดงตามปกติ |
| โหลดสำเร็จ มีข้อมูล | แสดงรายการ |
| โหลดไม่สำเร็จ | **ซ่อนทั้งส่วน** ไม่มีกล่องแดง |
| โหลดสำเร็จ แต่ไม่มีข้อมูล | ซ่อนทั้งส่วน |

เหตุผลที่ไม่ขึ้นกล่องแดง

1. **หน้าแรกยังใช้งานได้** ข้อความแนะนำ ปุ่ม และภาพตัวอย่างไม่ต้องพึ่งเซิร์ฟเวอร์ กล่องแดงบนหน้าที่ใช้งานได้ปกติทำให้ผู้ใช้ตกใจโดยไม่จำเป็น
2. **หน้าเลือกอาการแจ้งข้อผิดพลาดเองอยู่แล้ว** พร้อมปุ่ม "ลองอีกครั้ง" ผู้ใช้ที่กดปุ่มหลักจะเจอที่นั่น และ `AppShell` ก็มีป้ายสถานะเซิร์ฟเวอร์อยู่แล้ว
3. **ส่วนนี้เป็นข้อมูลเสริม** ถ้าหายไป ผู้ใช้เสียแค่รู้ว่ารองรับเครื่องรุ่นไหน ไม่เสียความสามารถหลัก

`App.tsx` ตั้ง `retry: false` ตอนโหลดไม่สำเร็จจึงเปลี่ยนเป็นสถานะผิดพลาดทันที ไม่มีข้อความ "กำลังโหลด" ค้าง

**ข้อแลกเปลี่ยนที่รู้ตัว:** ผู้ใช้แยกไม่ออกว่าส่วนนี้หายเพราะโหลดไม่สำเร็จหรือเพราะไม่มีข้อมูล ยอมรับได้เพราะสองกรณีนี้ผลต่อผู้ใช้เท่ากัน

## 6. การจัดวางสองคอลัมน์

ใช้ CSS grid ระบุตำแหน่งชัดเจนบนจอ `lg:` (กว้างตั้งแต่ 1024px)

| จอ | ลำดับ |
|---|---|
| มือถือ / จอกลาง | ข้อความแนะนำ → **ภาพตัวอย่าง** → รองรับตอนนี้ (ภาพตัวอย่างอยู่ใต้ปุ่มทันที) |
| `lg:` ขึ้นไป | ซ้าย: ข้อความแนะนำ แล้วรองรับตอนนี้ / ขวา: ภาพตัวอย่างสูงข้ามสองแถว |

เพราะลำดับใน HTML กับตำแหน่งบนจอใหญ่ไม่ตรงกัน ทุกส่วนจึงระบุ `lg:col-start-*` และ `lg:row-start-*` เอง แถวล่างเป็น `1fr` ให้รับความสูงที่เหลือ กันไม่ให้ช่องว่างไปโผล่ระหว่างข้อความแนะนำกับ "รองรับตอนนี้"

หัวข้อแยกสองบรรทัดด้วย `<span className="block">` ให้บรรทัดหักตรงวลีเสมอ ไม่ให้เบราว์เซอร์ตัดกลางคำ

ปุ่มใช้ `Button` กับ `useNavigate` เหมือนหน้าเลือกอาการ ไม่ใช้ `<Link>` เพราะ `Button` ไม่มีแบบที่เป็นลิงก์ และไม่อยากเขียนคลาสปุ่มซ้ำอีกชุด

## 7. การตัดสินใจระหว่างทำที่ไม่ได้อยู่ในแผน

| เรื่อง | ที่ทำ | เหตุผล |
|---|---|---|
| สถานะแรกของภาพตัวอย่าง | สร้าง `POWER_CHECKPOINT` ในหน้านี้ ไม่แก้ `fixtures.ts` | `fixtures.ts` ไม่มี `n1` และเป็นไฟล์ที่ปิดไปแล้ว (ผู้พัฒนาเลือกวิธีนี้) |

| ห่อภาพตัวอย่าง | `<figure>` + `<figcaption>` | บอกโปรแกรมอ่านหน้าจอว่าเป็นตัวอย่าง |

| การจัดวาง | grid ระบุตำแหน่งเอง | ต้องให้ภาพตัวอย่างอยู่ใต้ปุ่มบนมือถือ แต่อยู่ขวาบนจอใหญ่ |

## 8. ข้อจำกัดที่รู้ตัว

- **ประโยค "ขั้นตอนที่เกี่ยวกับไฟฟ้าต้องยืนยันคำเตือนก่อนทุกครั้ง" กว้างกว่าที่ข้อมูลเป็นจริงเล็กน้อย** ข้อมูลตอนนี้มีสถานะที่ต้องยืนยันคำเตือนเพียง 3 สถานะ (`n_power_off`, `n_power_back_on` ในอาการไฟแสดงสถานะกะพริบ และ `n_fix_breaker` ในอาการแอร์ไม่ทำงาน) ทั้งสามเกี่ยวกับไฟฟ้า แต่สถานะไฟฟ้าอื่น เช่น `n_fix_power` (เสียบปลั๊กให้แน่น ลองเสียบอุปกรณ์อื่นทดสอบเต้ารับ) ไม่ได้ตั้งให้ต้องยืนยัน คำที่ตรงกว่าคือ "ขั้นตอนที่ระบบระบุว่าเสี่ยงไฟฟ้า"
- **ยังไม่มีเทสอัตโนมัติของหน้า** ตรวจด้วยเบราว์เซอร์ เหมือนขั้น 4–6
- **ลำดับอ่านของโปรแกรมอ่านหน้าจอไม่ตรงกับตำแหน่งบนจอใหญ่** ในโค้ด ภาพตัวอย่างมาก่อน "รองรับตอนนี้" (เพื่อให้มือถือเรียงถูก) ผู้ใช้โปรแกรมอ่านหน้าจอจะได้ยินภาพตัวอย่างก่อนรายการเครื่องที่รองรับ ซึ่งยังเข้าใจได้
- **ปุ่มหลักยังเป็น `text-sm`** ตามปุ่มอื่นของแอป ดีไซน์ต้นฉบับใหญ่กว่านี้ จะทบทวนในขั้น 9.1
