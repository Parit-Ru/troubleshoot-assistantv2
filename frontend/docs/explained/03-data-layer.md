# ขั้น 3 — ชั้นข้อมูล

ขั้นนี้ยังไม่มีหน้าจอ แต่เป็นทุกอย่างที่หน้าจอต้องใช้ในการคุยกับเซิร์ฟเวอร์

| ไฟล์ | หน้าที่ |
|---|---|
| `src/env.d.ts` | บอกชนิดของตัวแปรจาก `.env` |
| `src/api/types.ts` | สัญญาว่าข้อมูลหน้าตาเป็นอย่างไร |
| `src/api/http.ts` | ประตูเดียวที่ทุกการเรียกเซิร์ฟเวอร์ต้องผ่าน |
| `src/api/http.test.ts` | เทส 5 ข้อของ `http.ts` |
| `src/mocks/fixtures.ts` | โหนดตัวอย่าง 8 สถานะจากกราฟจริง |
| `src/mocks/mockServer.ts` | เซิร์ฟเวอร์จำลองที่ใช้ engine ตัวจริง |
| `src/mocks/mockServer.test.ts` | เทส 10 ข้อของเซิร์ฟเวอร์จำลอง |
| `src/api/traversal.ts` | หนึ่งฟังก์ชันต่อหนึ่ง endpoint และจุดสลับ mock |
| `src/api/queries.ts` | hook ของ React Query ที่หน้าจอเรียกใช้ |

ผลรวมเทส 15 ข้อ ผ่านทั้งหมด

## 1. เรื่องที่พบระหว่างทำขั้นนี้

ตอนเขียน `types.ts` ได้ไล่ตรวจไฟล์ทั้งหมดใน `backend/src` แล้วพบว่า **REST API ยังไม่มีอยู่จริง** มีแค่ engine, `graph.repository.ts`, health และ database ไม่มี controller, service, session store และไม่มีเทส e2e เทส 82 ตัวที่ผ่านเป็นของ engine ล้วน

ตัดสินใจทำ frontend ให้จบก่อนด้วยโหมดจำลอง แล้วค่อยทำ API

ผลที่ตามมาสองข้อ

1. **ไฟล์ในขั้นนี้กลายเป็นสัญญาที่ backend ต้องทำตาม** ไม่ใช่สิ่งที่เดาจากโค้ดที่มีอยู่ ตอนเขียน REST API จริง ต้องเปิด `mockServer.ts` กับ `mockServer.test.ts` ดู แล้วทำให้ตรงกันทุกข้อ
2. **แผงสาธิตในขั้น 7.7 จะยังพิสูจน์อะไรไม่ได้** จนกว่าจะมี REST API จริง เพราะในโหมดจำลอง โค้ดที่ปฏิเสธคำสั่งอยู่ในเบราว์เซอร์เดียวกับคนกด

## 2. ข้อมูลไหลผ่านไฟล์ไหนบ้าง

```
หน้าจอ
  │ เรียก hook
  ▼
queries.ts        React Query จำผลไว้ในแคช
  │ เรียกฟังก์ชัน
  ▼
traversal.ts      เช็คว่า VITE_USE_MOCK เป็น 'true' ไหม
  ├─ ใช่ ────► mockServer.ts ────► engine ตัวจริงใน backend/
  └─ ไม่ใช่ ──► http.ts ──────────► REST API จริง
```

มีจุดเดียวในทั้งแอปที่รู้ว่ามี mock อยู่ คือ `traversal.ts` หน้าจอไม่รู้เลยว่าข้างหลังเป็นอะไร

## 3. `env.d.ts`

ไฟล์ `.d.ts` บอก TypeScript ว่าอะไรมีชนิดเป็นอะไร โดยไม่สร้างโค้ดจริง ตอน build หายไปทั้งไฟล์

ดักสองกรณีที่อันตราย คือพิมพ์ชื่อตัวแปรผิด และเอาไปใช้ผิดประเภท กรณีหลังอันตรายที่สุด ถ้าเขียน `if (import.meta.env.VITE_USE_MOCK)` จะเป็นจริงเสมอ แม้ค่าจะเป็นคำว่า false เพราะข้อความที่ไม่ว่างถือเป็นจริงใน JavaScript ผลคือเว็บจริงจะใช้เซิร์ฟเวอร์จำลอง ซึ่งไม่มีการบังคับด่านความปลอดภัยฝั่งเซิร์ฟเวอร์

`VITE_USE_MOCK` ประกาศเป็น `string` ไม่ใช่ `boolean` เพราะค่าจากไฟล์ `.env` เป็นข้อความเสมอ ต้องเทียบ `=== 'true'` ทุกครั้ง

## 4. `types.ts`

แบ่งเป็น 3 กลุ่มตามระดับความมั่นใจ

| กลุ่ม | ที่มา | ความมั่นใจ |
|---|---|---|
| type ของ engine | re-export จาก `backend/src/traversal-engine/types.ts` | แน่นอน เป็นไฟล์เดียวกัน |
| `GraphSummary` | ลอกจาก `graph.repository.ts` | แน่นอน เทียบกับโค้ดจริงแล้ว |
| `SessionResponse`, `EquipmentItem`, `ApiErrorBody` | เสนอเอง | **ยังไม่ยืนยัน** รอ REST API |

### `export type` กับ `import type` ต่างกันอย่างไร

`export type { ... } from` เป็นการส่งต่อชื่อออกไปให้ไฟล์อื่นใช้ **ไม่ได้ทำให้ชื่อนั้นใช้ได้ในไฟล์ตัวเอง** ชื่อไหนที่ไฟล์นี้ใช้เองด้วย ต้องอยู่ในบรรทัด `import type` ด้วย

เคยพลาดข้อนี้ระหว่างทำ ลืมใส่ `SessionStatus` ในบรรทัด `import type` ได้ error ว่า Cannot find name 'SessionStatus'

### ทำไมต้องลอก `GraphSummary` แทน import

`graph.repository.ts` import NestJS ถ้า frontend แตะไฟล์นั้น จะลาก NestJS ทั้งก้อนเข้ามา ราคาที่จ่ายคือถ้าฝั่ง backend แก้ `GraphSummary` ต้องมาแก้ตามที่นี่ด้วย

## 5. `http.ts`

### ทำไมต้องมี `ApiError` ของตัวเอง

ความล้มเหลวมาได้สามทาง และหน้าตาไม่เหมือนกันเลย

| ทาง | `fetch` ทำอะไร |
|---|---|
| เน็ตไม่ติด เซิร์ฟเวอร์ดับ หรือ CORS | โยน `TypeError` |
| เซิร์ฟเวอร์ตอบ 400 หรือ 500 | **ไม่โยนอะไรเลย** ถือว่าสำเร็จ ต้องเช็ค `response.ok` เอง |
| body แปลง JSON ไม่ได้ | โยนตอนเรียก `.json()` |

ถ้าไม่รวบให้เป็นแบบเดียว ทุกหน้าจอต้องเขียนโค้ดแยกแยะเองทั้งสามแบบ

### ทำไมอ่าน `VITE_API_URL` ในฟังก์ชัน ไม่ใช่บนสุดของไฟล์

1. ถ้าอ่านตอน import แล้วค่าหาย แอปจะพังเป็นหน้าขาวก่อน React ได้วาดอะไร ไม่มีที่แสดงข้อความบอกสาเหตุ
2. เทสใช้ `vi.stubEnv` ซึ่งสั่งหลัง import ไปแล้ว ถ้าอ่านตอน import จะไม่ทัน

### ทำไมไม่มีค่าสำรองเป็น localhost

นี่คือบั๊กเดิมของ `lib/api.ts` ที่ทำให้เว็บซึ่ง deploy แล้วไปเรียกเซิร์ฟเวอร์ในเครื่องของผู้ใช้เอง เทสข้อสุดท้ายของ `http.test.ts` มีไว้กันไม่ให้ใครเผลอเอาค่าสำรองกลับมาใส่

### ทำไมเขียน field แยกบรรทัด

`tsconfig.app.json` ตั้ง `erasableSyntaxOnly` ไว้ ซึ่งห้ามไวยากรณ์แบบย่อ `constructor(readonly status: number)` ต้องประกาศ field แล้วกำหนดค่าใน constructor ตามปกติ

## 6. `fixtures.ts`

โหนดตัวอย่าง 8 สถานะ ใช้ในหน้า gallery ภาพตัวอย่างในหน้าแรก และเทสของ component

ข้อความทุกข้อความคัดลอกจาก `data/manuals/samsung_ac_ar70h.json` ตรงๆ ไม่มีข้อความไหนที่แต่งขึ้น เพราะภาพหน้าจอจากหน้า gallery จะถูกเอาไปใส่รายงาน และการสร้างเนื้อหาขึ้นเองขัดหลักการของโครงงาน

ต่างจาก `mockServer.ts` ตรงที่ไฟล์นี้ตอบแค่ว่ากล่องขั้นตอนแต่ละแบบหน้าตาเป็นอย่างไร ไม่ได้ตอบว่ากดแล้วไปไหนต่อ

จุดที่ต้องรู้คือ `handoffInformedNode` ในไฟล์กราฟเขียนว่า `{{error_code}}` แต่ที่นี่เป็น `E1` แล้ว เพราะเซิร์ฟเวอร์แทนค่าให้ก่อนส่งมา ไฟล์นี้จำลองสิ่งที่หน้าจอได้รับ

## 7. `mockServer.ts`

### ไม่มีตรรกะเดินกราฟเลย

ใช้ engine ตัวเดียวกับเซิร์ฟเวอร์จริง และไฟล์กราฟตัวเดียวกับที่ backend โหลด สิ่งที่จำลองคือชั้น HTTP เท่านั้น

ถ้าเขียนตรรกะขึ้นใหม่ จะมีตรรกะสองชุด แล้ววันหนึ่งเพี้ยนจากกัน หน้าจอจะโกหกเรื่องด่านความปลอดภัย

### ทำไมสถานะไม่ขยับเวลาถูกปฏิเสธ

ไม่ได้เขียนโค้ดย้อนสถานะเลย engine เป็น pure function คืน session ใหม่โดยไม่แก้ของเดิม ถ้ามันโยน error บรรทัด `sessions.set` จะไม่ถูกรัน สถานะเก่าจึงอยู่ครบโดยอัตโนมัติ

นี่คือประโยชน์ของการออกแบบให้ engine ไม่แก้ของเดิม ความถูกต้องมาจากโครงสร้าง ไม่ต้องพึ่งการจำว่าต้องย้อนอะไรบ้าง

### ตารางแปลง error เป็นรหัส HTTP

| error จาก engine | status | code |
|---|---|---|
| `SafetyConfirmationRequiredError` | 400 | `SAFETY_CONFIRMATION_REQUIRED` |
| `InvalidActionError` | 400 | `INVALID_ACTION` |
| `SessionAlreadyCompletedError` | 409 | `SESSION_COMPLETED` |
| `NodeNotFoundError` | 500 | `GRAPH_NODE_MISSING` |
| `UnsupportedSchemaVersionError` | 500 | `GRAPH_SCHEMA_UNSUPPORTED` |
| ไม่พบ session | 404 | `SESSION_NOT_FOUND` |
| ไม่พบกราฟ | 404 | `GRAPH_NOT_FOUND` |

**exception filter ของ REST API จริงต้องแปลงตามตารางนี้ทุกแถว**

### ข้อจำกัด

session อยู่ในหน่วยความจำของแท็บ กด F5 แล้วหายหมด การทดสอบว่า refresh แล้วยังอยู่ขั้นเดิม ต้องรอเซิร์ฟเวอร์จริงในขั้น 10.2

หน่วงเวลา 300 มิลลิวินาทีเพื่อให้เห็นสถานะกำลังโหลด ตอนรันเทสตั้งเป็น 0

## 8. เทสของเซิร์ฟเวอร์จำลอง

### ทำไมต้องเทสของปลอม

mock ไม่ได้ปลอมตรรกะ ใช้ engine ตัวจริง เทสจึงตรวจสองอย่าง คือ engine ทำงานถูกเมื่อรันในเบราว์เซอร์ และการแปลง error เป็นรหัส HTTP ถูกต้อง

### เทสที่สำคัญที่สุด

ข้อที่ส่ง `continue` ที่ด่านความปลอดภัย เพราะเป็นข้อสอบหลักของโครงงาน ตรวจสองชั้น คือเซิร์ฟเวอร์ต้องตอบ 400 **และ** ต้องอ่านสถานะซ้ำแล้วยังอยู่โหนดเดิม

ชั้นที่สองสำคัญมาก เพราะระบบที่ตอบ error แล้วแอบเดินต่อ จะแย่กว่าระบบที่ไม่มีด่านเลย

### เทสที่คิดว่าไม่ต้องมี แต่ต้องมี

**ยืนยันคำเตือนแล้วต้องเดินต่อได้** ด่านที่บล็อกทุกอย่างก็ผิด ถ้ามีแต่เทสว่าบล็อกได้ จะไม่รู้ว่าผ่านไม่ได้เลยสักทาง

**กรอกรหัสผิดต้องไม่เป็น error** การกรอกผิดเป็นเส้นทางหนึ่งในกราฟ พาไปโหนดอธิบายรูปแบบรหัส หน้าจอจึงห้ามตรวจรูปแบบเอง

**ข้อความหน้าจบต้องไม่มี `{{` ค้าง** ถ้าการแทนค่าพัง ผู้ใช้จะเห็น `{{error_code}}` บนหน้าจอ

## 9. `traversal.ts`

### ทำไมใช้ `await import(...)` ไม่ใช่ `import` ธรรมดา

นี่คือหัวใจของไฟล์นี้ ถ้า import ธรรมดา engine กับไฟล์กราฟทั้งหมดจะติดเข้า build จริงเสมอ

ตอน build Vite แทนค่า `import.meta.env.VITE_USE_MOCK` เป็นข้อความ `'false'` ตรงๆ เงื่อนไข `'false' === 'true'` เป็นเท็จแน่นอน Vite จึงตัดโค้ดข้างในทิ้งพร้อมไฟล์ `mockServer` ทั้งไฟล์

ผลทดสอบ build จริง

| โหมด | ไฟล์ JS ที่ได้ | มีข้อมูลกราฟใน build |
|---|---|---|
| `VITE_USE_MOCK=false` | ไฟล์เดียว | ไม่มีเลย |
| `VITE_USE_MOCK=true` | 2 ไฟล์ แยก `mockServer` ออกมา | มีเฉพาะในไฟล์ mock |

### ข้อควรระวัง

เงื่อนไขต้องเขียนตรงๆ ในทุกฟังก์ชัน ห้ามเก็บลงตัวแปรไว้ใช้ซ้ำ เพราะ Vite อาจตัดโค้ดไม่ได้ และข้อมูลกราฟจะหลุดเข้า build จริง

### ทำไม `getHealth` ไม่มีทางไป mock

หน้าที่ของมันคือเช็คว่าเซิร์ฟเวอร์จริงยังอยู่ไหม ถ้า mock ตอบแทนได้ก็ไม่มีความหมาย

### ทำไมต้อง `encodeURIComponent`

sessionId มาจาก URL ที่ผู้ใช้แก้เองได้ ถ้ามี `/` หรือ `?` ปนมา จะกลายเป็นเรียก endpoint ผิดตัว

### สัญญาเพิ่มเติมที่ backend ต้องทำตาม

`POST /traversal/sessions` รับ body `{ graphId }` ฟิลด์เดียว ส่วน `POST /traversal/sessions/:id/actions` รับ `TraversalAction` ตรงๆ ตามที่ engine กำหนด

## 10. `queries.ts`

### hook สองแบบ

| แบบ | ใช้เมื่อ | ทำงานเมื่อ |
|---|---|---|
| `useQuery` | อ่านข้อมูล | หน้าจอแสดง |
| `useMutation` | เปลี่ยนข้อมูล | สั่ง `.mutate()` เท่านั้น |

### จุดสำคัญที่สุด

`onSuccess` ของ mutation เอา session ที่เซิร์ฟเวอร์ตอบกลับมาใส่แคชทันที หน้าจอจึงเปลี่ยนเป็นขั้นถัดไปโดยไม่ต้องยิงไปขอซ้ำ

ถ้าเซิร์ฟเวอร์ปฏิเสธ `onSuccess` จะไม่ทำงาน แคชจึงยังเป็นโหนดเดิม หน้าจอไม่ขยับ ตรงกับสถานะจริงบนเซิร์ฟเวอร์

### ทำไมรวม query key ไว้ที่เดียว

key ต้องตรงกันทุกตัวอักษรทั้งตอนอ่านและตอนเขียนแคช ถ้าที่หนึ่งเขียน `['session', id]` อีกที่เขียน `['sessions', id]` แคชจะไม่เชื่อมกัน แล้วหน้าจอจะไม่อัปเดตโดยไม่มี error เตือน

### ทำไมไม่มีเทส

ไฟล์นี้แทบไม่มีตรรกะของเราเอง เป็นการต่อสายระหว่าง React Query กับ `traversal.ts` ซึ่งเทสแยกไปแล้ว การเทส hook ต้องติดตั้ง Testing Library เพิ่ม เก็บไว้ในงานเสริมขั้น 11.3

## 11. คำถามที่กรรมการอาจถาม

**"ทำไมไม่เขียน mock ให้ตอบค่าตายตัวไปเลย จะง่ายกว่า"**

> ถ้าตอบค่าตายตัว หน้าจอจะเดินได้แค่เส้นทางที่เขียนไว้ครับ และที่สำคัญกว่าคือจะมีตรรกะสองชุด ถ้าวันหนึ่งเพี้ยนจากกัน หน้าจอจะแสดงว่าด่านความปลอดภัยทำงานทั้งที่ engine จริงไม่ได้ทำ ผมจึงให้ mock ใช้ engine ตัวเดียวกับเซิร์ฟเวอร์ สิ่งที่จำลองมีแค่ชั้น HTTP

**"แน่ใจได้ยังไงว่า mock ไม่หลุดเข้าเว็บจริง"**

> build จริงไม่มีไฟล์ mock เลยครับ เพราะ Vite แทนค่าเงื่อนไขเป็นข้อความตายตัวตอน build แล้วตัดโค้ดที่ไม่มีทางทำงานทิ้ง ตรวจได้จากโฟลเดอร์ `dist` ที่มีไฟล์ JS ไฟล์เดียว และไม่มีข้อความจากกราฟอยู่ในนั้น

**"เทส 15 ข้อนี้ ทดสอบอะไรที่เทส 82 ข้อของ engine ยังไม่ได้ทดสอบ"**

> เทสของ engine ตรวจตรรกะการเดินกราฟครับ ส่วน 15 ข้อนี้ตรวจชั้นที่ห่อ engine คือการแปลง error เป็นรหัส HTTP ให้ถูก การรับมือเมื่อเซิร์ฟเวอร์ตอบผิดรูปแบบ และการที่ engine ยังทำงานถูกเมื่อย้ายมารันในเบราว์เซอร์
