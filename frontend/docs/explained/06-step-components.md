
**ทำไมดู flag ก่อน `type`:** `isTerminal` และ `requiresSafetyConfirmation` เป็นค่าที่เซิร์ฟเวอร์คำนวณมาให้แล้ว ถือเป็นคำตอบสุดท้าย หน้าจอไม่ต้องคิดซ้ำจาก `type`

ถ้าสลับไปดู `type` ก่อน สถานะ `instruction` ที่ต้องยืนยันคำเตือนจะหลุดไปเป็นกล่อง "ถัดไป" ธรรมดา ความปลอดภัยไม่ได้หายไป เพราะเซิร์ฟเวอร์ยังปฏิเสธ `continue` อยู่ แต่ผู้ใช้จะติดอยู่ที่สถานะนั้นโดยไม่รู้ว่าทำไม

## 4. ช่องติ๊กคำเตือน กับตัวบังคับความปลอดภัยจริง

> **ช่องติ๊กในหน้าจอไม่ใช่ตัวบังคับความปลอดภัย**
> ตัวบังคับจริงคือ `resolveNextNode` ฝั่งเซิร์ฟเวอร์ ซึ่งรับเฉพาะ `{ type: 'confirm_safety' }` ที่สถานะแบบนี้
> ถ้ามีคนแก้โค้ดหน้าจอให้ส่ง `{ type: 'continue' }` แทน เซิร์ฟเวอร์จะปฏิเสธ และสถานะไม่ขยับ

ช่องติ๊กมีไว้เพื่อประสบการณ์ใช้งาน หลังกด "ถัดไป" ติดกันหลายครั้ง นิ้วจะกดที่ตำแหน่งเดิมโดยไม่อ่าน ช่องติ๊กบังคับให้เปลี่ยนท่าทาง (ต้องแตะอีกจุดหนึ่งก่อน) ผู้ใช้จึงต้องหยุด

ลำดับในกล่อง: ขอบแดง → ป้าย → **กล่องคำเตือน** → ข้อความขั้นตอน → ช่องติ๊ก → ปุ่มยืนยัน คำเตือนมาก่อนข้อความ เพราะผู้ใช้ต้องเห็นอันตรายก่อนรู้ว่าจะให้ทำอะไร `StepCard` จึงมีช่อง `notice` แยกไว้ก่อนหัวข้อ

ใช้ `<input type="checkbox">` จริง ไม่สร้างช่องติ๊กปลอมจาก `div` เพราะได้การกด Space การรองรับโปรแกรมอ่านหน้าจอ และการแตะที่ข้อความเพื่อติ๊ก มาโดยไม่ต้องเขียนเอง

**คำเตือนทั้ง 3 ข้อในข้อมูลผู้พัฒนาเขียนเอง** (มี `author_note` กำกับ) ไม่ได้มาจากคู่มือ บรรทัดที่มาจึงใช้คำว่า "ที่มาของขั้นตอนนี้" แทน "อ้างอิง" เพื่อผูกที่มากับตัวขั้นตอน ไม่ให้เข้าใจว่าคำเตือนมาจากคู่มือด้วย แต่ `RenderedNode` ยังไม่มีข้อมูลบอกว่าคำเตือนไหนผู้พัฒนาเขียน หน้าจอจึงแสดงความต่างนี้ไม่ได้ (งานค้าง B3)

## 5. `key={node.nodeId}` กับสองสถานะที่ต้องยืนยันติดกัน

สถานะของช่องติ๊ก (`acknowledged`) และค่าที่พิมพ์ในช่องกรอก เก็บเป็น `useState` ในกล่อง ต้องเริ่มจากว่างทุกครั้งที่เปลี่ยนสถานะ

กล่อง**ไม่ได้ล้างค่าเอง** ตัวที่ทำให้ล้างคือ `key={node.nodeId}` ที่ผู้เรียกใส่ให้ เมื่อ key เปลี่ยน React จะทิ้งกล่องเดิมทั้งกล่องแล้วสร้างใหม่ state ทุกตัวจึงกลับเป็นค่าเริ่มต้น

ทำไมเรื่องนี้สำคัญ: ผังขั้นตอน `samsung_ac_ar70h_indicator_blinking` มีสถานะที่ต้องยืนยันคำเตือน**สองสถานะติดกัน** (`n_power_off` แล้ว `n_power_back_on`) ทั้งสองเป็นกล่องแบบเดียวกัน ถ้าไม่มี key React จะใช้กล่องเดิมซ้ำ ช่องติ๊กจะค้างเป็นติ๊กมาจากสถานะแรก ผู้ใช้จะกดยืนยันสถานะที่สองได้ทันทีโดยไม่ได้อ่านคำเตือนใหม่

เลือกใช้ key แทนการเขียน `useEffect` ล้างค่าเมื่อ `nodeId` เปลี่ยน เพราะ key เป็นกลไกที่ React ออกแบบมาเพื่อเรื่องนี้ ไม่ต้องจำว่า state ตัวไหนต้องล้างบ้าง และไม่มีจังหวะที่หน้าจอแสดงค่าเก่าก่อนล้างทัน

หน้า gallery ใส่ key แบบเดียวกันแล้ว หน้าตรวจอาการในขั้น 7 ต้องใส่ด้วย (มีคอมเมนต์เตือนไว้ใน `StepView.tsx` และ `SafetyGateStep.tsx`)

## 6. ทำไมไม่ตรวจรูปแบบรหัสในหน้าจอ

`InputStep` ทำแค่ตัดช่องว่างหัวท้าย และไม่ให้ส่งค่าว่าง ไม่ตรวจว่ารหัสถูกรูปแบบหรือไม่

1. **เซิร์ฟเวอร์ไม่ได้ส่งรูปแบบที่ถูกต้องมาให้** ถ้าหน้าจอเขียนกฎเอง จะกลายเป็นกฎชุดที่สองซึ่งอาจไม่ตรงกับข้อมูล
2. **การกรอกผิดไม่ใช่ข้อผิดพลาด แต่เป็นการเปลี่ยนสถานะ** ในผังขั้นตอน `samsung_ac_ar70h_error_message` ถ้ากรอกรหัสผิดรูปแบบ เครื่องสถานะจะพาไปสถานะ `n_invalid_code` ที่อธิบายว่ารหัสหน้าตาเป็นอย่างไร ถ้าหน้าจอกันไว้ ผู้ใช้จะไม่มีทางไปถึงสถานะนั้นเลย

ไม่แปลงเป็นตัวพิมพ์ใหญ่ให้ เพราะค่าที่ส่งต้องตรงกับที่ผู้ใช้เห็น และปิดการเดาคำ แก้คำ ขึ้นตัวพิมพ์ใหญ่อัตโนมัติ เพราะรหัสไม่ใช่คำในพจนานุกรม

ใช้ `<form onSubmit>` เพื่อให้กด Enter แล้วส่งได้ แทนการดักปุ่มคีย์บอร์ดเอง มือถือจะแสดงปุ่ม "ไป/ส่ง" บนแป้นให้ด้วย ต้องเรียก `preventDefault` กันเบราว์เซอร์โหลดหน้าใหม่ และเช็คซ้ำในฟังก์ชัน เพราะกด Enter ได้แม้ปุ่มถูกปิดอยู่

## 7. ทำไมปุ่มใช่และไม่ใช่มีน้ำหนักเท่ากัน

ทั้งสองปุ่มใช้ `variant="answer"` เหมือนกันทุกอย่าง ไม่ใช้เขียวกับแดง

สีจะชี้นำคำตอบ ผู้ใช้อาจกดสีเขียวเพราะรู้สึกว่าเป็นคำตอบที่ "ดี" ทั้งที่ควรตอบตามสิ่งที่เห็นที่เครื่องจริง ถ้าตอบผิด เครื่องสถานะจะพาไปผิดทาง แม้ทุกขั้นจะถูกต้องตามคู่มือ

คำบนปุ่มต้องเป็น "ใช่" และ "ไม่ใช่" ตรงตัว ห้ามเปลี่ยนเป็น "มี/ไม่มี" เพราะคำถามในข้อมูลอ้างถึงคำนี้โดยตรง เช่น "หากไม่ทราบ ให้ตอบไม่ใช่"

ดีไซน์ต้นฉบับวางสองปุ่มข้างกัน สูง 56px ตัวอักษร 18px แต่ `Button` ที่มีอยู่ใช้ `text-sm` และปุ่ม `answer` เต็มแถว ขั้นนี้ใช้ของที่มีไปก่อน แล้วทบทวนตอนตรวจบนมือถือในขั้น 9.1

## 8. บรรทัดที่มา

ทุกกล่องมีบรรทัดที่มาแน่นอน เพราะ `StepCard` เป็นคนใส่ `ReferenceLine` ให้ ไม่ต้องพึ่งให้กล่องแต่ละแบบจำเอง

| ส่วน | แสดงอะไร |
|---|---|
| บรรทัดหลัก | `ที่มาของขั้นตอนนี้: คู่มือ Samsung AR70H**D1*** หน้า 43` |
| กดปุ่ม "ดูรหัสเอกสาร" | `RAC255-00_IB_26Y_AR80H_WindFree_GEO_CB_EN-WEB_251229-D04` (ตัวอักษรกว้างเท่ากัน) |

รหัสเอกสารยาวและผู้ใช้ทั่วไปอ่านไม่รู้เรื่อง จึงซ่อนไว้ แต่ต้องเข้าถึงได้ เพราะเป็นสิ่งที่ใช้ตรวจย้อนกับไฟล์คู่มือจริง

ช่วงหน้าใช้ขีดยาว en dash (`หน้า 43–44`) ไม่ใช่ hyphen อักขระสองตัวนี้หน้าตาคล้ายกันมาก จึงแยกเป็นค่าคงที่ `EN_DASH` และมีเทสจับไว้

ถ้าไม่มีชื่อคู่มือส่งมา บรรทัดหลักจะใช้รหัสเอกสารแทน บรรทัดนี้จึงไม่มีทางว่าง

## 9. การตัดสินใจระหว่างทำที่ไม่ได้อยู่ในแผน

| เรื่อง | ที่ทำ | เหตุผล |
|---|---|---|

| กรอบโฟกัสของช่องติ๊ก | เพิ่มคลาสชุดเดียวกับ `Button` | ตรวจจริงแล้วเจอว่าช่องติ๊กใช้กรอบของเบราว์เซอร์ ไม่ใช่สีส้ม |
| `nodeId` เหนือกล่องในหน้า gallery | แสดงตัวเล็ก | ตอนถ่ายภาพลงรายงานจะรู้ว่ากล่องไหนคือสถานะไหน |
| `safetyWarning` ว่าง | แสดงแค่หัวข้อคำเตือน ไม่มีข้อความสำรอง | ข้อความสำรองจะเป็นคำเตือนที่แต่งขึ้นเอง |

## 10. ข้อจำกัดที่รู้ตัว

- **ยังไม่มีเทสอัตโนมัติของกล่อง** ตรวจด้วยเบราว์เซอร์ผ่านหน้า gallery เท่านั้น เหมือนขั้น 4 และ 5
- **หน้า gallery ไม่ได้พิสูจน์ด่านความปลอดภัย** แสดงแค่ว่าหน้าจอส่ง `confirm_safety` ถูก ส่วนการที่เซิร์ฟเวอร์ปฏิเสธ `continue` พิสูจน์ได้จากเทสของกลไกควบคุมเครื่องสถานะ และจะสาธิตกับเซิร์ฟเวอร์จริงเมื่อ REST API เสร็จ
- **ปุ่มยังต่างจากดีไซน์** ดูข้อ 7
- **หน้าจอบอกไม่ได้ว่าคำเตือนไหนผู้พัฒนาเขียนเอง** ดูข้อ 4 และงานค้าง B3
