# ช่องกรอกผลลัพธ์ที่หน้าสถานะสิ้นสุด — ส่วนหน้าจอ (ขั้น 3)

อาจารย์ที่ปรึกษาขอให้หน้าสุดท้ายของการตรวจมีช่องให้ผู้ใช้กรอกว่าผลเป็นอย่างไร เอกสารนี้อธิบายฝั่งหน้าจอ ส่วนฝั่ง backend และฐานข้อมูลอยู่ใน `backend/docs/explained/13-session-outcome.md`

## 1. ชิ้นส่วนต่อกันอย่างไร

```
OutcomeForm ── onSubmit(text ที่ตัดช่องว่างแล้ว) ──▶ SessionPage.handleOutcome
                                                         │ (ref กันกดเบิ้ล)
                                                         ▼
                                  useSubmitOutcome ──▶ POST /traversal/sessions/:id/outcome   body { "text": … }
                                                         │
                          ◀──── SessionResponse (มี outcome) ◀──────┘
                                  │ setQueryData(session)
                                  ▼
          session.data.outcome เป็น string ──▶ OutcomeForm แสดงข้อความอ่านอย่างเดียว

เส้นทางของฟอร์มเข้าหน้า:  SessionPage ─ outcomeForm ▶ StepView ─ form ▶ OutcomeStep (เฉพาะ node.isTerminal)
```

กฎเดิมของโครงงานยังใช้: component ชั้นล่างรับค่าทาง props แล้วแจ้งเหตุการณ์ออก **ไม่เรียก API เอง** หน้า `SessionPage` เป็นเจ้าของ mutation เหมือนที่เป็นเจ้าของ `useSubmitAction`

## 2. สองสถานะของฟอร์ม ตัดสินจากเซิร์ฟเวอร์อย่างเดียว

| `session.outcome` | ที่หน้าจอ |
|---|---|
| `null` หรือไม่มี | ฟอร์ม (ช่องพิมพ์ + ปุ่ม "บันทึกผล") |
| ข้อความ | "บันทึกผลแล้ว" + ข้อความอ่านอย่างเดียว ไม่มีช่องพิมพ์ ไม่มีปุ่มบันทึก |

หน้าจอ **ไม่มีตัวแปร "บันทึกแล้ว" ของตัวเอง** `useSubmitOutcome` เอาผลตอบกลับของเซิร์ฟเวอร์ใส่แคชของ session (`setQueryData`) เหมือน `useSubmitAction` ฟอร์มจึงเปลี่ยนเป็นข้อความอ่านอย่างเดียวทันที และตอนกด F5 หน้าเรียก `GET /traversal/sessions/:id` ซึ่งส่ง `outcome` กลับมาด้วย หน้าจอจึงเห็นเหมือนเดิมโดยไม่ต้องมีโค้ดแยกสำหรับ "เปิดหน้าที่เคยบันทึกแล้ว"

ถ้าเซิร์ฟเวอร์ปฏิเสธ `onSuccess` ไม่ทำงาน แคชไม่เปลี่ยน ฟอร์มอยู่ที่เดิมพร้อมข้อความที่พิมพ์ไว้

## 3. ฟอร์มขึ้นเฉพาะสถานะสิ้นสุด

`StepView` ส่ง `outcomeForm` ให้ `OutcomeStep` เท่านั้น (แขนง `node.isTerminal`) แขนงอื่นของ `StepView` (ด่านความปลอดภัย, checkpoint, input, instruction) **ไม่รับ prop นี้เลย** ฟอร์มจึงไม่มีทางโผล่กลางการตรวจ แม้ผู้เรียกจะส่งมาผิดที่ ชั้นที่สองคือเซิร์ฟเวอร์: ถ้า session ยังเดินอยู่ จะตอบ 409 `SESSION_NOT_COMPLETED` (หัวข้อ 7)

หน้า `NodeGalleryPage` (หน้าดูกล่องทุกชนิดตอนพัฒนา) เรียก `StepView` โดยไม่ส่ง `outcomeForm` จึงไม่มีฟอร์มที่นั่น

## 4. ไม่บังคับ และปุ่มเดิมไม่ขึ้นกับฟอร์ม

- ปุ่ม "บันทึกผล" กดได้เมื่อมีข้อความจริงเท่านั้น (ไม่ใช่ว่าง ไม่ใช่ช่องว่างล้วน) ผู้ใช้ไม่กรอกอะไรเลยก็จบการตรวจได้
- "ตรวจอาการอื่น" และ "เริ่มอาการนี้ใหม่" อยู่ใน `actions` ของ `OutcomeStep` **นอก `<form>`** ไม่ผูกกับค่าในช่อง และไม่ถูกปิดระหว่างกำลังบันทึก (ตรวจด้วย Chrome แล้ว: กดจริงตอนช่องว่างและพาไปหน้าที่ถูกต้อง ส่วนตอนกำลังส่งและตอนส่งไม่สำเร็จตรวจว่าปุ่มไม่ถูกปิด ไม่ได้กดจริง)
- ปุ่ม "บันทึกผล" เป็นแบบ `secondary` ปุ่มหลักสีส้มของหน้ายังเป็น "ตรวจอาการอื่น" การบันทึกผลเป็นของเสริม ไม่แย่งความสำคัญ

ข้อที่ต้องรู้: ถ้าผู้ใช้พิมพ์ค้างไว้แล้วกด "ตรวจอาการอื่น" **ข้อความที่ยังไม่บันทึกหายโดยไม่ถาม** (ตั้งใจ ตามข้อกำหนดว่าปุ่มต้องไม่ผูกกับฟอร์ม) ร่างข้อความไม่ถูกเก็บลง `localStorage`/`sessionStorage` เพราะอาจมีข้อมูลส่วนตัว มีแค่ใน state ของ component

สามชั้น แต่ละชั้นกันคนละอย่าง

หลังบันทึกสำเร็จ ฟอร์มหายไป ไม่มีทางส่งซ้ำจากหน้าจอ

## 7. ข้อผิดพลาด

`describeError()` เลือกข้อความจาก `code` ไม่ใช้ `message` ของเซิร์ฟเวอร์ ตามกติกาเดิม (ตรวจแล้วว่าข้อความภายในของเซิร์ฟเวอร์ไม่ขึ้นหน้าจอ) ข้อผิดพลาดของการบันทึกแสดง **ในฟอร์มเอง** ใต้ช่องพิมพ์ ไม่ปนกับกล่องข้อผิดพลาดด้านบนของหน้า (ซึ่งเป็นของการตอบคำถามและการเริ่มใหม่)

| รหัส | เกิดเมื่อ | หัวข้อที่ผู้ใช้เห็น | ปุ่มในฟอร์ม | ตรวจ Chrome |
|---|---|---|---|---|
| `INVALID_OUTCOME` 400 | ว่าง / ไม่ใช่ข้อความ / ยาวเกิน 1000 (ช่องกันไว้แล้ว จึงเกิดยาก) | ข้อความผลลัพธ์บันทึกไม่ได้ (บอกเพดาน) | ไม่มี แก้ข้อความแล้วกดบันทึกใหม่ | ✅ |
| `SESSION_NOT_COMPLETED` 409 | session ยังเดินอยู่ (หน้าจอเก่ากว่าเซิร์ฟเวอร์) | การตรวจนี้ยังไม่จบ | ดึงข้อมูลล่าสุด | ✅ |
| `OUTCOME_ALREADY_SUBMITTED` 409 | เคยบันทึกไปแล้ว เช่น กดจากอีกแท็บ | การตรวจนี้บันทึกผลไปแล้ว | ดึงข้อมูลล่าสุด → เห็นข้อความที่บันทึกไว้ของครั้งแรกแบบอ่านอย่างเดียว | ✅ |
| `NETWORK_ERROR` | ต่อเซิร์ฟเวอร์ไม่ได้ | เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ | ไม่มี ลองใหม่ด้วยปุ่ม "บันทึกผล" เดิม (ข้อความที่พิมพ์ยังอยู่) | ✅ |
| `SESSION_NOT_FOUND` 404 | session หมดอายุ/ถูกลบ | ไม่พบการตรวจนี้ | ไม่มี ใช้ "ตรวจอาการอื่น" ที่อยู่ใต้ฟอร์ม | ❌ ไม่ได้ตรวจในฟอร์ม (มีเทสของข้อความใน `errors.test.ts` แล้ว) |

เฉพาะ `recovery = reload-session` ที่มีปุ่มในฟอร์ม ปุ่ม "ดึงข้อมูลล่าสุด" เรียก `handleRefresh` เดิมของหน้า (ล้างข้อผิดพลาด แล้วถามเซิร์ฟเวอร์ใหม่) ส่วน `retry` ไม่ใช้ปุ่ม "ลองอีกครั้ง" ของกล่องหน้า เพราะปุ่มนั้นดึง session ใหม่ ไม่ได้ส่งซ้ำ จะหลอกว่าส่งซ้ำแล้ว

ระหว่างบันทึก ถ้ารอเกิน 4 วินาทีหน้าขึ้นกล่อง "เซิร์ฟเวอร์กำลังเริ่มทำงาน" (รวม `saveOutcome.isPending` ใน `isWaiting` แล้ว เหตุผลเดียวกับ Render ตอนตื่นช้า) ข้อนี้ **มาจากการอ่านโค้ด ไม่ได้ตรวจด้วย Chrome** (เซิร์ฟเวอร์ปลอมหน่วงแค่ 0.5 วินาที)

## 8. ข้อความของผู้ใช้: แสดงเป็นตัวอักษร ไม่กรองเนื้อหา

- แสดงด้วย text ของ React (`{savedText}`) ไม่ใช้ `dangerouslySetInnerHTML` ข้อความ `<img onerror=…>` กับ `<script>` ไม่ทำงาน และไม่มี element จริงโผล่ในหน้า (ตรวจ Chrome ✅)
- `whitespace-pre-wrap` คงการขึ้นบรรทัดใหม่ที่ผู้ใช้พิมพ์ · `break-words` กันข้อความยาวไม่เว้นวรรคดันหน้าจอให้ล้น (ตรวจ 1,000 ตัวอักษรติดกัน ที่จอ 375px ✅)
- **ไม่กรองเนื้อหา** ไม่ตรวจข้อมูลส่วนตัว ไม่กรองคำ คำเตือน "ไม่ต้องใส่ข้อมูลส่วนตัว" เป็นแค่การขอ **ไม่ใช่การป้องกัน** ห้ามเขียนในรายงานว่าระบบ "ปกป้องข้อมูลส่วนตัว"
- ข้อความอยู่ในฐานข้อมูลต่อไปแม้ session หมดอายุ (ยังไม่มีตัวกวาด session หมดอายุ) ดู doc 13 หัวข้อ 3 "ข้อควรรู้ด้านข้อมูล"
- ข้อความเป็นข้อมูลบันทึกอย่างเดียว ไม่ผ่านเครื่องสถานะ ไม่ใช้ตัดสินขั้นตอน ไม่ใช้ในระบบค้นหา และ **ห้ามอ้างว่าระบบเรียนรู้จากข้อความนี้**

## 9. ความยาว

`lib/outcome.ts` ลอก `MAX_OUTCOME_LENGTH = 1000` จาก `backend/src/traversal/traversal.dto.ts` (อยู่สองที่ เหมือน `MAX_QUERY_LENGTH` ของการค้นหา)

- ช่องพิมพ์ใช้ `maxLength={1000}` ผู้ใช้จึงพิมพ์เกินไม่ได้ (วาง 1,001 ตัวอักษร ช่องรับ 1,000 ✅)
- ตัวนับนับตามที่พิมพ์จริง รวมช่องว่าง เพื่อเทียบกับ `maxLength` ของช่อง ส่วนเซิร์ฟเวอร์นับ **หลัง** ตัดช่องว่าง ผลคือหน้าจอไม่มีทางส่งข้อความที่เซิร์ฟเวอร์ปฏิเสธเพราะยาวเกิน
- นับเป็นหน่วย JavaScript (`.length`) เหมือนเซิร์ฟเวอร์ อีโมจินับเป็น 2
- เทส `เพดานเท่ากับของ backend (1000)` เช็กแค่ว่าค่าฝั่งนี้เป็น 1000 **ไม่ได้เทียบกับ backend อัตโนมัติ** ถ้า backend เปลี่ยนค่า ไม่มีอะไรเตือน ต้องจำไว้เอง
- ❌ ยังไม่ได้ตรวจว่าเบราว์เซอร์นับการขึ้นบรรทัดใหม่ที่ขอบ 1,000 ตรงกับเซิร์ฟเวอร์หรือไม่ (ถ้าไม่ตรง ผลคือขึ้น `INVALID_OUTCOME` ไม่ใช่ข้อมูลเสีย)

## 10. โหมดจำลอง (mock)

`mockServer.submitOutcome` ตอบรหัสและลำดับการตรวจ **ตรงกับ backend** ถ้าเรียงต่างกัน หน้าจอที่ลองกับตัวจำลองจะเจอข้อความคนละอย่างกับของจริง

| ลำดับ | ตรวจ | ผล |
|:---:|---|---|
| 1 | รูปแบบข้อความ (ว่าง, ช่องว่างล้วน, เกิน 1000) | 400 `INVALID_OUTCOME` |
| 2 | ไม่พบ session | 404 `SESSION_NOT_FOUND` |
| 3 | session ยังเดินอยู่ | 409 `SESSION_NOT_COMPLETED` |
| 4 | เคยบันทึกแล้ว | 409 `OUTCOME_ALREADY_SUBMITTED` |
| — | ผ่านหมด | เก็บข้อความ ตอบ session เดิมพร้อม `outcome` |

ที่ต้องรู้

- ลำดับ **รูปแบบก่อน session** มาจากการอ่าน controller จริง (`parseOutcomeBody` ถูกเรียกก่อนเข้า service) ไม่ใช่ที่คิดไว้ตอนแรก
- ตัวตรวจรูปแบบเป็น `parseOutcomeBody` ตัวเดียวกับ backend (import ตรงจาก `backend/src/traversal/traversal.dto.ts`) ไม่เขียนกฎซ้ำเป็นชุดที่สอง ด้วยเหตุผลเดียวกับที่ mock ใช้ engine ตัวเดียวกับเซิร์ฟเวอร์ (ถ้ามีกฎสองชุดแล้วเพี้ยนจากกัน หน้าจอจะบอกข้อมูลผิด) นี่เป็นครั้งแรกที่ `mockServer.ts` import ของ backend นอกโฟลเดอร์ `traversal-engine/`
- ผลลัพธ์เก็บใน `Map` แยกจาก `sessions` เหมือน backend เก็บแยกจาก `SessionState` ของ engine engine จึงไม่เคยเห็นผลลัพธ์
- ทุก response ของ mock มี `outcome` (`null` จนกว่าจะบันทึก) `abandonSession` ลบผลลัพธ์ไปด้วย (เซิร์ฟเวอร์จริง `DELETE FROM sessions` ลบทั้งแถว)
- ไม่หลุดเข้า build จริง: build จริง (ไม่ตั้ง `VITE_USE_MOCK`) ได้ไฟล์ JS ไฟล์เดียว ค้น `samsung_ac_ar70h_stops_working` (ข้อมูลผัง), `text ต้องไม่ว่าง` (ข้อความของ `parseOutcomeBody`) และ `parseOutcomeBody` ไม่พบเลย ส่วนข้อความไทยของฟอร์มและรหัส error ใหม่ (ซึ่งต้องอยู่ใน bundle) พบอย่างละ 1 ครั้ง ใช้ยืนยันว่าวิธีค้นอ่านภาษาไทยได้จริง ผล 0 ข้างบนจึงเชื่อถือได้
