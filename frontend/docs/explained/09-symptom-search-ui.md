## 1. ชิ้นส่วนต่อกันอย่างไร

```
SymptomSearchForm ── onSubmit ──▶ SymptomsPage ── useSymptomSearch ──▶ POST /symptom-search
                                      │                                      │
                                      │◀──────── SymptomSearchResponse ◀─────┘
                                      ▼
                          SymptomSearchResults ─▶ SymptomRow (แสดงคะแนน)
                                      │ onSelect(graphId)
                                      ▼
   useStartSession({ graphId, query: search.data.query }) ──▶ POST /traversal/sessions
                                      │
                                      ▼
                    หน้าตรวจอาการ: แสดง "คะแนนความคล้าย" จาก session.confidence
```

กฎเดิมของโครงงานยังใช้: component ชั้นล่างรับค่าทาง props แล้วแจ้งเหตุการณ์ออก ไม่เรียก API เอง หน้า `SymptomsPage` เป็นคนตัดสินใจว่าจะค้นหาหรือเริ่ม session เมื่อไร

## 2. หน้าที่ของการค้นหา: เสนอ ไม่ตัดสิน

หลักการของโครงงาน: เครื่องสถานะเป็นผู้ตัดสินขั้นถัดไป การค้นหาตอบได้แค่ "น่าจะเริ่มผังไหน" และ **ผู้ใช้ต้องเลือกเองเสมอ** หน้าจอจึง

- ใช้คำว่า "อาการที่ใกล้เคียงกับที่พิมพ์" ไม่ใช้ "ตรงกับ" หรือ "พบอาการของคุณคือ"
- แสดงเป็น **"คะแนนความคล้าย 0.984"** (ทศนิยม 3 ตำแหน่ง) ไม่แปลงเป็นเปอร์เซ็นต์ เพราะ cosine ไม่ใช่ความน่าจะเป็น "0.984" ไม่ได้แปลว่าถูก 98.4% และห้ามเขียน "มั่นใจ x%" (มีเทสบนหน้าจอจริงตรวจว่าไม่มีคำว่า "มั่นใจ" และไม่มี %)
- มีข้อความอธิบายใต้หัวข้อผลค้นหา: คะแนนบอกแค่ว่าข้อความใกล้กันแค่ไหน ไม่ใช่โอกาสที่จะถูกต้อง
- แสดง "ใกล้กับ “ข้อความอาการในข้อมูล”" ให้ผู้ใช้เห็นว่าทำไมจึงถูกเสนอ (มาจาก `matchedText`)
- หน้าตรวจอาการแสดงคะแนนพร้อมคำว่า "แสดงเป็นข้อมูลประกอบเท่านั้น ขั้นตอนถัดไปตัดสินตามคู่มือ" เพราะ `confidence` ฝั่งเซิร์ฟเวอร์เก็บเพื่อแสดงอย่างเดียว ไม่ได้ใช้ตัดสินอะไร (มีเทสฝั่ง backend พิสูจน์ว่าคะแนน 1 ก็ข้ามด่านความปลอดภัยไม่ได้)

## 3. ไม่มีผังผ่านเกณฑ์ → ไม่เดา

เมื่อ `matches` ว่าง (เช่น "วันนี้ฝนจะตกไหม" ได้คะแนนสูงสุด 0.414 ต่ำกว่าเกณฑ์ 0.55) หน้าจอแสดงกล่อง "ไม่พบอาการที่ใกล้เคียงกับที่พิมพ์" บอกว่าระบบไม่เดาให้ ชี้ไปรายการอาการด้านล่าง และแนะนำให้ติดต่อศูนย์บริการ Samsung ไม่ใส่เบอร์โทรเพราะข้อมูลของโครงงานไม่มีเบอร์ที่ตรวจสอบแล้ว และห้ามแต่ง

## 4. การส่ง `query` ตอนเริ่ม session

| เริ่มจาก | ส่ง `query` | `confidence` ที่ได้ | หน้าตรวจอาการ |
|---|:---:|---|---|
| แถวในผลค้นหา | ใช่ | ตัวเลข (เซิร์ฟเวอร์คำนวณเอง) | แสดงบรรทัดคะแนน |
| แถวในรายการอาการ | ไม่ | `null` | ไม่แสดงอะไร (ไม่แต่งตัวเลข) |
| ปุ่ม "เริ่มอาการนี้ใหม่" | ไม่ | `null` | ไม่แสดง (เริ่มซ้ำไม่ใช่การค้นหาใหม่) |

รายละเอียดที่ต้องรู้

- **ส่ง `search.data.query` ไม่ใช่ข้อความในช่องพิมพ์** เพราะผู้ใช้อาจแก้ช่องพิมพ์หลังค้นหาแล้ว ถ้าส่งข้อความใหม่ คะแนนจะไม่ตรงกับผลที่เห็นอยู่ข้างบน และ `search.data.query` เป็นข้อความที่เซิร์ฟเวอร์ตัดช่องว่างแล้ว
- **หน้าจอไม่ส่งคะแนนไปเอง** เซิร์ฟเวอร์คำนวณจาก `query` ผู้ใช้จึงแต่งคะแนนผ่านหน้าจอไม่ได้ (ตรวจในเทสบนหน้าจอจริงว่า body ไม่มีฟิลด์ `confidence`) ⚠️ แต่คะแนนยังไม่ใช่เขตความปลอดภัย เพราะ `query` ยังมาจากผู้ใช้ ห้ามนำไปตัดสินสิทธิ์ใดๆ
- `useStartSession` เปลี่ยนจากรับ `graphId` เป็นรับ `{ graphId, query? }` จึงต้องแก้ผู้เรียกทั้งสองที่ (`SymptomsPage`, `SessionPage`)

## 5. แถวที่กดอยู่: เก็บ "ส่วนของหน้า" ด้วย

ผังเดียวกันอยู่ได้ทั้งผลค้นหาและรายการอาการ ถ้าเก็บแค่ `graphId` ตัวหมุน "กำลังเริ่ม" จะขึ้นสองแถวพร้อมกัน หน้าจึงเก็บ `{ area: 'search' | 'list', graphId }` แล้วให้ฟังก์ชัน `rowState` คิดสภาพของแต่ละแถว (กำลังเริ่มเอง / ถูกปิดเพราะแถวอื่นกำลังเริ่ม) ช่องพิมพ์ถูกปิดระหว่างเริ่ม session ด้วย กันค้นหาซ้อน

`SymptomRow` ใช้ซ้ำทั้งสองที่ แทนการสร้างแถวใหม่ที่ต้องเขียนสถานะ "กำลังเริ่ม/กดไม่ได้" ซ้ำ โดยรับ `summary` แค่ `graphId` + ชื่อ (`Pick<GraphSummary, …>`) และรับ `score`/`matchedText` เพิ่มแบบไม่บังคับ

## 6. ข้อผิดพลาดของการค้นหา

ตัดสินจาก `code` ไม่ใช้ `message` ของเซิร์ฟเวอร์ (เขียนไว้ให้นักพัฒนา) ตามกติกาเดิมของ `describeError`

| รหัส | เกิดเมื่อ | ข้อความที่ผู้ใช้เห็น | สีกล่อง |
|---|---|---|---|
| `INVALID_QUERY` 400 | คำค้นว่าง/ไม่ใช่ข้อความ/ยาวเกิน 200 | ข้อความที่พิมพ์ใช้ค้นหาไม่ได้ | ฟ้า |
| `SEARCH_NOT_READY` 503 | กำลังโหลดโมเดล (เซิร์ฟเวอร์เพิ่งตื่น) | ระบบค้นหากำลังเริ่มทำงาน รอสักครู่แล้วลองใหม่ | ฟ้า |
| `SEARCH_UNAVAILABLE` 503 | ปิดสวิตช์อยู่ หรือโหลดไม่สำเร็จ | ระบบค้นหาไม่พร้อมใช้งาน เลือกจากรายการด้านล่างแทน | ฟ้า |
| 400 ไม่มี `code` | JSON ผิดไวยากรณ์ Express ตอบเองก่อนถึงตัวแปลง error | เซิร์ฟเวอร์อ่านคำขอไม่ได้ | แดง |
| `NETWORK_ERROR` | ต่อเซิร์ฟเวอร์ไม่ได้ | เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ | แดง |

`SEARCH_UNAVAILABLE` ไม่บอกให้ "ลองใหม่" เพราะรอแล้วไม่หาย (ปิดสวิตช์) ต่างจาก `SEARCH_NOT_READY` ที่รอได้ ส่วนกรณี 400 ที่ไม่มี `code` แยกจาก 500 ที่ไม่รู้สาเหตุด้วย status เพื่อไม่ให้ขึ้นว่า "ระบบไม่รู้จัก" ในทุกกรณีของ `UNKNOWN_ERROR`

ทุกกรณี รายการอาการเดิมยังใช้ได้ การค้นหาล้มไม่ทำให้เริ่มการตรวจไม่ได้

## 7. โหมดจำลอง (mock)

ตัวจำลองไม่มีโมเดลค้นหา และ **ไม่แต่งผลลัพธ์** (ผลปลอมจะทำให้หน้าจอดูเหมือนค้นหาได้จริง) `searchSymptoms()` ของ mock ตอบ 503 `SEARCH_UNAVAILABLE` เหมือนเซิร์ฟเวอร์จริงตอนปิดสวิตช์ ส่วน `confidence` ของ session ในโหมดจำลองเป็น `null` เสมอ ตรวจแล้วว่าข้อความของ mock ไม่หลุดเข้า build จริง (ค้นใน `dist/` ไม่พบ)

**สิ่งที่ผู้ช่วยตรวจแล้ว (ทุกข้อข้างบน 20 รายการ)** ด้วย Chrome จริงต่อ backend ในเครื่อง (โมเดลจริง ฐานข้อมูล Aiven แบบอ่านอย่างเดียว) สคริปต์ตรวจอยู่นอก repo (ไม่ commit) **ข้อที่ไม่ได้ทดสอบกับของจริง:** การกดแถวผลค้นหาแล้วเริ่ม session จริงบนฐานข้อมูล เพราะจะเขียนแถวลง DB เดียวกับที่ Render ใช้ ในการตรวจนี้ดักคำขอใน browser เพื่อตรวจ body แล้วตอบข้อมูลจำลองที่สร้างจาก engine ตัวจริง ส่วนฝั่งเซิร์ฟเวอร์ (บันทึก/อ่านคืน `confidence`) มีเทสของ backend และเคยยิงจริงบน MariaDB ในขั้น 1.8 ยังไม่เคยยืนยันบน MySQL 8.4 ผ่านหน้าจอ
