# ขั้น 5 — หน้าเลือกอาการ

ขั้นนี้เปลี่ยนหน้า `/symptoms` จากฉบับชั่วคราวให้เป็นหน้าจริง ผู้ใช้เห็นรายการอาการทั้งหมดที่ระบบรองรับ กดหนึ่งอาการแล้วเริ่มการตรวจอาการได้

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/labels.ts` | ตารางแปลงค่าจากข้อมูลเป็นข้อความไทย (ค่าคงที่ล้วน) |
| `src/lib/symptoms.test.ts` | เทสของการจัดกลุ่มและการเรียงชื่อ 5 ข้อ |
| `src/lib/symptoms.ts` | จัดกลุ่มอาการตามเครื่อง และเรียงตามลำดับภาษาไทย |
| `src/components/SymptomRow.tsx` | อาการหนึ่งแถว ไม่เรียก API เอง |
| `src/pages/SymptomsPage.tsx` | หน้าเลือกอาการ (แทนที่ฉบับชั่วคราวของขั้น 4) |

เทสรวมเป็น 20 ข้อ (เดิม 15 + ใหม่ 5)

> **ศัพท์:** เอกสารนี้ใช้คำว่า ผังขั้นตอนการวินิจฉัย / เครื่องสถานะ / สถานะ / การเปลี่ยนสถานะ ตาม `PROJECT_CONTEXT.md` ข้อ 3
> ชื่อในโค้ดยังคงเดิม — **`GraphSummary` = ข้อมูลย่อของผังขั้นตอนการวินิจฉัย 1 ชุด**, **`graphId` = รหัสของผังขั้นตอน**, **`nodeId` = รหัสของสถานะ**
> ผังขั้นตอน 1 ชุด = 1 อาการ หน้าเลือกอาการจึงคือหน้าที่ให้ผู้ใช้เลือกผังขั้นตอนที่จะเดิน

## 1. ชิ้นส่วนต่อกันอย่างไร
useGraphs() ← ดึงรายการผังขั้นตอนทั้งหมด (13 ชุดของแอร์)
↓
groupSymptoms() ← จัดกลุ่มตามเครื่อง + เรียงชื่อไทย
↓
SymptomsPage ← ตัดสินใจว่าจะเริ่ม session เมื่อไร
↓ props
SymptomRow ← แสดงผลอย่างเดียว กดแล้วแจ้งกลับด้วย onSelect
↓ onSelect
useStartSession() ← เริ่ม session แล้วไปหน้า /session/:id

กฎที่ยึดตลอดโครงงาน: component ชั้นล่างรับค่าผ่าน props แล้วแจ้งเหตุการณ์ออก ไม่เรียก API เอง เพราะถ้าแถวเรียก API เองจะทดสอบแยกไม่ได้ และหน้าจะคุมไม่ได้ว่าตอนนี้มีกี่คำขอที่ค้างอยู่

## 2. การจัดกลุ่ม

`groupSymptoms` จัดกลุ่มด้วยสามค่าพร้อมกันคือ `deviceCategory` + `brand` + `modelPattern` ไม่ใช่ประเภทเครื่องอย่างเดียว

เหตุผล: หัวกลุ่มบนหน้าจอแสดงยี่ห้อและรุ่นไว้ด้วย ตอนนี้มีแค่แอร์ AR70H รุ่นเดียวจึงไม่ต่างกัน แต่เมื่อเพิ่มคู่มือตู้เย็นสองรุ่น ถ้าจัดกลุ่มด้วยประเภทอย่างเดียว อาการจากสองคู่มือจะถูกยัดในกลุ่มเดียวกัน แล้วหัวกลุ่มจะแสดงรุ่นได้แค่รุ่นเดียว ซึ่งกลายเป็นการอ้างอิงที่ผิด — ขัดกับหลักของโครงงานที่ทุกข้อความต้องย้อนกลับไปที่คู่มือที่ถูกต้องได้

การจัดกลุ่มใช้ `Map` โดยสร้าง key จากสามค่าต่อกันด้วย `|` เพราะ `Map` ใช้ key เป็นข้อความเทียบตรงๆ และ `Map` จำลำดับที่ใส่เข้าไป ลำดับของกลุ่มจึงคงที่ ไม่สุ่มไปมา

## 3. การเรียงภาษาไทย

ภายในกลุ่มเรียงด้วย `new Intl.Collator('th').compare`

ถ้าเทียบข้อความด้วย `<` `>` ธรรมดา จะเป็นการเทียบรหัสตัวอักษร ซึ่งไม่ใช่ลำดับพจนานุกรมไทย `Intl.Collator('th')` เป็นตัวเรียงภาษาไทยที่มีอยู่ใน JavaScript อยู่แล้ว ไม่ต้องเพิ่มไลบรารี

สร้าง `Collator` ครั้งเดียวไว้นอกฟังก์ชัน เพราะการสร้างแต่ละครั้งมีต้นทุน ถ้าสร้างใหม่ทุกครั้งที่เรียงจะเสียเวลาโดยไม่จำเป็น

**ผลที่ต้องรู้:** ตัวเรียงไทยข้ามสระหน้า (แ เ โ) แล้วเรียงตามพยัญชนะตัวถัดไป ชื่ออาการที่ขึ้นต้นด้วย "แอร์..." จึงไปรวมกันอยู่ท้ายรายการ (เรียงที่ อ) ไม่ได้อยู่ต้นรายการอย่างที่หลายคนคาด พฤติกรรมนี้ถูกต้องตามหลักการเรียงไทย และมีเทสข้อหนึ่งตรึงลำดับนี้ไว้ ถ้าวันหนึ่งผลเปลี่ยน เทสจะฟ้อง

`symptomName` คืน `entrySymptomTh` ถ้ามี ไม่มีก็คืน `entrySymptom` เพราะข้อมูลบางชุดอาจยังไม่มีชื่อไทย หน้าจอต้องไม่ว่าง

## 4. ไม่แก้ข้อมูลที่รับเข้ามา

`Array.prototype.sort` แก้ array ตัวที่ถูกเรียก ไม่ได้คืน array ใหม่ ถ้าเรียง array ที่ React Query เก็บไว้ในแคชโดยตรง จะเป็นการแก้ข้อมูลในแคช ซึ่ง React Query ไม่รู้ว่าเปลี่ยน อาจทำให้หน้าจอกับข้อมูลไม่ตรงกัน

`groupSymptoms` จึงสร้าง array ใหม่ของแต่ละกลุ่มแล้วค่อย `sort` array ที่สร้างเอง มีเทสข้อหนึ่งตรวจว่าลำดับของ array ที่ส่งเข้าไปไม่ถูกแก้

## 5. การกันกดซ้อน

ถ้าผู้ใช้กดหลายแถวรัวๆ หรือกดแถวเดิมซ้ำ จะเกิด session หลายอันบนเซิร์ฟเวอร์ โดยที่ผู้ใช้ได้ใช้จริงแค่อันเดียว

หน้าจึงเก็บ `startingId` (รหัสผังขั้นตอนของแถวที่กด) ไว้เอง เพราะ `useStartSession` บอกได้แค่ว่ากำลังเริ่มอยู่หรือไม่ ไม่บอกว่าเริ่มของแถวไหน แล้วแบ่งแถวเป็น 3 สภาพ

| สภาพ | เงื่อนไข | กดได้ | หน้าตา |
|---|---|:---:|---|
| `starting` | แถวที่กด | ไม่ | ตัวหมุน + "กำลังเริ่ม" สีส้ม ไม่จาง |
| `disabled` | แถวอื่นระหว่างรอ | ไม่ | จาง 40% |
| `idle` | ไม่มีใครกำลังเริ่ม | ได้ | ปกติ |

แถวที่กำลังเริ่มก็ถูกปิดปุ่มด้วย แต่**ไม่จาง** เพื่อให้ผู้ใช้เห็นว่าระบบกำลังทำงานอยู่ที่แถวไหน (จุดนี้ต่างจากแผนเดิมที่ใช้ `disabled:opacity-40` กับทุกแถวที่กดไม่ได้)

เมื่อเริ่มไม่สำเร็จ `isPending` กลับเป็น `false` เอง แถวทุกแถวจึงกลับมากดได้อีกครั้งโดยไม่ต้องเขียนโค้ดคืนสภาพ

## 6. ทำไมเริ่ม session ใน `onClick` เท่านั้น

ห้ามย้ายไปไว้ใน `useEffect` เด็ดขาด

`StrictMode` ในโหมด dev ตั้งใจเรียก effect สองรอบเพื่อหาโค้ดที่ทำงานซ้ำแล้วพัง ถ้าเริ่ม session ใน effect จะได้ session สองอันทุกครั้งที่เข้าหน้า อันหนึ่งกลายเป็นขยะบนเซิร์ฟเวอร์

การกดปุ่มเป็นเหตุการณ์จากผู้ใช้ เกิดกี่ครั้งเท่าที่ผู้ใช้กด ไม่มีการเรียกซ้ำจากตัว React เอง

---

## 7. ทำไมหน้าตรวจอาการไม่ต้องดึง session ซ้ำ

`useStartSession` มี `onSuccess` ที่เอา session ที่เพิ่งได้ใส่ลงแคชที่ key `['session', sessionId]` ให้แล้วตั้งแต่ขั้น 3

หน้าตรวจอาการใช้ `useSession(sessionId)` ซึ่งอ่านจาก key เดียวกัน พอเปลี่ยนหน้าไปจึงเจอข้อมูลในแคชทันที ไม่ต้องยิง GET ซ้ำ ผู้ใช้ไม่ต้องเห็นตัวหมุนสองรอบติดกัน และลดจำนวนคำขอที่ส่งไปเซิร์ฟเวอร์ลงหนึ่งครั้งต่อการเริ่มหนึ่งครั้ง

---

## 8. การแจ้งข้อผิดพลาด

หน้านี้มีจุดที่ผิดพลาดได้สองจุด คือโหลดรายการอาการไม่ได้ กับเริ่ม session ไม่ได้ ทั้งสองจุดใช้กล่องเดียวกัน (`ErrorNotice` ในไฟล์เดียวกัน เพราะยังไม่มีหน้าอื่นใช้)

| กรณี | หัวข้อ | เนื้อหา |
|---|---|---|
| `code === 'NETWORK_ERROR'` | เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ | บอกให้ตรวจการเชื่อมต่อแล้วลองใหม่ |
| อื่นๆ | เกิดข้อผิดพลาด | แสดง HTTP status ไว้ใช้ไล่หาสาเหตุ |

ต่างกันเพราะสาเหตุต่างกัน เชื่อมต่อไม่ได้คือคำขอไปไม่ถึงเซิร์ฟเวอร์ (เน็ตหลุด หรือเซิร์ฟเวอร์ไม่ทำงาน) ส่วนกรณีอื่นคือเซิร์ฟเวอร์รับคำขอแล้วแต่ตอบว่าผิดพลาด ซึ่งตัวเลข status ช่วยบอกว่าเกิดอะไร

เฉพาะกรณีโหลดรายการไม่ได้ที่มีปุ่ม "ลองอีกครั้ง" เพราะการโหลดรายการเป็นสิ่งที่หน้าเริ่มเอง ส่วนการเริ่ม session ผู้ใช้กดแถวซ้ำได้อยู่แล้ว

### กล่อง "เซิร์ฟเวอร์กำลังเริ่มทำงาน"

backend จะ deploy บน Render ซึ่งแผนฟรีให้เซิร์ฟเวอร์หลับเมื่อไม่มีคนใช้ คำขอแรกหลังหลับใช้เวลาหลายสิบวินาที ถ้าไม่บอกอะไรเลย ผู้ใช้จะคิดว่าระบบค้าง

หน้าจึงตั้งนาฬิกาไว้ 4 วินาที ครอบทั้งตอนโหลดรายการและตอนเริ่ม session (ตัวแปร `isWaiting`) ถ้ายังรออยู่เมื่อครบเวลาจึงแสดงกล่องนี้ ฟังก์ชัน cleanup ของ `useEffect` ล้างนาฬิกาและซ่อนกล่องทันทีที่เลิกรอ กล่องจึงไม่ค้างอยู่หลังข้อมูลมาแล้ว

## 9. สิ่งที่ตั้งใจไม่ทำ

| ไม่ทำ | เหตุผล |
|---|---|
| ไม่แสดง `severity` และ `difficulty` | เป็นข้อมูลของอาการโดยรวม แต่ผู้ใช้ยังไม่รู้ว่าเครื่องตัวเองเป็นอะไร การเห็น "ยาก/รุนแรง" ตั้งแต่ยังไม่เริ่มตรวจ อาจทำให้ตัดสินใจผิดหรือไม่กล้าเลือกอาการที่ตรงจริง |
| ไม่มีช่องค้นหา | มี 13 อาการ กวาดตาอ่านครบได้ และถ้าใส่ช่องค้นหาตอนนี้จะสับสนกับการค้นหาอาการด้วยภาษาธรรมชาติ ซึ่งเป็นงานที่ยังไม่ได้ทำและทำงานคนละแบบ (ช่องนี้จะกรองข้อความตรงตัว ไม่ได้เข้าใจความหมาย) |
| ไม่เรียงอาการที่พบบ่อยไว้ต้นรายการ | ข้อมูลตอนนี้ไม่มีค่าความถี่หรือลำดับความสำคัญให้ใช้ ถ้าเรียงเองจะเป็นการเดา |

## 10. ข้อจำกัดที่รู้ตัว

- **อาการที่คนเจอบ่อยอยู่ท้ายรายการ** อาการที่ขึ้นต้นด้วย "แอร์ไม่เย็น" และ "แอร์ไม่ทำงาน" น่าจะเป็นอาการที่ถูกเลือกบ่อยที่สุด แต่การเรียงตามพจนานุกรมไทยทำให้ไปอยู่ท้าย ถ้าจะแก้ต้องเพิ่มข้อมูลลำดับความสำคัญลงในผังขั้นตอนแต่ละชุดก่อน แล้วเรียงด้วยค่านั้นก่อนจึงเรียงตามชื่อ — เป็นการแก้ข้อมูล ไม่ใช่แก้หน้าจอ
- **ยังไม่มีเทสของ component** `SymptomRow` และ `SymptomsPage` ตรวจด้วยมือในเบราว์เซอร์ ยังไม่มีเทสอัตโนมัติ เหมือนกับขั้น 4
- **ข้อความ "เชื่อมต่อเซิร์ฟเวอร์ไม่ได้" ปรากฏสองที่** กล่องในหน้านี้ และป้ายสถานะเซิร์ฟเวอร์ใน `AppShell` จากขั้น 4 ซ้ำกันแต่ไม่ผิด
