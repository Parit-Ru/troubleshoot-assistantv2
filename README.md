# troubleshoot-assistantv2

ระบบช่วยเหลือและแนะนำการซ่อมเครื่องใช้ไฟฟ้าภายในบ้าน
(Home Appliance Repair Assistance and Recommendation System)

โครงงานวิชา 01418499 — วิทยาการคอมพิวเตอร์ มหาวิทยาลัยเกษตรศาสตร์ วิทยาเขตกำแพงแสน

ระบบพาผู้ใช้แก้ปัญหาเครื่องใช้ไฟฟ้า Samsung **ทีละขั้น** ตามขั้นตอนในหัวข้อ Troubleshooting ของคู่มือผู้ใช้
โดยใช้ **เครื่องสถานะเชิงกำหนด (Deterministic Finite Machine)** เป็นผู้ตัดสินว่าขั้นถัดไปคืออะไร
ไม่ใช่ให้ LLM ตัดสินใจ และบังคับการยืนยันคำเตือนความปลอดภัยที่ฝั่งเซิร์ฟเวอร์

เทสทั้งหมด: backend **155 ข้อ** (9 ชุด) · frontend **55 ข้อ** (7 ไฟล์)

### REST API

**กลไกเครื่องสถานะ (`/traversal`) — 5 endpoint**

- `GET /traversal/graphs`
- `POST /traversal/sessions` — body `{ "graphId": "...", "query": "..." }` (`query` ไม่บังคับ ส่งเฉพาะเมื่อเลือกผังจากผลค้นหา เซิร์ฟเวอร์คำนวณ `confidence` เอง ไม่รับคะแนนจากหน้าจอ)
- `GET /traversal/sessions/:id`
- `POST /traversal/sessions/:id/actions`
- `DELETE /traversal/sessions/:id` (คืนสถานะ 204)

ทุก response ของ session มีฟิลด์ `confidence` (ตัวเลขทศนิยม 3 ตำแหน่ง หรือ `null`)

**ค้นหาอาการ (`/symptom-search`) — 2 endpoint**

- `POST /symptom-search` — body `{ "query": "..." }` ตอบ 200 พร้อมผังที่ผ่านเกณฑ์สูงสุด 3 รายการและคะแนนความคล้าย (ว่าง = ไม่มีผังที่ตรง)
- `GET /symptom-search/status` — สถานะระบบค้นหา (`disabled`/`loading`/`ready`/`failed`) และหน่วยความจำที่ใช้ (`memoryRssMb`)

รหัสข้อผิดพลาดที่ใช้ร่วมกันทั้ง backend และ frontend: `SAFETY_CONFIRMATION_REQUIRED`, `INVALID_ACTION`, `SESSION_COMPLETED`, `SESSION_NOT_FOUND`, `GRAPH_NOT_FOUND`, `GRAPH_NODE_MISSING`, `GRAPH_SCHEMA_UNSUPPORTED`, `INTERNAL_ERROR` และของการค้นหา: `INVALID_QUERY` (400), `SEARCH_NOT_READY` (503 กำลังโหลดโมเดล ลองใหม่ได้), `SEARCH_UNAVAILABLE` (503 ปิดอยู่หรือโหลดไม่สำเร็จ)

## ค้นหาอาการด้วยภาษาธรรมชาติ

ผู้ใช้พิมพ์อาการ (เช่น "แอร์ไม่เย็น") ระบบเสนอผังขั้นตอนที่ใกล้เคียงสูงสุด 3 รายการพร้อม **คะแนนความคล้าย** ผู้ใช้เลือกและยืนยันเอง แล้วจึงเริ่มการตรวจตามเครื่องสถานะ

หลักการ

- การค้นหามีหน้าที่เดียวคือเสนอว่า "จะเริ่มผังไหน" **ขั้นถัดไปในผังเป็นของเครื่องสถานะเสมอ** และ engine ไม่ได้อ่านคะแนนไปตัดสินเส้นทาง (มีเทสตรวจว่า `confidence` เป็น `null`, 0 หรือ 1 ให้สถานะถัดไปเหมือนกัน — เทสนี้ตรวจเส้นทางของผัง `stops_working` ไม่ได้ตรวจที่สถานะด่านความปลอดภัยโดยตรง)
- ใช้โมเดล embedding สำเร็จรูป (`paraphrase-multilingual-MiniLM-L12-v2` ตัดตารางคำศัพท์แล้ว อยู่ใน `backend/model-slim/` ที่มาและสัญญาอนุญาตดู `backend/MODEL_NOTICE.md`) **ไม่ได้เทรนเอง** MySQL ไม่มีชนิด `VECTOR` จึงคำนวณความคล้าย (cosine) ในโค้ดเอง
- cosine **ไม่ใช่ความน่าจะเป็น** หน้าจอแสดงเป็น "คะแนนความคล้าย" ไม่แสดงเป็น "มั่นใจ x%"
- ไม่มีผังผ่านเกณฑ์ → ระบบไม่เดา แนะนำเลือกจากรายการหรือติดต่อศูนย์บริการ Samsung

ตัวแปรสภาพแวดล้อม

| ตัวแปร | ความหมาย |
|---|---|
| `SYMPTOM_SEARCH_ENABLED` | ต้องเป็น `true` เป๊ะๆ จึงโหลดโมเดล ค่าอื่นหรือไม่ตั้ง = ปิด (ใช้ RAM ราว 250–300 MB ในเครื่องผู้พัฒนา) ปิดอยู่เซิร์ฟเวอร์ส่วนที่เหลือทำงานปกติ |
| `ONNXRUNTIME_NODE_INSTALL=skip` | ตั้งตอนติดตั้งแพ็กเกจบน Linux (เช่น Render) เพื่อไม่ให้ดาวน์โหลดไลบรารี CUDA ที่ CPU ไม่ใช้ |

ข้อจำกัดที่รู้ตัว (วัดจากชุดตั้งเกณฑ์ที่ AI ร่าง ไม่ใช่ผลรายงาน)

- คำว่า "แอร์" ดึงทุกผังของแอร์เข้าหากัน ผังอันดับ 2–3 จึงอาจไม่เกี่ยวกับที่พิมพ์ (หน้าจอแสดงคะแนนให้เห็นช่องว่างระหว่างอันดับ)
- คำค้นนอกขอบเขตบางคำหลุดเกณฑ์ (เช่น "พัดลมตั้งพื้นส่ายไม่ได้" ได้ผังปรับความแรงพัดลมของแอร์) โมเดลแยกชนิดเครื่องไม่ได้ เกณฑ์จึงไม่ใช่เขตความปลอดภัย ผู้ใช้ต้องเห็นชื่อผังแล้วตัดสินเอง
- ผังคู่ที่สับสนง่าย: ตัวเครื่องด้านใน ↔ น้ำหยดเครื่องนอก, ไฟกะพริบ ↔ รหัสข้อผิดพลาด
- ชุดตั้งเกณฑ์ 56 ข้อร่างโดย AI ผู้พัฒนายังไม่ได้ตรวจแก้ ตัวเลขจากชุดนี้ใช้เลือกเกณฑ์ได้เท่านั้น ใช้อ้างความแม่นยำไม่ได้ (รายละเอียด: `backend/docs/explained/10` และ `11`)

## ขอบเขต

- เครื่องใช้ไฟฟ้า Samsung 4 ประเภท: เครื่องปรับอากาศ, ตู้เย็น, เครื่องซักผ้า, โทรทัศน์ (ตัดไมโครเวฟออกตามข้อเสนอแนะของอาจารย์)
- **ระดับผู้ใช้เท่านั้น** — สิ่งที่คู่มือบอกให้เจ้าของเครื่องทำเองได้ เช่น ตรวจไฟ/เบรกเกอร์ ตั้งค่า ทำความสะอาดฟิลเตอร์ อ่านรหัสข้อผิดพลาด
- อาการที่เกินขอบเขตต้องจบที่สถานะส่งต่อ "ติดต่อศูนย์บริการ Samsung" เสมอ ระบบไม่แต่งวิธีซ่อมขึ้นเอง

## เริ่มใช้งาน

ต้องใช้ Node.js 20 ขึ้นไป

### Backend

    cd backend
    npm install
    copy .env.example .env      # แล้วกรอกค่า DB_* ให้ครบ
    npm run migrate             # migration 001–004 (004 เพิ่มคอลัมน์ confidence)
    npm run seed
    npm run seed:equipment
    npm run start:dev           # ตรวจว่าทำงาน: http://localhost:3000/health
    npm test

`npm run seed` นำเข้าเฉพาะผังขั้นตอนของแอร์ (13 ชุด)

ระบบค้นหาอาการปิดอยู่เป็นค่าเริ่มต้น ถ้าต้องการลองในเครื่อง ตั้ง `SYMPTOM_SEARCH_ENABLED=true` ใน `backend/.env` แล้วรัน `npm run start:dev` ใหม่ ตรวจที่ `http://localhost:3000/symptom-search/status` (รอจน `state` เป็น `ready`)

### Frontend

    cd frontend
    npm install
    npm run dev
    npm test

ค่าเริ่มต้นใน `frontend/.env.development` คือ `VITE_USE_MOCK=false` หน้าเว็บจึงเรียก backend จริงเสมอ — **ต้องเปิด backend ไว้ก่อน** (`npm run start:dev`) จึงจะใช้งานหน้าเว็บได้
ถ้าต้องการกลับไปใช้ตัวจำลองที่รันอยู่ในเบราว์เซอร์ (เช่น ตอนทำงานโดยไม่ต่อฐานข้อมูล) ให้ตั้งค่าเป็น `true` แล้วรัน `npm run dev` ใหม่ — ในโหมดจำลองไม่มีระบบค้นหา ช่องค้นหาจะแจ้งว่าไม่พร้อมใช้งาน และเลือกจากรายการอาการได้ตามปกติ

### วัดคุณภาพการค้นหา (นักพัฒนา)

    cd backend
    npm run build
    node scripts/validate-eval-queries.js        # ตรวจรูปแบบชุดคำค้น (ไม่โหลดโมเดล)
    node scripts/eval-symptom-search.js          # วัดกับชุดตั้งเกณฑ์: ตารางกวาดเกณฑ์ รายข้อที่พลาด

### Deploy

backend อยู่บน Render (แผนฟรี) ฐานข้อมูลอยู่บน Aiven MySQL และ frontend อยู่บน GitHub Pages (`npm run deploy` ใน `frontend/`) ขั้นตอนขึ้นระบบค้นหาแบบสองจังหวะ (ขึ้นโค้ดโดยปิดสวิตช์ก่อน แล้วเปิดและวัดหน่วยความจำ) การย้อนกลับ และสคริปต์ตรวจ `backend/scripts/check-deployed-search.js` อยู่ใน `backend/docs/explained/12-deploy-symptom-search.md`

สองเรื่องที่เคยพลาดตอนขึ้นจริง (ตรวจด้วยสคริปต์ข้างบนได้)

- `CORS_ORIGIN` บน Render ต้องเป็น origin ของหน้าเว็บเป๊ะๆ (`https://parit-ru.github.io` ไม่มี path ไม่มี `/` ท้าย) ถ้าผิด เบราว์เซอร์บล็อกทุกคำขอของหน้าเว็บ แม้ `curl` จะเรียกได้ปกติ
- หลัง `npm run deploy` ต้องดูแท็บ Actions ของ repo ว่ามี "pages build and deployment" รอบใหม่ที่สำเร็จ การ push สาขา `gh-pages` อย่างเดียวไม่รับประกันว่าหน้าเว็บจะอัปเดต

ข้อจำกัดของ Render แผนฟรี: เซิร์ฟเวอร์หลับเมื่อไม่มีคนใช้ การเปิดครั้งแรกหลังหลับใช้เวลาราว 32–35 วินาที (วัดแบบควบคุม 1 ครั้ง: 35.4 วินาที) แล้วระบบค้นหาพร้อมอีกราว 5 วินาที หน้าเว็บมีกล่อง "เซิร์ฟเวอร์กำลังเริ่มทำงาน" แสดงเมื่อรอเกิน 4 วินาที

## สาธิตด่านความปลอดภัยฝั่งเซิร์ฟเวอร์

ด่านความปลอดภัยถูกบังคับอยู่ในฟังก์ชันเปลี่ยนสถานะ (`resolveNextNode()`) ฝั่งเซิร์ฟเวอร์ ไม่ใช่ที่หน้าเว็บ วิธีพิสูจน์:

> ⚠️ สคริปต์ `demo-safety-gate.ps1` ถูกลบออกจาก repo ใน commit `bc9f910` คำสั่งข้างล่างจึงใช้ไม่ได้จนกว่าจะกู้คืนหรือเขียนใหม่

    cd backend
    ./scripts/demo-safety-gate.ps1

สคริปต์นี้ยิง HTTP request ตรงเข้า REST API โดยไม่ผ่านหน้าเว็บ เพื่อยืนยันว่าต่อให้ผู้ใช้แก้โค้ดฝั่งเบราว์เซอร์ ก็ข้ามด่านนี้ไม่ได้
(โครงงานนี้ตัดสินใจไม่เขียน e2e test ด้วย supertest — ใช้สคริปต์นี้เป็นหลักฐานแทน)

## ตรวจไฟล์ผังขั้นตอน

    pip install jsonschema
    python scripts/validate_graph.py data/manuals/samsung_ac_ar70h.json

ผังขั้นตอนของแอร์ผ่านครบ 13 ชุด (มีคำเตือน 1 ข้อเรื่องการอ้างอิงคู่มือติดตั้งที่ยังไม่อยู่ในฐานความรู้)

ไม่ควรใช้ `--all` ในตอนนี้ เพราะ `data/manuals/` มีฉบับร่างของเครื่องซักผ้าที่ยังไม่ผ่านการตรวจ
ซึ่งไม่ผ่าน validator ทุกชุดตามที่คาดไว้ ทำให้คำสั่ง `--all` จบด้วยสถานะล้มเหลว
