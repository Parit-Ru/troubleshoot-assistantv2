## 1. ฟีเจอร์คืออะไร

ที่หน้าสถานะสิ้นสุด (ทั้งแบบ `resolution` และ `escalation`) ผู้ใช้เขียนข้อความอิสระว่าทำตามขั้นตอนแล้วผลเป็นอย่างไร ระบบเก็บข้อความนั้นไว้กับ session การกรอก **ไม่บังคับ** ผู้ใช้กด "ตรวจอาการอื่น" หรือ "เริ่มอาการนี้ใหม่" ได้โดยไม่กรอก

## 2. หลักการที่ห้ามละเมิด (ใช้ตลอดทุกขั้น)

1. **กลไกควบคุมเครื่องสถานะ (`traversal-engine/`) ไม่ถูกแก้ และไม่อ่านค่าผลลัพธ์** เทสของ engine ต้องผ่านเท่าเดิมโดยไม่แก้ไฟล์เทส
2. ผลลัพธ์เป็น **ข้อมูลบันทึกอย่างเดียว** เหมือน `confidence` ไม่ใช้ตัดสินเส้นทาง ไม่ใช้ในระบบค้นหาอาการ ไม่ส่งเข้า LLM
3. **ไม่ส่งผ่าน `submitAction` / `resolveNextNode`** ใช้ endpoint แยก (session ที่จบแล้วถูกปฏิเสธด้วย `SESSION_COMPLETED` อยู่แล้ว และ `resolveNextNode` ต้องเป็นจุดตัดสินใจเดียวต่อไป)
4. ไม่บังคับกรอก
5. **ห้ามอ้างว่าระบบ "เรียนรู้จากผลที่ผู้ใช้กรอก"** หรือเอาไปคำนวณความแม่นยำ เป็นแค่ข้อมูลที่เก็บไว้
6. ไม่มีระบบล็อกอิน ข้อความผูกกับ session เท่านั้น

## 3. migration 005 (`backend/migrations/005_add_session_outcome.sql`)

```sql
ALTER TABLE sessions
  ADD COLUMN outcome_text TEXT NULL,     -- ข้อความที่ผู้ใช้กรอก
  ADD COLUMN outcome_at   DATETIME NULL; -- เวลาที่บันทึก
```
(ฉบับย่อเพื่ออ่านง่าย ไฟล์จริงมี `COMMENT` และ `AFTER` ครบ และไม่มีคอมเมนต์ท้ายบรรทัด)

| คอลัมน์ | ชนิด | ความหมาย |
|---|---|---|
| `outcome_text` | `TEXT NULL` | ข้อความผลลัพธ์ `NULL` = ยังไม่ได้กรอก |
| `outcome_at` | `DATETIME NULL` | เวลาที่บันทึก ตั้งด้วย `NOW()` ใน SQL ตามข้อตกลงของ `SessionStore` |

### ทำไมออกแบบแบบนี้

| การตัดสินใจ | เหตุผล |
|---|---|
| **เพิ่มคอลัมน์ `NULL` ได้เท่านั้น ไม่แก้ของเดิม** | แถวเดิมได้ `NULL` เอง ไม่ต้องแก้ข้อมูลเก่า และ backend รุ่นเก่าบน Render ยังทำงานได้ระหว่างรอ deploy |
| **`NULL` ไม่ใช่สตริงว่าง** | แยก "ยังไม่กรอก" ออกจาก "กรอกว่าง" ไม่ได้ ถ้าใช้สตริงว่าง (และ API ไม่รับข้อความว่างอยู่แล้ว) |
| **`ALTER TABLE` คำสั่งเดียวเพิ่มสองคอลัมน์** | ตัวรัน migration (`run-migrations.js`) **ไม่ครอบ transaction** ถ้าไฟล์พังกลางทางต้องแก้ด้วยมือ MySQL 8 ทำ DDL แบบ atomic ต่อ 1 คำสั่ง จึงไม่มีสถานะที่ได้คอลัมน์เดียว |
| **`TEXT` ไม่ใช่ `VARCHAR`** | ตามที่ตกลงไว้ ความยาวสูงสุดจำกัดที่ฝั่งแอป (ค่าที่เสนอ 1,000 ตัวอักษร ไม่เกิน 4,000 ไบต์ใน `utf8mb4` ต่ำกว่าขีดจำกัด 65,535 ไบต์ของ `TEXT`) |
| **`DATETIME` ไม่ใช่ `TIMESTAMP`** | ตามที่ตกลงไว้ `DATETIME` ไม่แปลงตาม time zone ตอนอ่าน ค่านี้ไม่ถูกเอาไปเทียบกับคอลัมน์เวลาอื่น จึงไม่กระทบอายุ session (`expires_at` เป็น `TIMESTAMP` ตัวเดิม) |

### ทำไมลำดับขึ้นระบบต้องเป็น "migration ก่อน แล้วค่อย deploy โค้ด"

- backend **รุ่นเก่า** ใช้ต่อได้หลังเพิ่มคอลัมน์ เพราะ SQL ทุกจุดที่แตะตาราง `sessions` ระบุชื่อคอลัมน์เอง (`INSERT`, `SELECT`, `UPDATE` ใน `session.store.ts`) ไม่มี `SELECT *` (ตรวจแล้วทั้ง `src/` และ `scripts/`) คอลัมน์ที่ไม่รู้จักจึงถูกข้ามเฉยๆ
- backend **รุ่นใหม่** (ขั้น 2) จะ `SELECT`/`UPDATE` คอลัมน์เหล่านี้ ถ้าขึ้นก่อน migration แล้วฐานข้อมูลยังไม่มีคอลัมน์ คำสั่ง SQL จะล้ม Render deploy อัตโนมัติจาก `main` เมื่อ push จึงต้องรัน migration บน Aiven **ก่อน** push โค้ดใหม่เสมอ

### ข้อควรรู้ด้านข้อมูล

- ข้อความเป็นข้อความอิสระ ผู้ใช้อาจพิมพ์ข้อมูลส่วนตัวมาเอง หน้าจอ (ขั้น 3) จึงมีคำเตือนไม่ให้ใส่ชื่อ เบอร์โทร ที่อยู่ และคำเตือนนี้ **ไม่ใช่การป้องกัน** ระบบไม่ได้กรองข้อมูลส่วนตัว
- **ยังไม่มีตัวกวาด session ที่หมดอายุ** (ดูคอมเมนต์ใน `session.store.ts`) ข้อความจึงอยู่ในตารางต่อไปแม้ session หมดอายุจนอ่านผ่าน API ไม่ได้แล้ว ถ้าจะใช้ข้อความนี้นอกเหนือจากที่ระบุ ต้องคิดเรื่องการเก็บรักษาและการแจ้งผู้ใช้ก่อน
- `sessions.updated_at` เป็น `ON UPDATE CURRENT_TIMESTAMP` การบันทึกข้อความจึงทำให้ `updated_at` เปลี่ยน (ไม่กระทบ `expires_at`)

## 4. สิ่งที่ยังไม่ได้ตรวจ (ณ ขั้น 1.1)

| เรื่อง | ผล |
|---|---|
| รัน migration 005 บน Aiven (MySQL 8.4.8) | **สำเร็จ** `schema_migrations` บันทึก 005 แล้ว (สถานะ ✅ ทั้ง 5 ไฟล์) |
| คอลัมน์ใหม่ | `outcome_text text NULL`, `outcome_at datetime NULL` ชุดอักขระ `utf8mb4` / `utf8mb4_unicode_ci` ลำดับถัดจาก `confidence` ตามที่ตั้งใจ |
| ข้อมูลเดิม | `sessions` 8 แถว และ `session_history` 23 แถว **เท่าก่อนหน้า** ไม่มีแถวใดมีค่าในคอลัมน์ใหม่ (ล้วน `NULL`) หมายเหตุ: ตัวเลข "ก่อนหน้า" มาจากการนับล่าสุดก่อนรัน (ตอนล้างข้อมูลทดสอบ T2 วันที่ 4 ต.ค.) ไม่ใช่การนับทันทีก่อนรัน เพราะมีเหตุการณ์ในหัวข้อ 6 |
| backend รุ่นเดิมบน Render หลังตารางเปลี่ยน | ตรวจแบบอ่านอย่างเดียว: `/health` ok, `/traversal/graphs` 200, และ `GET /traversal/sessions/<UUID ที่ไม่มีอยู่>` ได้ **404 `SESSION_NOT_FOUND` ไม่ใช่ 500** ซึ่งรัน `SELECT` ที่ระบุชื่อคอลัมน์กับตารางที่แก้แล้วจริง |
| เส้นทางเขียนของ backend รุ่นเดิม (`INSERT`/`UPDATE`) | **ยังไม่ได้ทดสอบจริงบน Render** (ข้อสรุปว่าใช้ได้มาจากการอ่าน SQL: ระบุคอลัมน์เองทั้งหมด และคอลัมน์ใหม่เป็น `NULL` ได้) ถ้าต้องการยืนยัน ต้องเริ่มและลบ session ทดสอบ 1 รายการผ่าน Render (เขียนฐานข้อมูลจริง) |
| ไวยากรณ์ SQL ล่วงหน้าบนตาราง `TEMPORARY` | **ไม่ได้ทำ** (ข้ามโดยไม่ตั้งใจ ดูหัวข้อ 6) ไวยากรณ์พิสูจน์ด้วยการรันจริงที่สำเร็จ |

## 5. วิธีตรวจ (ซ้ำได้)

ที่โฟลเดอร์ `backend\`

```powershell
node scripts/run-migrations.js --status    # ดูสถานะ ไม่รันอะไร (อ่านอย่างเดียว)
node scripts/run-migrations.js             # รัน migration ที่ยังไม่เคยรัน (กระทบฐานข้อมูลตาม .env)
```

⚠️ **ใน Windows PowerShell อย่าใช้ `npm run migrate -- --status`** PowerShell ตัดตัวคั่น `--` ทิ้งก่อนส่งให้ npm ทำให้ npm ไม่ส่ง `--status` ต่อไปถึงสคริปต์ (npm เตือน `Unknown cli config "--status"`) แล้ว **สคริปต์รันโดยไม่มี `--status` คือรัน migration จริง** ใช้ `node scripts/run-migrations.js --status` แทน หรือใส่ตัวคั่นในเครื่องหมายคำพูด `npm run migrate '--' --status` (ทดสอบทั้งสองแบบแล้วหลัง migration ครบ: แบบมีเครื่องหมายคำพูดแสดงรายการสถานะ ส่วนแบบ `-- --status` เข้าโหมดรันและพิมพ์ "ไม่มี migration ที่ต้องรัน" พร้อมคำเตือนของ npm) ข้อควรระวังนี้มาจากเหตุการณ์จริงในหัวข้อ 6

ตรวจคอลัมน์ใหม่ด้วย SQL: `SHOW COLUMNS FROM sessions LIKE 'outcome%';` ต้องได้ 2 แถว (`outcome_text text YES`, `outcome_at datetime YES`) จำนวนแถวเดิมของ `sessions` ต้องเท่าเดิม และค่าของคอลัมน์ใหม่เป็น `NULL` ทั้งหมด

**เรื่องเวลาที่ตรวจเอง:** คอลัมน์ `applied_at` ของ `schema_migrations` เป็น `TIMESTAMP` ซึ่งไลบรารี `mysql2` ฝั่ง Node แปลงตาม time zone ของเครื่องที่รัน (ในเครื่องนี้ UTC+7) ตัวเลขที่พิมพ์จึงเหลื่อมไป 7 ชั่วโมงจากเวลาจริงของเซิร์ฟเวอร์ ถ้าจะเทียบเวลา ให้เทียบใน SQL ด้วย `TIMESTAMPDIFF(SECOND, applied_at, NOW())` (เซิร์ฟเวอร์ใช้ time zone `SYSTEM` = UTC) เรื่องเดียวกับที่คอมเมนต์ใน `session.store.ts` เตือนไว้

## 6. เหตุการณ์ที่เกิดจริงตอนรัน migration (บันทึกตามจริง)

ตอนจะดูสถานะก่อนรัน ผู้พัฒนา (Claude Code) พิมพ์ `npm run migrate -- --status` ใน PowerShell ตัวคั่น `--` ถูกตัดทิ้งตามที่เขียนในหัวข้อ 5 ผลคือสคริปต์รัน migration 005 จริงบน Aiven ทันที ก่อนขั้นตอนที่วางแผนไว้ (ตรวจสถานะ → เก็บสภาพตาราง → ตรวจไวยากรณ์บนตาราง `TEMPORARY` → รัน) การรัน migration อยู่ในสิ่งที่ผู้พัฒนาอนุมัติแล้ว (ขั้น 1.2) และสำเร็จ แต่ขั้นตอนตรวจล่วงหน้าถูกข้ามและไม่ได้เก็บภาพ "ก่อนแก้" จึงใช้การตรวจหลังรันตามหัวข้อ 4 แทน ต้นตอคือคอมเมนต์หัวไฟล์ `backend/scripts/run-migrations.js` บรรทัดที่ 7 ซึ่งแนะนำรูปแบบ `npm run migrate -- --status` ที่ใช้ไม่ได้ใน PowerShell (ไฟล์เดิมนอกขอบเขตงานนี้ ยังไม่ได้แก้ แจ้งผู้พัฒนาแล้ว)

## 7. `SessionStore` — เมธอดเก็บและอ่านผลลัพธ์ (ขั้น 2.1)

ไฟล์ `backend/src/traversal/session.store.ts` เพิ่ม 2 เมธอดท้ายคลาส (`find()` เดิมไม่ถูกแก้)

| เมธอด | ทำอะไร | SQL |
|---|---|---|
| `saveOutcome(sessionId, text)` → `boolean` | บันทึกข้อความของ session ที่จบแล้ว **ได้ครั้งเดียว** คืน `true` = บันทึกแล้ว `false` = ไม่มีแถวตรงเงื่อนไข | `UPDATE sessions SET outcome_text = ?, outcome_at = NOW() WHERE session_id = ? AND status = 'completed' AND outcome_text IS NULL` |
| `findOutcome(sessionId)` → `string \| null` | อ่านข้อความที่เคยบันทึก `null` = ยังไม่กรอก / ไม่มี session / หมดอายุ | `SELECT outcome_text FROM sessions WHERE session_id = ? AND expires_at > NOW()` |

### ทำไมออกแบบแบบนี้

| การตัดสินใจ | เหตุผล |
|---|---|
| **เงื่อนไข `outcome_text IS NULL` อยู่ใน `UPDATE` เดียวกัน** | ทำให้ "ส่งครั้งเดียว" เป็น atomic ถ้าสองคำขอพร้อมกัน InnoDB ล็อกแถวทีละคำสั่ง คำขอแรกเปลี่ยน `NULL` เป็นข้อความ คำขอที่สองเห็นว่าไม่ใช่ `NULL` แล้วไม่แก้อะไร (0 แถว) มีผู้ชนะคนเดียวโดยไม่ต้องใช้ transaction ถ้าเช็คก่อนแล้วค่อยเขียนเป็นสองคำสั่ง ทั้งสองคำขออาจผ่านการเช็คพร้อมกันแล้วเขียนทับกัน |
| **`status = 'completed'` ในคำสั่งเดียวกัน** | กันไว้อีกชั้นว่าจะไม่บันทึกให้ session ที่ยังเดินอยู่ แม้ service จะตรวจแล้ว |
| **คืน `boolean` ไม่แยกสาเหตุที่ล้ม** | `false` เป็นได้ 3 สาเหตุ (ไม่มี session / ยังไม่จบ / เคยบันทึกแล้ว) service จะเรียก `find()` ตรวจสองข้อแรกก่อน แล้วถือว่า `false` ที่เหลือคือ "เคยบันทึกแล้ว" (ขั้น 2.3) |
| **`findOutcome` แยกจาก `find()`** | `find()` คืน `SessionState` ซึ่งเป็น type ของกลไกควบคุมเครื่องสถานะ ถ้ายัดค่านี้เข้าไป engine จะได้รับมันไปด้วย **โครงสร้างนี้ทำให้ engine ไม่เคยเห็นผลลัพธ์เลย** ไม่ใช่แค่ตั้งใจไม่อ่าน และ service จะเรียก `findOutcome` เฉพาะตอน session จบ (สถานะอื่นไม่มีทางมีค่า) การเดินขั้นตอนปกติจึงไม่เสียคำสั่ง SQL เพิ่ม |
| **ไม่ต่ออายุ session ตอนบันทึก** | การกรอกผลลัพธ์ไม่ใช่ action ของเครื่องสถานะ ผลข้างเคียง: ถ้ากรอกตอนใกล้ครบ 24 ชั่วโมงนับจาก action ล่าสุด การบันทึกอาจได้ 404 (session หมดอายุ) |
| **เวลา `NOW()` ใน SQL** | ตามข้อตกลงของ `SessionStore` ไม่ใช้เวลาจาก JavaScript |
| **ไม่ตรวจความยาวหรือข้อความว่างที่นี่** | เป็นหน้าที่ของ DTO (ขั้น 2.2) store รับค่าที่ผ่านการตรวจมาแล้ว |

### สิ่งที่ตรวจแล้วและที่ยังไม่ได้ตรวจ

| เรื่อง | สถานะ |
|---|---|
| `tsc`, build, เทสเดิมทั้งชุด | ✅ ผ่าน (backend 9 ชุด **155** ข้อเท่าเดิม) ไฟล์ใน `traversal-engine/` ไม่ถูกแก้ |
| ไวยากรณ์และชื่อคอลัมน์ของ SQL ทั้งสองคำสั่ง | ✅ ตรวจกับสคีมาจริงบน Aiven ด้วย `EXPLAIN UPDATE` (ไม่แก้แถวใด) ได้แผน `UPDATE/sessions/type=range/key=PRIMARY` และลำดับพารามิเตอร์ถูก (ข้อความก่อนรหัส session) |
| `findOutcome` | ✅ รัน `SELECT` จริงกับ UUID ที่ไม่มีอยู่ ได้ `null` |
| ข้อมูลไม่ถูกแตะระหว่างตรวจ | ✅ `sessions` 8 แถว แถวที่มี `outcome_text` 0 แถว ก่อนและหลัง |
| **`saveOutcome` เขียนจริง** (บันทึกสำเร็จ → `true`, ส่งซ้ำ → `false`, ภาษาไทยอ่านกลับได้ตรงตัวอักษร, สองคำขอพร้อมกันได้ผู้ชนะคนเดียว) | ❌ **ยังไม่ได้ทดสอบ** ต้องมี session ที่จบแล้วจริง (ต้องเขียนฐานข้อมูลจริง) จะตรวจในการทดสอบเต็มระบบ (ขั้น 2.8/5) |
| เทสยูนิตของ `SessionStore` | ไม่มี (ตามเดิม: ต้องใช้ MySQL จริง พิสูจน์ผ่านการยิง API) เทสของ service ใช้ store ปลอมที่จะเพิ่ม 2 เมธอดนี้ในขั้น 2.7 |

## 8. DTO — ตัวตรวจ body (ขั้น 2.2) `traversal.dto.ts`

| สิ่งที่เพิ่ม | ทำอะไร |
|---|---|
| `MAX_OUTCOME_LENGTH = 1000` | เพดานความยาวข้อความ นับหลังตัดช่องว่างหน้าหลัง เป็นหน่วย `.length` ของ JavaScript (อีโมจิ = 2) |
| `InvalidOutcomeError` | error ของ body ผลลัพธ์ แยกจาก `InvalidRequestBodyError` เพื่อให้ filter ออกรหัส `INVALID_OUTCOME` ไม่ปนกับ `INVALID_ACTION` |
| `parseOutcomeBody(body)` | body ต้องเป็น object ที่มี `text` เป็นข้อความ ตัดช่องว่างหน้าหลัง **ห้ามว่าง** ไม่เกินเพดาน คืน `{ text }` เท่านั้น (field แปลกปลอมถูกทิ้ง) |
| ฟิลด์ `outcome: string \| null` ใน `SessionResponseDto` | อยู่ใน response ของ session ทุกชนิด |

ข้อควรรู้: ไม่กรองเนื้อหา (ไม่กรองข้อมูลส่วนตัว ไม่ escape HTML) ข้อความเป็นข้อมูลบันทึก หน้าจอต้องแสดงเป็นข้อความธรรมดาผ่าน React (ห้ามใช้ `dangerouslySetInnerHTML`) ข้อความว่างถือว่าผิดรูปแบบ: ผู้ใช้ **ไม่กรองก็ได้** แต่ถ้าส่งมาต้องมีเนื้อหา (หน้าจอไม่ควรส่งคำขอเมื่อช่องว่าง)

## 9. service — ลำดับการตรวจและการประกอบ response (ขั้น 2.3, 2.6) `traversal.service.ts`

`submitOutcome(sessionId, text)` ตรวจตามลำดับนี้ แต่ละข้อใช้รหัสต่างกัน หน้าจอจึงแสดงข้อความถูกกรณี:

| ลำดับ | เงื่อนไข | error | HTTP / รหัส |
|:-:|---|---|---|
| 1 | session ไม่มีหรือหมดอายุ | `SessionNotFoundError` (เดิม) | 404 `SESSION_NOT_FOUND` |
| 2 | `session.status` ไม่ใช่ `'completed'` | `SessionNotCompletedError` (ใหม่) | 409 `SESSION_NOT_COMPLETED` |
| 3 | `saveOutcome()` คืน `false` (เคยบันทึกแล้ว) | `OutcomeAlreadySubmittedError` (ใหม่) | 409 `OUTCOME_ALREADY_SUBMITTED` |
| — | สำเร็จ | — | 200 พร้อม session ปัจจุบัน และ `outcome` = ข้อความที่เพิ่งบันทึก |

- **ข้อ 3 ไม่เช็คก่อนเขียน** ให้ `UPDATE` เดียวตัดสิน (หัวข้อ 7) ถ้าข้อ 1–2 ผ่านแล้วแต่ได้ `false` แปลว่ามีผลลัพธ์อยู่แล้ว (สองคำขอพร้อมกัน ชนะได้คนเดียว) ช่องว่างที่ยอมรับ: ถ้า session หมดอายุพอดีระหว่างข้อ 1 กับ `UPDATE` ตัว `UPDATE` ยังเขียนสำเร็จ (ไม่เช็คอายุ) ซึ่งไม่มีผลเสีย
- **`getSession`** อ่านผลลัพธ์ด้วย `findOutcome()` **เฉพาะตอน `status === 'completed'`** ผู้ใช้ที่กำลังตรวจอยู่ไม่เสียคำสั่ง SQL เพิ่ม (มีเทสนับจำนวนครั้งที่เรียก)
- **`startSession` / `submitAction`** คืน `outcome: null` เสมอ ซึ่งถูกต้อง: session ที่เพิ่งเริ่มหรือเพิ่งเดินต่อ (แม้เพิ่งถึงสถานะสิ้นสุด) ยังไม่เคยมีผลลัพธ์ เพราะ `saveOutcome` รับเฉพาะ session ที่จบแล้ว และ action หลังจบถูกปฏิเสธอยู่แล้ว
- `toResponse()` ยังเป็นจุดประกอบ response จุดเดียว รับ `outcome` เป็นพารามิเตอร์ที่ 4 (ค่าเริ่มต้น `null`)

## 10. endpoint และ filter (ขั้น 2.4, 2.5)

**`POST /traversal/sessions/:id/outcome`** body `{ "text": "..." }` → ตอบ **200** (ไม่ใช่ 201 ต่างจาก `/sessions` และ `/actions` เพราะไม่ได้สร้างทรัพยากรใหม่ ต้องใส่ `@HttpCode(200)` เพราะค่าเริ่มต้นของ NestJS สำหรับ POST คือ 201) response เป็นรูปเดียวกับ session อื่น

| รหัสที่ client เห็น | HTTP | เกิดเมื่อ |
|---|:-:|---|
| `INVALID_OUTCOME` | 400 | body ผิดรูปแบบ (ไม่ใช่ object / ไม่มี `text` / ไม่ใช่ข้อความ / ว่าง / เกิน 1,000) |
| `SESSION_NOT_FOUND` | 404 | ไม่มี session หรือหมดอายุ (รหัสเดิม) |
| `SESSION_NOT_COMPLETED` | 409 | session ยังเดินอยู่ |
| `OUTCOME_ALREADY_SUBMITTED` | 409 | เคยบันทึกผลลัพธ์แล้ว (ส่งครั้งเดียวเท่านั้น) |

- ตัวเลือก "ส่งครั้งเดียว ไม่ให้แก้" ตามที่ตกลง (ข้อ 1)
- `traversal.exception.filter.ts` แปลง error ใหม่ 3 ตัวด้วย `instanceof` เหมือนตัวอื่น (ตอนนี้รู้จัก 11 ชนิด) ติดที่ระดับ controller ด้วย `@UseFilters` อยู่แล้ว route ใหม่จึงได้ filter นี้เอง
- **ไม่ต้องลงทะเบียน provider หรือโมดูลเพิ่ม** (`traversal.module.ts` ไม่ถูกแก้): error เป็นคลาสธรรมดา ไม่ใช่ provider ส่วน controller, service, store ลงทะเบียนอยู่แล้ว

## 11. ทำไมจึงบอกได้ว่ากลไกควบคุมเครื่องสถานะ (engine) ไม่ถูกแตะและไม่เห็นผลลัพธ์

| หลักฐาน | รายละเอียด |
|---|---|
| โค้ด | `git status` / `git diff` ของ `backend/src/traversal-engine/` ว่างเปล่า ทั้งไฟล์โค้ดและไฟล์เทส |
| โครงสร้าง | `SessionState` (type ของ engine) ไม่มีฟิลด์ผลลัพธ์ `find()` ไม่อ่านคอลัมน์ใหม่ ผลลัพธ์ผ่าน `findOutcome()` ซึ่งเรียกที่ชั้น service หลังเรียก engine แล้วเท่านั้น engine จึงไม่เคยได้รับค่านี้เป็นอินพุต |
| พฤติกรรม | `submitOutcome` ไม่เรียก `submitAction` / `resolveNextNode` เลย (เรียกแค่ `getCurrentNode` เพื่ออ่านสถานะปัจจุบัน เหมือน `getSession`) |
| เทส | หลังบันทึกผลลัพธ์ การส่ง action เข้า session เดิมยังถูกปฏิเสธด้วย `SessionAlreadyCompletedError` ตามเดิม · เดินเส้นเดียวกัน มี/ไม่มีผลลัพธ์ จบที่สถานะเดียวกัน · `confidence` ไม่ถูกแตะ |

## 12. เทสและการตรวจ (ขั้น 2.7, 2.8)

| รายการ | ผล |
|---|---|
| เทส backend ทั้งชุด | **10 ชุด 183 ข้อผ่าน** (เดิม 9 ชุด 155 ข้อ เพิ่ม 28: DTO 9, service 14, filter 5 ในไฟล์ใหม่ `traversal.exception.filter.spec.ts`) เทสเดิมทุกข้อผ่านโดยไม่แก้ |
| `tsc --noEmit`, `npm run build` | ผ่าน |
| เทสของ engine | ไม่ถูกแก้ ผ่านเท่าเดิม |
| ทดลองใส่บั๊กโดยตั้งใจ (mutation check) | ลบการตรวจ "จบแล้ว" และให้ `getSession` อ่านผลลัพธ์ทุกครั้ง → เทสล้ม **พอดี 2 ข้อที่ออกแบบไว้** (ข้อ `SessionNotCompletedError` และข้อ "ไม่เรียก `findOutcome`") แล้วคืนไฟล์เดิมจากสำเนา (แฮชตรง) เพื่อยืนยันว่าเทสใหม่จับความผิดพลาดได้จริง |
| ตรวจชั้น HTTP กับ backend ในเครื่อง (**ไม่เขียนข้อมูล**) | 10/10: session ที่ไม่มี → 404 `SESSION_NOT_FOUND` · body ผิด 5 แบบ → 400 `INVALID_OUTCOME` · 1,000 ตัวอักษรพอดีผ่านตัวตรวจ (ไปจบที่ 404) · รหัสเดิมของ `/actions` ยังเป็น `INVALID_ACTION` |

### ที่ยังไม่ได้ตรวจ (ต้องเขียนฐานข้อมูลจริง ทำในขั้น 5)

- เส้นทางที่ **สำเร็จจริง** กับ MySQL: `POST` ได้ 200 และข้อความถูกบันทึก, ส่งซ้ำได้ 409 `OUTCOME_ALREADY_SUBMITTED`, ยิงกับ session ที่ยังเดินอยู่ได้ 409 `SESSION_NOT_COMPLETED`
- ภาษาไทยและอักขระพิเศษอ่านกลับจากฐานข้อมูลตรงตัวอักษร
- สองคำขอ **พร้อมกันจริง** ได้ผู้ชนะคนเดียว (เทสปัจจุบันพิสูจน์ตรรกะของ service ด้วย store ปลอมที่ไม่มีการแข่งกันจริง ความ atomic เป็นคุณสมบัติของ `UPDATE` เงื่อนไขเดียว ซึ่งตรวจได้เฉพาะกับฐานข้อมูลจริง)
- `@HttpCode(200)` ตอนสำเร็จ (ตรวจได้เมื่อมี session ที่จบแล้วจริง)
