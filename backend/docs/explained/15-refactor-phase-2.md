# Refactor เฟส 2 — ทำให้ `graph.repository.ts` สั้นและอ่านง่ายขึ้น

ไฟล์เดียวที่แก้: `backend/src/traversal/graph.repository.ts` (ตัวโหลดผังขั้นตอนจาก MySQL เข้าหน่วยความจำตอนบูต) พฤติกรรมเหมือนเดิม ยกเว้นข้อความ error ของข้อมูลเสีย 3 กรณี (ดูหัวข้อ "สิ่งที่เปลี่ยนจริงๆ")

## เปลี่ยนอะไร

**1. `buildNode` ไม่ต้องสร้างตัวแปรชั่วคราว**
ก่อน: ทุกกรณีเขียน `const node: CheckpointNode = {...}; return node;` และมีตัวช่วย `need` ห่อ `required` อีกชั้น ส่งรหัสผัง รหัสโหนด และชนิดโหนดต่อกันทุกครั้ง
หลัง: `return { ... }` ตรงๆ ทุกกรณี และเรียก `required(ค่า, 'ชื่อคอลัมน์', row)` ซึ่งอ่านรหัสผัง รหัสโหนด และชนิดโหนดจาก `row` เอง
TypeScript ยังตรวจชนิดครบ: เมธอดประกาศว่าคืน `TroubleshootingNode` และ `switch` ตัวสุดท้ายยังมี `never` ยืนยันว่าครอบคลุมทั้ง 5 ประเภท

**2. ยุบ `required` กับ `requiredEnum` เป็นฟังก์ชันเดียว**
สองตัวเดิมทำเรื่องเดียวกัน (โยน error ถ้าค่าเป็น NULL) ต่างกันแค่ตัวหนึ่งคืน `string` อีกตัวคืน enum ตอนนี้เป็น `required<T extends string>` ตัวเดียว คืน type เดิมกลับไป

**3. เอา getter `count` กับ `nodeCount` ออก**
ไม่มีใครเรียกนอกจาก log บรรทัดเดียวตอนบูต ตอนนี้ log ใช้ `this.graphs.size` และ `nodeRows.length` ตรงๆ

**4. ลบ import ชนิดโหนด 5 ตัวที่ไม่ได้ใช้แล้ว** (`CheckpointNode`, `InstructionNode`, `InputNode`, `ResolutionNode`, `EscalationNode`)

ผลต่อขนาด: ไฟล์จาก 402 → 336 บรรทัด (รวมการลดคอมเมนต์ของเฟส 1 ที่ยังไม่ได้ commit) `buildNode` จาก 100 → 72 บรรทัด ยังไม่สั้นมากเพราะ 5 กรณีของ `switch` ต้องระบุทุก field อยู่ดี แต่ไม่มีโค้ดซ้ำซ้อนแล้ว

## สิ่งที่เปลี่ยนจริงๆ (ไม่ใช่แค่ท่าทาง)
`required` รุ่นเก่าสองตัวมีข้อความ error ต่างกัน และ `requiredEnum` ไม่ตรวจสตริงว่าง ตอนนี้ใช้ข้อความเดียวและตรวจ NULL หรือสตริงว่างทุกกรณี ผลคือ
- ข้อความ error ของคอลัมน์ `input_type`, `outcome_kind` (ตอนเป็น NULL) เปลี่ยนจาก "…ต้องมีคอลัมน์ 'x' แต่ค่าเป็น NULL" เป็นรูปแบบเดียวกับคอลัมน์อื่น ("…เป็น type='…' ซึ่งต้องมีคอลัมน์ 'x' แต่ค่าเป็น NULL/ว่าง") ชนิด error ยังเป็น `GraphDataIntegrityError` เหมือนเดิม
- ค่าว่าง `''` ในคอลัมน์ ENUM ทั้งสองนี้ รุ่นเก่ายอมผ่าน รุ่นใหม่โยน error ซึ่งในฐานข้อมูลที่ตั้ง strict mode (Aiven ใช้ MySQL 8.4) ค่าแบบนี้เกิดไม่ได้ และเกิดเฉพาะกรณีข้อมูลเสียตอนบูต ไม่กระทบผู้ใช้
สองข้อนี้เกิดเฉพาะตอนข้อมูลในฐานข้อมูลเสีย ซึ่งทำให้เซิร์ฟเวอร์ไม่บูตอยู่แล้ว ไม่ใช่ข้อมูลปกติ

## ตรวจว่าพฤติกรรมไม่เปลี่ยนอย่างไร
ไฟล์นี้ **ไม่มี test ของตัวเอง** (เทส backend 183 ข้อไม่ได้เรียกมัน ใช้ของปลอมแทน) ผมจึงทำตัวเทียบ (อยู่นอก repo) ที่เก็บสำเนารุ่นก่อนแก้ แล้วรันทั้งสองรุ่นเทียบกัน
- **ฐานข้อมูลจริง (SELECT อย่างเดียว):** ทั้งสองรุ่นโหลดได้ 13 ผัง 95 โหนด และเมื่อแปลงเป็น JSON แล้ว `listAll()` กับผังทุกตัว (ทุกโหนด ทุก field รวมลำดับ key) เหมือนกันทุกตัวอักษร
- **แถวที่ทำให้เสียโดยตั้งใจ (ปลอม ไม่แตะฐานข้อมูล) 17 กรณี:** ขาด `on_yes`/`on_no`/`next_node`/`store_as`/`input_type`/`outcome_kind`, ค่าว่าง, `node_type` แปลก, `schema_version` ไม่ใช่ 2, ผังไม่มีโหนด, `entry_node` ไม่มีในผัง, ค่า JSON เป็น string, โหนดปกติแต่ละชนิด ผลเหมือนกัน 14 กรณี ต่างกัน 3 กรณีที่ข้อความ error ตามที่อธิบายข้างบน (ชนิด error เหมือนเดิม)
- backend jest 10 ชุด 183 ข้อ ผ่าน (เท่าค่าตั้งต้น) · `tsc` ทั้งแบบ dev และแบบ build ผ่าน · ไฟล์ test ไม่ถูกแตะ (hash ตรง)
- ก่อนแก้ ผมรันตัวเทียบกับตัวมันเอง (รุ่นเก่า = รุ่นใหม่) ได้ "เหมือนกันทั้งหมด" เพื่อยืนยันว่าตัวเทียบเองไม่มีปัญหา

## ที่ไม่ได้ตรวจ
- ไม่ได้รัน backend จริงขึ้นมาแล้วยิง API (ตัวเทียบเรียก `GraphRepository` ตรงๆ โดยไม่ผ่าน NestJS) การเรียกใช้ผ่าน DI เหมือนเดิมเพราะไม่ได้แก้ constructor หรือ decorator
- ไม่ได้เพิ่ม test ใหม่ให้ไฟล์นี้ (ตามกฎห้ามเพิ่ม/แก้ test โดยไม่ถาม) ช่องว่างนี้ยังอยู่
