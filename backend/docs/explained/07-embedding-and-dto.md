# ขั้น 1.4–1.5 — `embedding.service.ts` และ `symptom-search.dto.ts`

สองไฟล์นี้เป็นชิ้นส่วนรอบนอกของงานค้นหาอาการ ไฟล์แรกแปลงข้อความเป็นเวกเตอร์ ไฟล์ที่สองกำหนดรูปร่างของ request/response และตรวจ body ที่ผู้ใช้ส่งมา ส่วนที่ตัดสินว่าผังขั้นตอนไหนคล้ายที่สุดอยู่ใน `symptom-matcher.ts` (เอกสาร `06`) ส่วนที่ต่อทั้งหมดเข้าด้วยกันคือ `symptom-search.service.ts` (ขั้น 1.6)

| ไฟล์ | หน้าที่ | เทส |
|---|---|---|
| `src/symptom-search/embedding.service.ts` | โหลดโมเดล MiniLM แล้วแปลงข้อความเป็นเวกเตอร์ 384 มิติ | ไม่มี (ดูข้อ 1.4) |
| `src/symptom-search/symptom-search.dto.ts` | ชนิดข้อมูล request/response + ตัวตรวจ body `parseSearchBody` | 10 เคส |
| `src/symptom-search/symptom-search.dto.spec.ts` | เทสของ dto | |

> **ศัพท์:** เอกสารนี้ใช้คำว่า เครื่องสถานะ / สถานะ ตาม PROJECT_CONTEXT ข้อ 3
> ชื่อในโค้ดยังคงเดิม: **`graph` ในโค้ด = ผังขั้นตอนการวินิจฉัย 1 อาการ (เครื่องสถานะ 1 ชุด)**
> เช่น `graphId` = รหัสผังขั้นตอน

## ส่วนที่ 1 — `embedding.service.ts` (ขั้น 1.4)

### 1.1 หน้าที่

รับข้อความ คืนเวกเตอร์ 384 มิติ (`Float32Array`) เท่านั้น ไม่รู้จักผังขั้นตอน ไม่คิดคะแนน

### 1.2 ค่าตั้งและเหตุผล

| ค่า | ที่มา / เหตุผล |
|---|---|
| โมเดล `Xenova/paraphrase-multilingual-MiniLM-L12-v2` | โมเดลสำเร็จรูป **ไม่ได้เทรนเอง** รองรับหลายภาษารวมไทย |
| `dtype: 'q8'` | รุ่นบีบอัด 8 บิต ใช้ RAM น้อยกว่า fp32 มาก |
| ใช้โมเดลที่ตัดคำศัพท์แล้วที่ `backend/model-slim/` | ไฟล์เล็กลงจาก 112.8 เหลือ 53.3 MiB และเวกเตอร์ **เหมือนกันทุกบิต 141/141 ข้อความ** (ผลจากขั้น 1.2.3) |
| `env.allowRemoteModels = false` | ไฟล์โมเดลอยู่ใน git แล้ว จึง **ห้ามดาวน์โหลดตอนรัน** ถ้าไฟล์หายจะพังให้เห็นทันที ไม่ใช่เงียบๆ ไปโหลดของอื่นมาแทน |
| `intraOpNumThreads: 1` | Render free มี 0.1 CPU ไม่มีประโยชน์ที่จะเปิดหลายเธรด |
| `MODEL_CACHE_DIR = path.resolve(__dirname, '../../model-slim')` | ขึ้นไป 2 ระดับจากโฟลเดอร์ `symptom-search` ได้ `backend/` เหมือนกันทั้งตอนรันจาก `src/` (เทส) และจาก `dist/` (เซิร์ฟเวอร์จริง) |
| ล็อกเวอร์ชัน `@huggingface/transformers` เป็น `"4.3.0"` ตายตัว | ตัวเลขที่วัดทั้งหมดใช้ 4.3.0 (ใน `package.json` ตั้งไว้แล้ว) |

### 1.3 `import()` แบบ lazy

`load()` ใช้ `await import('@huggingface/transformers')` ไม่ใช่ `import` ที่หัวไฟล์ เพราะเมื่อปิดฟีเจอร์ค้นหา (`SYMPTOM_SEARCH_ENABLED` ไม่ใช่ `true`) เซิร์ฟเวอร์จะไม่โหลดไลบรารีนี้เลย ประหยัดหน่วยความจำบน Render ที่มีแค่ 512 MB และไม่กระทบด่านความปลอดภัย

### 1.4 ทำไมไม่มีเทสของไฟล์นี้

ต้องโหลดโมเดลจริง (ใช้ RAM ราว 250 MB) ทำให้เทสช้าและไม่เสถียรบนเครื่องอื่น ไฟล์นี้จึงบางที่สุดเท่าที่ทำได้ (ไม่มีตรรกะคำนวณ) และพิสูจน์ด้วยสองทาง:

1. สคริปต์วัดใน `backend/scripts/` (ใช้ค่าตั้งชุดเดียวกัน)
2. `GET /symptom-search/status` ตอนรันจริง (ขั้น 1.7 และ 1.11)

ส่วนตรรกะที่ต้องเทสจริงอยู่ใน `symptom-matcher.ts` ซึ่งเทสด้วยเวกเตอร์ปลอมแล้ว (19 เคส)

### 1.5 สิ่งที่ตรวจไว้ตอนเขียน (ไม่ใช่ผลวัดทางวิชาการ)

คอมไพล์แล้วโหลดโมเดลจริงจากไฟล์ใน git ได้ 384 มิติ และ `modelFilesFoundLocally = true` เป็นแค่การเช็กว่าไฟล์ทำงาน **ห้ามอ้างเป็นผลวัดความแม่นยำหรือหน่วยความจำ** ตัวเลขหน่วยความจำบน Render ต้องวัดจริงในขั้น 1.11

## ส่วนที่ 2 — `symptom-search.dto.ts` (ขั้น 1.5)

### 2.1 หน้าที่

| ส่วน | รายละเอียด |
|---|---|
| `parseSearchBody(body)` | ตัวตรวจ body ของ `POST /symptom-search` |
| `InvalidSearchQueryError` | error ของเราเอง (ให้ filter จับด้วย `instanceof`) แปลงเป็น 400 `INVALID_QUERY` ในขั้น 1.7 |
| `SymptomMatchDto`, `SymptomSearchResponseDto` | รูปร่างผลค้นหา |
| `SearchStatusDto`, `SearchState` | รูปร่างของ `GET /symptom-search/status` |

ไฟล์นี้บริสุทธิ์เหมือน `traversal.dto.ts`: ไม่ import NestJS ไม่แตะโมเดลหรือฐานข้อมูล เทสได้เร็ว

### 2.2 ทำไมเขียนตัวตรวจเอง ไม่ใช้ class-validator

body มี field เดียว (`query`) เขียนเป็นฟังก์ชันธรรมดาแล้วอธิบายได้ทุกบรรทัด ไม่ต้องลงแพ็กเกจเพิ่ม ไม่ต้องอธิบาย decorator ซึ่งเป็นแนวเดียวกับที่ใช้ใน `traversal.dto.ts`

### 2.3 `parseSearchBody` ตรวจอะไรบ้าง (ตามลำดับ)

| ลำดับ | เงื่อนไข | ผล |
|---|---|---|
| 1 | body เป็น `null`, array, ข้อความ, ตัวเลข หรือไม่มี | โยน error (ต้องเช็ก `null` และ array แยก เพราะ `typeof null === 'object'`) |
| 2 | `query` ไม่ใช่ข้อความ | โยน error |
| 3 | `query` ว่าง หรือมีแต่ช่องว่าง (หลังตัดช่องว่างหน้าหลัง) | โยน error |
| 4 | `query` ยาวเกิน `MAX_QUERY_LENGTH` (200) | โยน error |
| 5 | ผ่านทั้งหมด | คืน object ใหม่ `{ query }` เฉพาะ field ที่รู้จัก field แปลกปลอมถูกทิ้ง |

### 2.4 ทำไมจำกัดที่ 200 ตัวอักษร

ทุกคำค้นถูกส่งเข้าโมเดลบนเซิร์ฟเวอร์ที่มี 0.1 CPU ถ้าไม่จำกัด ผู้ใช้ส่งข้อความยาวมากมาแล้วทำให้เซิร์ฟเวอร์ช้าหรือหน่วยความจำพุ่งได้ อาการที่คนพิมพ์จริงสั้นกว่านี้มาก ความยาวนับ **หลังตัดช่องว่าง** (ข้อความ 200 ตัวอักษรที่มีช่องว่างคั่นหน้าหลังยังผ่าน)

> 200 เป็นค่าที่ผมกำหนดเพื่อกันการใช้ทรัพยากรเกินจำเป็น **ไม่ได้มาจากการวัด** ไม่ควรอ้างว่ามีที่มาทางวิชาการ

### 2.5 การตัดสินใจเล็กๆ ที่ควรรู้

| เรื่อง | ทำอย่างไร | เหตุผล |
|---|---|---|
| `bestScore` | ชนิด `number \| null` (`null` = ไม่มีผังให้เทียบเลย) | ถ้าใช้ 0 จะปนกับกรณีที่คะแนนต่ำจริง |
| `score` ใน response | ปัดทศนิยม 3 ตำแหน่งตอนส่งออก แต่เทียบเกณฑ์ด้วยค่าเต็ม | อ่านง่ายโดยไม่ทำให้ผลตัดสินเพี้ยน (ทำใน service ขั้น 1.6) |
| `SearchState` | `disabled \| loading \| ready \| failed` | `disabled` คือปิดสวิตช์ไว้ ต่างจาก `failed` ที่พยายามโหลดแล้วล้มเหลว |
| ผังที่ไม่ผ่านเกณฑ์ | `matches` ว่าง | หน้าจอต้องแสดงการส่งต่อศูนย์บริการ Samsung **ห้ามเดา** |

### 2.6 ข้อควรระวังทางวิชาการ

- `score` คือ cosine ไม่ใช่ความน่าจะเป็น หน้าจอเรียกว่า **"คะแนนความคล้าย"** ห้ามแสดงเป็น "มั่นใจ x%"
- ผลของขั้นนี้คือการเทสตัวตรวจ body ไม่ใช่ผลวัดคุณภาพการค้นหา

## ส่วนที่ 4 — ภาพรวมว่าไฟล์ทั้งหมดต่อกันอย่างไร

```
POST /symptom-search { query }
   │
   ▼  (ขั้น 1.7) controller ส่ง body ต่อ ไม่มีตรรกะเอง
symptom-search.dto.ts       parseSearchBody   ← ขั้น 1.5 (เอกสารนี้)
   │
   ▼  (ขั้น 1.6) service
embedding.service.ts        embed(query)      ← ขั้น 1.4 (เอกสารนี้)
   │  เวกเตอร์ 384 มิติ
   ▼
symptom-matcher.ts          rankGraphs → selectMatches   ← ขั้น 1.3 (เอกสาร 06)
   │
   ▼
SymptomSearchResponseDto    { query, threshold, bestScore, matches }
```

หลักการที่ไม่เปลี่ยน: ระบบค้นหามีหน้าที่เลือกว่า **จะเริ่มผังขั้นตอนไหน** เท่านั้น และผู้ใช้ต้องยืนยันเอง ส่วนการตัดสินว่าขั้นถัดไปภายในผังคืออะไรยังเป็นของเครื่องสถานะทั้งหมด
