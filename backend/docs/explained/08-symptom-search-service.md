## 2. โครงสร้างของ service

```
constructor(EmbeddingService, GraphRepository)

onApplicationBootstrap()   ← NestJS เรียกตอนแอปบูตเสร็จ (คืน void)
   └─ ถ้า SYMPTOM_SEARCH_ENABLED === 'true' → prepareIndex() แบบไม่รอ

prepareIndex()             ← โหลดโมเดล + สร้างดัชนีในหน่วยความจำ (ไม่โยน error)
search(query)              ← ค้นหา
getStatus()                ← รายงานสถานะ
```

### 2.1 สถานะ 4 แบบ

| สถานะ | ความหมาย | `search()` ได้ผล |
|---|---|---|
| `disabled` | ไม่ได้เปิดสวิตช์ (ค่าเริ่มต้น) | โยน `SearchUnavailableError` |
| `loading` | กำลังโหลดโมเดลและสร้างดัชนี | โยน `SearchNotReadyError` |
| `ready` | พร้อมค้นหา | คืนผลค้นหา |
| `failed` | พยายามโหลดแล้วล้มเหลว | โยน `SearchUnavailableError` |

ความต่างของสอง error: `NotReady` แปลว่าลองใหม่ภายหลังได้ ส่วน `Unavailable` แปลว่าตอนนี้ไม่มีทางใช้ได้ (ขั้น 1.7 แปลงเป็น 503 `SEARCH_NOT_READY` และ 503 `SEARCH_UNAVAILABLE` ตามลำดับ)

## 3. การตัดสินใจสำคัญและเหตุผล

### 3.1 `onApplicationBootstrap()` คืน `void` ไม่ใช่ Promise

ถ้าคืน Promise NestJS จะ **รอให้โหลดโมเดลเสร็จก่อนเปิดรับ request** บน Render free (0.1 CPU) การโหลดอาจนานมาก ระหว่างนั้น `/health` และ **ด่านความปลอดภัยจะตอบไม่ได้** ทั้งที่สองส่วนนี้ไม่เกี่ยวกับการค้นหาเลย

จึงสั่งโหลดแบบไม่รอ (`void this.prepareIndex()`) แล้วให้ `GET /symptom-search/status` บอกความคืบหน้าแทน มีเทสยืนยันว่าเมธอดคืน `undefined` ทันทีและสถานะเป็น `loading`

### 3.2 ปิดเป็นค่าเริ่มต้น

ต้องตั้ง `SYMPTOM_SEARCH_ENABLED=true` (ต้องเป็นข้อความ `true` เป๊ะๆ ค่า `1`, `TRUE`, `yes` ไม่นับ) จึงโหลดโมเดล เหตุผล: ถ้าหน่วยความจำเกินแล้วเซิร์ฟเวอร์ล่ม จะล่มทั้งตัวรวมถึงส่วนที่ทำงานอยู่ได้ดี การมีสวิตช์ทำให้ **แก้ได้ด้วยการปิดสวิตช์** โดยไม่ต้องแก้โค้ด

### 3.3 `prepareIndex()` ไม่โยน error ออกมา

ถ้าโหลดล้มเหลว จับ error แล้วตั้งสถานะ `failed` พร้อมเก็บข้อความไว้ให้ `/status` แสดง ระบบค้นหาพัง **ไม่ควรทำให้ส่วนอื่นพังตาม** หน้าเลือกอาการแบบเดิม (13 อาการ) ยังใช้ได้เสมอ

### 3.4 เวกเตอร์คำนวณใหม่ในหน่วยความจำทุกครั้งที่เปิดเซิร์ฟเวอร์

เดิมเสนอให้เก็บเวกเตอร์ในตาราง `graph_embeddings` แต่ **ตารางนี้ไม่มีอยู่จริง** (migration 001–003 ไม่ได้สร้าง; PROJECT_CONTEXT §5 ระบุผิด) จึงเลือกคำนวณสดโดย:

- ไม่ต้องแก้ schema
- รับประกันว่าเวกเตอร์ของอาการกับของคำค้นมาจากโมเดลตัวเดียวกันเสมอ
- MySQL 8.4 ไม่มีชนิด `VECTOR` / `DISTANCE()` อยู่แล้ว จึงต้องคำนวณ similarity ในโค้ดเอง

ข้อความตัวแทนมี 36 ข้อความจาก 13 ผัง ถ้าเพิ่มครบ 4 เครื่องแล้วเริ่มช้า ค่อยย้ายเวกเตอร์ไปเก็บในตาราง

> ผลข้างเคียงที่ต้องรู้: ทุกครั้งที่ Render ปลุกเซิร์ฟเวอร์ที่หลับอยู่ ต้องโหลดโมเดลและ embed 36 ข้อความใหม่ ช่วงนั้นสถานะเป็น `loading` (ยังไม่เคยวัดบน Render จริง)

### 3.5 ใช้ `findById()` ต่อจาก `listAll()`

`listAll()` คืน `GraphSummary` ซึ่งไม่มีคำพ้อง (`entry_symptom_aliases`) จึงวนเอารหัสผังจาก `listAll()` แล้วเรียก `findById()` เพื่อได้ผังเต็ม ผังทั้งหมดอยู่ในหน่วยความจำอยู่แล้ว จึงไม่ยิง SQL เพิ่ม

### 3.6 ปัดคะแนนตอนส่งออก แต่เทียบเกณฑ์ด้วยค่าเต็ม

`score` ในผลลัพธ์ปัด 3 ตำแหน่ง (อ่านง่าย) แต่การตัดสินว่าผ่านเกณฑ์ใช้ค่าเต็ม เพื่อไม่ให้ผังที่ได้ 0.4996 ถูกปัดเป็น 0.500 แล้วดูเหมือนผ่านเกณฑ์ ทั้งที่ไม่ผ่าน (มีเทสยืนยันการปัด 0.7071… เป็น 0.707)

### 3.7 `bestScore` ส่งเสมอ

ส่งแม้ไม่มีผังผ่านเกณฑ์ เพื่อให้ขั้น 1.9 (ตั้งเกณฑ์) เห็นว่าคำค้นที่พลาดนั้นใกล้เกณฑ์แค่ไหน เป็น `null` เฉพาะกรณีไม่มีผังให้เทียบเลย

## 5. เทส (`symptom-search.service.spec.ts`, 10 เคส)

### วิธีเทส

- **ตัวแปลงข้อความปลอมแบบ one-hot:** ข้อความตัวแทนลำดับที่ i ได้เวกเตอร์ที่มี 1 ในมิติ i ค้นด้วยข้อความตัวแทนตรงๆ จึงได้คะแนน **1** กับผังของมัน และ **0** กับผังอื่น สองค่านี้ไม่ขึ้นกับเกณฑ์ที่จะปรับภายหลัง
- **`GraphRepository` ปลอม** สร้างจากไฟล์ผังแอร์จริง 13 ชุด
- ไม่โหลดโมเดล ไม่ต่อ MySQL

| # | เคส | สิ่งที่พิสูจน์ |
|---|---|---|
| 1 | `prepareIndex` | ดัชนี 36 ข้อความ จาก 13 ผัง สถานะ `ready` |
| 2 | ค้นด้วยข้อความตัวแทน | ผังนั้นอันดับ 1 คะแนน 1 ข้อมูลครบทุก field |
| 3 | คำค้นที่ไม่ตรงผังไหน | `matches` ว่าง `bestScore` เป็น 0 |
| 4 | ปัดเศษ | เวกเตอร์ 2 มิติ ได้ 0.7071… ส่งออก 0.707 |
| 5 | ค้นตอนกำลังโหลด | `SearchNotReadyError` |
| 6 | ค้นตอนปิดสวิตช์ | `SearchUnavailableError` |
| 7 | โหลดโมเดลล้มเหลว | `prepareIndex` ไม่โยน error, สถานะ `failed`, เก็บข้อความ error |
| 8 | bootstrap ตอนไม่เปิดสวิตช์ | ไม่เรียก `load()` สถานะ `disabled` |
| 9 | bootstrap ตอนเปิดสวิตช์ | คืน `undefined` ทันที สถานะ `loading` แล้วเป็น `ready` |
| 10 | ค่าตัวแปรที่ไม่ใช่ `true` เป๊ะๆ | `1`, `TRUE`, `yes`, ข้อความว่าง ถือว่าปิด |

### การทดสอบเชิงลบ

หลังเขียนเสร็จ ผมแก้ service ให้ผิดชั่วคราวสองแบบเพื่อดูว่าเทสจับได้จริง: (ก) ทำให้ `onApplicationBootstrap` เป็น async → เคสที่ 8 และ 9 ล้ม (ข) เอาการปัดเศษออก → เคสที่ 4 ล้ม แล้วคืนโค้ดกลับก่อนส่งมอบ

รวมทั้ง backend หลังขั้นนี้: **6 suites, 131 เทสผ่าน** (เดิม 92 + ขั้น 1.3 อีก 19 + ขั้น 1.5 อีก 10 + ขั้น 1.6 อีก 10)
