# ขั้น 1.9.1–1.9.2 — ชุดคำค้นสำหรับวัดผล และสคริปต์วัดผลการค้นหาอาการ

ขั้น 1.9 มีเป้าหมายสองอย่าง: วัดว่าการค้นหาอาการด้วยภาษาธรรมชาติจับคู่ผังขั้นตอนได้ดีแค่ไหน และตั้งค่าเกณฑ์ `MATCH_THRESHOLD` จากการวัด แทนค่าชั่วคราว 0.5 เดิม เอกสารนี้อธิบายสองขั้นย่อยแรก คือเครื่องมือกับกติกา ส่วนผลวัดและเกณฑ์ที่เลือก (0.55) อยู่ในเอกสาร 11

> **ศัพท์:** เอกสารนี้ใช้คำว่า เครื่องสถานะ / สถานะ ตาม PROJECT_CONTEXT ข้อ 3
> ชื่อในโค้ดยังคงเดิม: **`graph` ในโค้ด = ผังขั้นตอนการวินิจฉัย 1 อาการ (เครื่องสถานะ 1 ชุด)**
> เช่น `expected_graph_id` = รหัสผังขั้นตอนที่คาดว่าควรได้

| ไฟล์ | หน้าที่ |
|---|---|
| `data/eval/README.md` | คู่มือเขียนคำค้น: กติกา ขนาดที่แนะนำ รูปแบบไฟล์ รหัสผัง 13 ชุด |
| `data/eval/queries_tuning.json` | ชุดตั้งเกณฑ์ 56 ข้อ **ร่างโดย Claude (ผู้ช่วย AI) ผู้พัฒนายังไม่ได้ตรวจแก้** (ดูหัวข้อ 1) |
| `data/eval/queries_report.json` | ชุดรายงานผล **ยังว่าง 0 ข้อ** ตามแผนจะเก็บจากเพื่อน แล้วผู้พัฒนาติด label และล็อกก่อนวัด |

## 1. ใครเขียนชุดคำค้น (ต้องบอกตรงๆ)

ตอนนี้ระบบค้นหาทำงานได้แล้ว แต่ยังตอบไม่ได้ว่า **ดีแค่ไหน** เกณฑ์ 0.5 เป็นค่าชั่วคราวที่ไม่ได้มาจากการวัด และคำค้นตัวอย่างไม่กี่คำที่เคยลองไม่ใช่ผลวัด (ห้ามอ้าง) จึงต้องมีโจทย์ที่กำหนดล่วงหน้าและจดคำตอบที่ถูกไว้ก่อนรันเสมอ

| ชุด | ใครเขียน | สถานะ |
|---|---|---|
| ชุดตั้งเกณฑ์ | **Claude (ผู้ช่วย AI)** ร่างให้ 56 ข้อ (ในขอบเขต 39 = ผังละ 3 ข้อ · นอกขอบเขต 17) | ฟิลด์ `author` ในไฟล์ระบุไว้ตรงๆ และ `status` เป็น `draft` **ผู้พัฒนายังไม่ได้ตรวจแก้** |
| ชุดรายงานผล | ยังไม่มี (ไฟล์ว่าง 0 ข้อ) | ตามแผนจะเก็บจากเพื่อน แล้วผู้พัฒนาเป็นคนติด label |

**ทำไมเรื่องนี้สำคัญ:** หลักการเดิมคือผู้ช่วยไม่ควรเขียนโจทย์ที่ใช้วัดระบบที่ผู้ช่วยช่วยสร้างเอง เพราะตัวเลขอาจดีเกินจริง ชุดตั้งเกณฑ์ **ไม่ได้เป็นไปตามหลักการนี้** จึงกำหนดการใช้งานไว้ดังนี้

- ชุดตั้งเกณฑ์ใช้ได้เฉพาะ **เลือกค่าเกณฑ์ และดูว่าผังไหนพลาด** ไม่ใช่ตัวเลขที่จะอ้างว่าระบบแม่นแค่ไหน
- ตัวเลขที่จะอ้างในเอกสารและตอนสอบ ต้องมาจากชุดรายงานผลเท่านั้น และชุดนั้นต้องมาจากเพื่อน **ห้ามให้ผู้ช่วยเขียนหรือเห็นก่อนวัด**
- ตอนสอบ ถ้าอาจารย์ถามว่าใครเขียนคำค้น ให้ตอบตามตารางข้างบน ห้ามตอบว่าผู้พัฒนาเขียนเองทั้งหมด
- เมื่อผู้พัฒนาตรวจแก้ชุดตั้งเกณฑ์เสร็จจริง ให้แก้ฟิลด์ `author` และตารางนี้ให้ตรงว่าตรวจแก้อะไรไปบ้าง ก่อนหน้านั้นห้ามเรียกว่าตรวจแล้ว

## 2. ทำไมต้องแยกสองชุด

| ชุด | ใช้ทำอะไร | ดูผลได้กี่รอบ |
|---|---|---|
| **ชุดตั้งเกณฑ์** (`tuning`) | เลือกค่าเกณฑ์, ตรวจว่าผังไหนพลาดแล้วแก้ข้อความตัวแทน | ไม่จำกัด |
| **ชุดรายงานผล** (`report`) | ตัวเลขที่จะอ้างในเอกสารและตอนสอบ | **ควรครั้งเดียว** ตอนท้าย |

ถ้าปรับเกณฑ์และแก้ข้อความตัวแทนโดยดูผลจากชุดเดียวกับที่ใช้รายงาน ระบบจะถูกปรับให้เข้ากับโจทย์ชุดนั้นเอง ตัวเลขจะดีเกินจริง เป็นการประเมินวนกลับหาตัวเอง แบบเดียวกับกฎของ 13 ผังแอร์ที่ใช้เทรนตัวจำแนกสถานะ

## 3. กติกาของชุดคำค้น

ตัวตรวจ (`validate-eval-queries.js`) บังคับกติกาเหล่านี้ให้ตั้งแต่ก่อนวัด:

| ประเภท | กติกา |
|---|---|
| **ข้อผิดพลาด** (ทำให้ล้ม) | JSON ผิดไวยากรณ์ · `set` ไม่ตรงชื่อไฟล์ · `status` ไม่ใช่ `draft`/`frozen` · `id` ซ้ำ · ยาวเกิน 200 ตัวอักษร · `category`/`style`/`kind` ผิดค่า · `expected_graph_id` ไม่มีในผังจริง (หรือไม่ใช่ `null` เมื่อนอกขอบเขต) · **คำค้นซ้ำกัน (รวมข้ามสองชุด)** · **คำค้นเหมือนข้อความตัวแทนของผังทุกตัวอักษร** |
| **คำเตือน** | ยังไม่กรอก `author` · น้อยกว่า 40 ข้อต่อชุด · ผังไหนมีน้อยกว่า 2 ข้อ · นอกขอบเขตน้อยกว่า 30% · คำค้นมีข้อความตัวแทนของผังอยู่ทั้งก้อน |

เหตุผลที่ห้ามซ้ำกับข้อความตัวแทน: ข้อความตัวแทนอยู่ในดัชนีอยู่แล้ว คำค้นที่เหมือนกันทุกตัวอักษรจะได้คะแนน 1.0 เสมอ ทำให้ผลดีเกินจริง

**ชนิดของคำค้น**

| `category` | ความหมาย | ฟิลด์เพิ่ม |
|---|---|---|
| `in_scope` | ควรได้ผังใดผังหนึ่ง | `expected_graph_id` เป็น id จริง · `style`: `colloquial`, `formal`, `english`, `typo_or_abbrev`, `vague` |
| `out_of_scope` | ระบบควรตอบว่าไม่มีผังที่ตรง แล้วส่งต่อศูนย์บริการ | `expected_graph_id: null` · `kind`: `other_appliance`, `ac_outside_manual`, `unrelated` |

ตัดสินว่า "ในขอบเขต" จากสิ่งที่คู่มือแอร์ AR70H ส่วนแก้ปัญหา (หน้า 43–44) ครอบคลุมเท่านั้น ไม่ใช่จากความรู้ทั่วไปว่าแอร์เสียได้เพราะอะไร เช่น "น้ำยาแอร์หมด" คู่มือส่วนนี้ไม่ได้สอนให้ผู้ใช้แก้เอง จึงเป็น `ac_outside_manual`

**ขนาดที่แนะนำต่อชุด:** อย่างน้อย 40 ข้อ, ทุกผังอย่างน้อย 2 ข้อ (26 ข้อขึ้นไป), นอกขอบเขตอย่างน้อย 30% จำนวนระดับนี้ทำให้ตัวเลขมีความไม่แน่นอนสูง ตอนรายงานให้เขียนเป็น "ถูก x จาก n ข้อ" ไม่ใช่เปอร์เซ็นต์อย่างเดียว

## 4. สคริปต์วัดผล (`eval-symptom-search.js`)

### 4.1 ใช้โค้ดชุดเดียวกับเซิร์ฟเวอร์จริง

สคริปต์เรียก `EmbeddingService`, `buildSymptomTexts`, `rankGraphs` และ `selectMatches` จากโฟลเดอร์ `dist/` (ต้อง `npm run build` ก่อน) จึงวัดของจริง ไม่ใช่ตัวเลียนแบบ ต่างจากเซิร์ฟเวอร์ข้อเดียว: อ่านผังจากไฟล์ `data/manuals/samsung_ac_ar70h.json` โดยตรง ซึ่งเป็นข้อมูลเดียวกับที่ `npm run seed` นำเข้า MySQL จึงไม่ต้องต่อฐานข้อมูล

### 4.2 สิ่งที่รายงาน

| ส่วน | ให้ข้อมูลอะไร |
|---|---|
| **ผลที่ไม่ขึ้นกับเกณฑ์** | ผังที่ถูกอยู่อันดับ 1 กี่ข้อ, อยู่ใน 3 อันดับแรกกี่ข้อ (แยกตาม `style`) |
| **การกระจายคะแนนสูงสุด** | ช่วงคะแนนของคำค้นนอกขอบเขต (แยกตาม `kind`) เทียบกับของคำค้นในขอบเขตที่ได้ผังถูกอันดับ 1 ถ้าซ้อนทับกันจะเตือนว่าไม่มีเกณฑ์เดียวที่แยกได้หมด |
| **ตารางกวาดเกณฑ์** | ทุกเกณฑ์ (ค่าเริ่มต้น 0.30–0.90 ทีละ 0.05): ในขอบเขตกี่ข้อผ่านเกณฑ์/ถูกปฏิเสธ, ผังถูกอันดับ 1 กี่ข้อในที่ผ่านเกณฑ์, ผังถูกอยู่ใน 3 อันดับกี่ข้อ, นอกขอบเขตปฏิเสธถูกกี่ข้อ |
| **รายข้อที่ต้องดู** | ผังถูกไม่ได้อยู่อันดับ 1 (พร้อมอันดับจริงและคะแนน 3 อันดับแรก), ในขอบเขตที่ถูกปฏิเสธ, นอกขอบเขตที่หลุดผ่านเกณฑ์ |

ความหมายของการเลือกเกณฑ์ มีต้นทุนสองด้านที่ขัดกัน:

- **เกณฑ์สูงเกินไป:** คำค้นที่ควรได้ผังถูกปฏิเสธ (ผู้ใช้ถูกส่งต่อศูนย์บริการทั้งที่มีขั้นตอนให้ทำเอง)
- **เกณฑ์ต่ำเกินไป:** คำค้นนอกขอบเขตหลุดผ่าน (ระบบเสนอผังที่ไม่เกี่ยว)

สคริปต์ไม่เลือกเกณฑ์ให้ แค่แสดงตัวเลขและชี้ว่าเกณฑ์ต่ำสุดที่ไม่มีคำค้นนอกขอบเขตหลุดผ่านคือเท่าไรในกริดนั้น การตัดสินใจอยู่ที่ขั้น 1.9.3–1.9.4

### 4.3 การล็อกชุดรายงานผลด้วยโค้ด

รัน `--set report` ได้ก็ต่อเมื่อทุกข้อต่อไปนี้เป็นจริง:

| เงื่อนไข | ทำไม |
|---|---|
| ไฟล์เป็น `"status": "frozen"` | ยืนยันว่าเขียนเสร็จแล้ว ไม่แก้ตามผล |
| ผ่านตัวตรวจแบบ `--strict` ทั้งสองไฟล์ | ไม่มีทั้งข้อผิดพลาดและคำเตือน |
| ระบุ `--threshold` เอง | ไม่กวาดเกณฑ์บนชุดนี้ เกณฑ์ต้องเลือกมาจากชุดตั้งเกณฑ์เท่านั้น |

ทุกครั้งที่รันชุดรายงานผลจะบันทึกหนึ่งบรรทัดลง `data/eval/report_runs.jsonl` (เวลา ผู้เขียน เกณฑ์ จำนวนข้อ ผลสรุป) เพื่อให้ **จำนวนครั้งที่รันเป็นหลักฐานตรวจสอบได้** ใช้นามสกุล `.jsonl` เพราะ `.gitignore` กันไฟล์ `*.log` ไว้

กลไกเหล่านี้กันได้แค่บางส่วน ส่วนที่สำคัญที่สุดเป็นวินัยของผู้พัฒนา: **ห้ามนำรายข้อที่พลาดในชุดรายงานผลไปแก้ระบบ** ถ้าแก้ ชุดนั้นใช้รายงานผลไม่ได้อีก

## 6. หมายเหตุ: การแก้ `tsconfig.json`

ระหว่างเตรียม `npm run build` (จำเป็นสำหรับสคริปต์วัดผล) พบ error `TS5103: Invalid value for '--ignoreDeprecations'` บนเครื่องผู้พัฒนา จึงแก้ `backend/tsconfig.json` โดยเอา `"baseUrl": "./"` และ `"ignoreDeprecations": "5.0"` ออก

- โค้ดทุกไฟล์ใช้ import แบบ relative ไม่พึ่ง `baseUrl`
- `"ignoreDeprecations"` เป็นค่าผูกเวอร์ชัน (`"5.0"` สำหรับ TypeScript 5, `"6.0"` สำหรับ 6) ใส่ผิดเวอร์ชันแล้ว build ล้ม จึงเอาออกดีกว่า
- ทดสอบแล้วว่า `tsc --noEmit` ผ่านกับ TypeScript 5.0.4, 5.8.3, 6.0.2, 6.0.3 และ 7.0.2 และ `nest build` ผ่านกับ 5.9.3 (เวอร์ชันของ lockfile) และ 6.0.3
- ⚠️ ยังไม่ได้ยืนยันว่า error ของเครื่องผู้พัฒนาหายเพราะการแก้นี้: ทำ error `TS5103` ให้เกิดซ้ำในแซนด์บ็อกซ์ไม่ได้ ต้องดูผล `npm run build` บนเครื่องผู้พัฒนา
