# ขั้น 1.2.2 — ตัดตารางคำศัพท์ของโมเดล

## 1. ทำอะไร และทำไม

ขั้น 1.1 วัดได้ว่าโมเดลใช้หน่วยความจำสูงสุดราว 440–456 MB เกินงบของ Render free และปรับค่าตั้งของ ONNX Runtime ไม่ช่วย ขั้น 1.2.1 สำรวจพบว่าตารางคำศัพท์ 250,037 แถว (`uint8`, 91.6 MiB) เป็น 81% ของไฟล์ และมีเพียง node `Gather` ตัวเดียวที่ใช้ตารางนี้

ระบบเราใช้แค่ภาษาไทยกับอังกฤษ จึงตัดแถวของ token ภาษาอื่นออก เหลือ 87,519 แถว (35%) โดยไม่แตะน้ำหนักส่วนอื่นของโมเดล

**สคริปต์นี้อ่านโมเดลต้นฉบับใน `backend/model-cache/` แต่ไม่แก้ไฟล์ต้นฉบับเลย** ผลเขียนลง `backend/model-slim/` ในโครงสร้างโฟลเดอร์เดียวกัน ลบทิ้งแล้วรันใหม่ได้เสมอ

## 2. สิ่งที่สคริปต์ทำ (เรียงตามลำดับ)

| ขั้น | ทำอะไร |
|---|---|
| 1 | เลือก token ที่เก็บ ด้วยกฎเดียวกับ `inspect_vocab.py` (import มาใช้ ไม่ลอกซ้ำ) บวก token พิเศษทุกตัว |
| 2 | เรียง token ที่เก็บตาม id เดิม แล้วให้ id ใหม่เรียง 0, 1, 2, … แถวที่ i ของตารางใหม่ = แถว `kept[i]` ของตารางเดิม |
| 3 | ตัดแถวของตารางในไฟล์ ONNX แล้วโหลดไฟล์ที่เขียนกลับมาเทียบ: โครงกราฟและน้ำหนักอื่นต้องเหมือนต้นฉบับทุกไบต์ |
| 4 | เขียน `tokenizer.json`, `config.json`, `tokenizer_config.json` ใหม่ให้ id ตรงกับตารางใหม่ และคัดลอก `special_tokens_map.json` |
| 5 | ตรวจตัวเอง (ดูหัวข้อ 4) |

**ทำไมเรียงตาม id เดิม:** token พิเศษ `<s>`=0, `<pad>`=1, `</s>`=2, `<unk>`=3 ถูกเก็บทั้งหมดและเป็น id ที่ต่ำที่สุด id ของมันจึงไม่เปลี่ยน สคริปต์ตรวจเรื่องนี้ด้วย เพราะกราฟของโมเดลอาจอ้าง id เหล่านี้ตรงๆ (เช่น id ของ `<pad>`) ส่วน `<mask>` ที่เคยเป็น id 250,001 จะได้ id ท้ายสุดแทน (ระบบไม่ใช้ `<mask>`)

## 3. ทำไมผลลัพธ์ของโมเดลจึงไม่เปลี่ยน

ตัวตัดคำเลือกได้เฉพาะ token ที่เป็นส่วนหนึ่งของข้อความ ข้อความที่มีแต่ตัวอักษรในชุดที่อนุญาต (ไทย, ASCII, เครื่องหมายทั่วไป) จึงไม่มีทางได้ token ที่ถูกตัด การตัดคำจึงเหมือนเดิม และโมเดลได้รับแถวจากตารางชุดเดียวกับเดิม น้ำหนักส่วนอื่นเหมือนเดิมทุกไบต์ ผลลัพธ์จึงต้องเท่าเดิม

## 4. การตรวจตัวเอง

สำหรับแต่ละข้อความ สคริปต์ตัดคำด้วยตัวตัดคำเดิมและตัวใหม่ แล้วเช็กสองอย่าง:

1. token เหมือนกัน
2. แถวที่ดึงจากตารางเดิมด้วย id เดิม **เหมือนทุกไบต์** กับแถวที่ดึงจากตารางใหม่ด้วย id ใหม่

| ชุดข้อความ | ผลที่ไม่ผ่านหมายถึง |
|---|---|
| **ข้อความที่ใช้ค้นหา** 43 ข้อความ (ข้อความตัวแทนของ 13 ผัง + คำค้นตัวอย่าง) | สคริปต์หยุดด้วย exit code 1 และห้ามใช้ `model-slim/` |
| ข้อความในสถานะทุกตัว (ไม่ได้ใช้ค้นหา) | แค่รายงาน ใช้ดูขอบเขตเพิ่มเติม ไม่ทำให้สคริปต์ล้ม |

สุดท้ายสคริปต์พิมพ์ตัวอย่าง "café 中文" เทียบ id ก่อนและหลังตัด เพื่อให้เห็นพฤติกรรมของตัวอักษรนอกชุด ซึ่งกลายเป็น `<unk>` (id 3)

## 5. วิธีรัน

ยืนที่ **รากของ repo**

```powershell
py -3.12 scripts/slim_model.py
```

- ต้องมี `inspect_vocab.py` อยู่ใน `scripts/` เดียวกัน (สคริปต์นี้ import กฎการเก็บ token มาจากไฟล์นั้น)
- ต้องมีโมเดลใน `backend/model-cache/` จากขั้น 1.1
- ไม่ต้องติดตั้งไลบรารีเพิ่ม (`onnx`, `numpy`, `tokenizers` มีแล้วใน Python 3.12 ตัวนี้)
- ก่อนรัน ให้เพิ่ม `model-slim/` ใน `backend/.gitignore` (ไฟล์ที่ส่งมาให้มีแล้ว)

## 6. ตัวเลขที่ควรเห็น

| รายการ | ค่าที่คาด |
|---|---|
| เก็บ token | **87,519** จาก 250,002 (ต้องเท่ากับขั้น 1.2.1) |
| id ของ `<mask>` | 250,001 → 87,518 |
| ตารางคำศัพท์ | [250037, 384] → [87519, 384] (91.6 → 32.1 MiB) |
| ไฟล์ ONNX | 112.8 → ราว 53 MiB |
| ข้อความที่ใช้ค้นหา | ไม่ผ่าน **0** จาก 43 |
| ข้อความในสถานะ | คาดว่าต่างไป 0 (ตัวอักษรทุกตัวในข้อความของ 13 ผังอยู่ในชุดที่อนุญาต แต่ตัวตัดคำมีขั้น normalize ก่อนตัดคำ จึงยังเป็นแค่ข้อคาดการณ์ ไม่ใช่ข้อรับประกัน) |

## 7. สิ่งที่ยังไม่ได้พิสูจน์

- สคริปต์ทดสอบกับโมเดลจำลอง (โครงสร้างเหมือนของจริง: `Gather` → `DequantizeLinear`, ตาราง `uint8` ที่มีแถวเกินตัวตัดคำ 35 แถว, `tokenizer.json` ที่สร้างด้วยไลบรารีเดียวกัน) รันจริงด้วย ONNX Runtime กับข้อความ 3,134 ข้อความ ผลตรงกันทุกไบต์ และทดสอบด้วยว่าถ้าเลือกแถวผิด การตรวจตัวเองจับได้ แต่โมเดลจริงมีตัว normalize ของตัวตัดคำ (`Precompiled`) และน้ำหนัก 348 ก้อนที่โมเดลจำลองไม่มี
- **หน่วยความจำที่ลดลงยังไม่ทราบ** ไฟล์เล็กลงราว 60 MiB แต่ขั้น 1.1 วัดได้ว่าหน่วยความจำเพิ่มราว 3.4 เท่าของไฟล์ ยังไม่รู้สาเหตุ ต้องวัดจริงในขั้น 1.2.4
- ขั้น 1.2.3 จะยืนยันกับโมเดลจริงด้วยตัวเลข cosine ระหว่างเวกเตอร์ของโมเดลเดิมและโมเดลที่ตัดแล้ว
