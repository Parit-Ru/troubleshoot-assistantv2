# ขั้น 1.11 — เตรียมและขึ้น deploy ระบบค้นหาอาการ

เอกสารนี้เป็นคู่มือขึ้น deploy ระบบค้นหาอาการบน Render (แผนฟรี หน่วยความจำ 512 MB) แบบสองจังหวะ และบันทึกผลการซ้อมที่ทำในเครื่องก่อนขึ้นจริง **ผลจริงบน Render ยังไม่มี** ส่วนท้ายเอกสาร (หัวข้อ 8) เว้นไว้ให้กรอกหลังวัดแล้ว

> **ศัพท์:** เครื่องสถานะ / สถานะ ตาม PROJECT_CONTEXT ข้อ 3 · ชื่อในโค้ดคงเดิม
> **จังหวะ ก** = ขึ้นโค้ดใหม่โดยปิดระบบค้นหา · **จังหวะ ข** = เปิดสวิตช์ `SYMPTOM_SEARCH_ENABLED`

| ไฟล์ | หน้าที่ |
|---|---|
| `backend/scripts/check-deployed-search.js` | ตรวจสถานะระบบค้นหาบนเซิร์ฟเวอร์ที่ deploy แล้ว ยิงคำค้น และวัด `memoryRssMb` (ไม่สร้าง session ไม่เขียนฐานข้อมูล) |
| `backend/.env.example` | เพิ่ม `SYMPTOM_SEARCH_ENABLED=false` และหมายเหตุ `ONNXRUNTIME_NODE_INSTALL` (ของขั้น 1.7 ที่ไม่เคยเข้า commit) |

## 2. ผลซ้อมในเครื่อง (ไม่ใช่ผลจาก Render)

ซ้อมจาก **clean checkout ของ commit `0f3d0aa` (`add frontend sysptom-search`)** (ตอนซ้อม hash คือ `dea31b3` ก่อนเขียนประวัติ git ใหม่ ตรวจแล้วว่าเนื้อไฟล์เหมือนกันทุกไฟล์) (ดึงด้วย `git archive` เฉพาะไฟล์ที่อยู่ใน git) ติดตั้งด้วย `npm ci` ตั้ง `ONNXRUNTIME_NODE_INSTALL=skip` รันด้วย `NODE_ENV=production` ต่อฐานข้อมูล Aiven จริงแบบอ่านอย่างเดียว บน Windows + Node v22.17.0

| รายการ | ผล |
|---|---|
| `npm ci` / `npm run build` | ผ่านทั้งคู่ (111 วินาที / 55 วินาที) · `node_modules` 598 MB · ไฟล์ CPU ของ Linux (`libonnxruntime.so.1`) มีครบ |
| บูตจนถึง `/health` ตอบ | 4–8 วินาที ทั้งโหมด development และ production |
| ปิดสวิตช์ | `state=disabled` · `memoryRssMb` 74–75 · ค้นหาตอบ 503 `SEARCH_UNAVAILABLE` · `GET /traversal/graphs` ได้ 13 ผัง |
| เปิดสวิตช์ | โหลดโมเดล 2.4–2.9 วินาที · `memoryRssMb` 283–304 · `modelFilesFoundLocally=true` |
| ยิงคำค้น 30 ครั้ง | ตอบ median 22 ms, max 62 ms · ไม่มีครั้งที่ล้มเหลว |
| ยิงพร้อมกัน 5 ตัว | `/health` ยังตอบ 200 ใน 128 ms (ระหว่างคำนวณเซิร์ฟเวอร์ไม่ค้าง) |
| ยิงต่อเนื่อง 1,000 ครั้ง | `memoryRssMb` 304 → 318 อัตราเพิ่มช้าลงเรื่อยๆ (+1–2 MB ต่อ 100 ครั้ง) |

**เรื่องหน่วยความจำเพิ่มขึ้น (ตรวจแล้วว่าไม่ใช่การรั่ว):** ตอนเห็นตัวเลขขยับหลังยิง 30 ครั้ง ผู้ตรวจสงสัยว่ารั่ว จึงทดลองแยก ยิงเฉพาะส่วน embedding 2,000 ครั้ง (คำค้นหลากหลาย ทำซ้ำสองรอบต่อแบบ) พบว่าหน่วยความจำขึ้นช่วง ~750 ครั้งแรก (233 → 291 MB) แล้ว **นิ่งที่ ~292 MB** และการ dispose tensor ผลลัพธ์ไม่ทำให้ต่างกัน จึงไม่แก้โค้ด คาดว่าค่าจริงทั้งเซิร์ฟเวอร์นิ่งราว 300–320 MB **บนเครื่องนี้** (ส่วนเกินที่ยังเห็นตอนยิงผ่าน HTTP 1,000 ครั้งอาจเป็นช่วงที่ยังไม่นิ่ง หรือส่วนของ Nest/HTTP ยังไม่ได้พิสูจน์)

**ข้อควรระวังเรื่องตัวเลขซ้อม:** รอบแรกหลังติดตั้งใหม่ เซิร์ฟเวอร์ใช้ 37 วินาทีกว่า `/health` จะตอบ และโหลดโมเดล 39.5 วินาที ทั้งที่รอบหลังๆ ใช้ 4–8 และ 2.9 วินาที ไม่ทราบสาเหตุแน่ชัด (สงสัยว่าเครื่องกำลังสแกนไฟล์ที่เพิ่งติดตั้ง แต่พิสูจน์ไม่ได้) จึงทิ้งตัวเลขรอบนั้นและใช้รอบที่ทำซ้ำได้ **ตัวเลขทั้งหมดในหัวข้อนี้มาจาก CPU ของเครื่องผู้พัฒนา ไม่บอกอะไรเกี่ยวกับ Render (0.1 CPU, Linux)**

## 3. สิ่งที่ยังไม่รู้ ณ ตอนเตรียม (ต้องวัดบน Render)

> **อัปเดตหลังวัดจริง (3 ต.ค.):** หน่วยความจำบน Linux/Render และเวลาโหลดโมเดลวัดแล้ว ดูหัวข้อ 8 ส่วนเวลา build, การรีสตาร์ต และพฤติกรรมของหน่วยความจำหลังใช้งานนานๆ ยังไม่ได้ตรวจ ตารางข้างล่างคือสิ่งที่ไม่รู้ ณ ก่อนขึ้น deploy เก็บไว้เป็นประวัติ

| เรื่อง | ทำไมสำคัญ |
|---|---|
| `memoryRssMb` จริงบน Linux/Render | เพดาน 512 MB ตัวเลขที่เคยเห็นมาจากเครื่องอื่น (Windows ~246–306 MB, แซนด์บ็อกซ์ Linux ~283–295 MB) ห้ามอ้างว่าอยู่ในเพดานจนกว่าจะวัด |
| เวลาโหลดโมเดลบน 0.1 CPU | ช่วงโหลด ผู้ใช้เจอ "ระบบค้นหากำลังเริ่มทำงาน" (หน้าจอรองรับแล้ว) และ Render ฟรีหลับบ่อย ทุกครั้งที่ตื่นต้องโหลดใหม่ |
| เวลาและหน่วยความจำของขั้น build บน Render | ครั้งแรกต้องติดตั้ง `@huggingface/transformers` + onnxruntime (`node_modules` 598 MB) |
| ค่าตั้งใน dashboard | Root Directory, Build Command, Start Command, Branch, Auto-Deploy ไม่มีอยู่ใน repo ต้องเทียบกับ `package.json` (`build` = `nest build`, `start:prod` = `node dist/main.js`) |

## 4. ลำดับขั้น (ทำตามลำดับ)

ทุกคำสั่งระบุโฟลเดอร์ที่ต้องยืนอยู่

### ขั้น 0 — ในเครื่อง (ยังไม่กระทบของจริง)
1. commit ไฟล์ของขั้นนี้บน `symptom-search` (ระบุ path ทีละไฟล์ ห้าม `git add .`) แล้ว push: `backend/.env.example`, `backend/scripts/check-deployed-search.js`, `backend/docs/explained/12-deploy-symptom-search.md`
2. รากของ repo: `git status` ต้องสะอาด

### ขั้น 1 — Render dashboard (ก่อน merge)
1. อ่านค่า **Root Directory / Build Command / Start Command / Branch / Auto-Deploy** แล้วเทียบกับตาราง หัวข้อ 3 (Branch ต้องเป็น `main`)
2. เพิ่ม Environment Variable: `ONNXRUNTIME_NODE_INSTALL` = `skip` (ไม่ตั้ง = onnxruntime ดาวน์โหลดไลบรารี CUDA/TensorRT ที่ CPU ไม่ใช้ ตรวจแล้วจากสคริปต์ติดตั้งของแพ็กเกจ ว่าไฟล์ CPU รวมมาในแพ็กเกจอยู่แล้ว)
3. **ห้ามตั้ง `SYMPTOM_SEARCH_ENABLED`** ในขั้นนี้ (ไม่ตั้ง = ปิด)
4. **ตรวจ `CORS_ORIGIN` ต้องเป็น origin ของหน้าเว็บเป๊ะๆ:** `https://parit-ru.github.io` (เฉพาะ scheme + โดเมน **ไม่มี path ไม่มี `/` ท้าย** ห้ามใส่ URL ของ repo `https://github.com/...`) โค้ดอ่านค่านี้ตรงๆ (`app.enableCors({ origin: process.env.CORS_ORIGIN ... })`) ค่าเดียวเท่านั้น ถ้าผิด หน้าเว็บจะเรียก backend ไม่ได้เลย แม้ `curl` จะเรียกได้ปกติ

### ขั้น 2 — merge และ deploy (จังหวะ ก)

> ⚠️ **ขั้นนี้ใช้ไม่ได้แล้ว ให้ข้าม:** ประวัติ git ถูกเขียนใหม่หลังเขียนเอกสารนี้ `main` กับสาขา `symptom-search` เนื้อไฟล์เหมือนกันแต่ประวัติคนละสาย การ merge จะได้ conflict หรือประวัติซ้ำ ปัจจุบันใช้ `main` เป็นต้นทางของ Render โดยตรง (deploy จาก `main`) คำสั่งข้างล่างเก็บไว้เป็นประวัติของวิธีที่ใช้ตอนนั้น (ขั้นนี้ทำไปแล้วเมื่อ 3 ต.ค.)
รากของ repo:
```powershell
git checkout main
git pull --ff-only origin main
git merge --ff-only symptom-search
git push origin main
```
`--ff-only` ทำให้ล้มทันทีถ้า `main` ถูกแก้จากที่อื่น แทนที่จะสร้าง merge commit เงียบๆ การ push คือการสั่ง deploy (ถ้าเปิด Auto-Deploy) ดูล็อก build บน Render ถ้าล้มให้เก็บล็อกส่วนท้ายไว้

### ขั้น 3 — ตรวจจังหวะ ก
โฟลเดอร์ `backend\`:
```powershell
node scripts/check-deployed-search.js https://troubleshoot-assistantv2.onrender.com
```
ผลที่ถูก: `/health` ok · **ส่วน 1b (CORS) ไม่มี ❌** (`access-control-allow-origin` ต้องเท่ากับ `https://parit-ru.github.io`) · `state=disabled` · `✅ ระบบค้นหาปิดอยู่` **จดค่า `memoryRssMb`** (ที่วัดจริงบน Render = 82 MB) ถ้าได้ "ไม่พบ endpoint" แปลว่า Render ยังรันโค้ดเก่า (ยังไม่ deploy เสร็จ หรือ Branch ผิด)

เปิดหน้าเว็บแล้วทดสอบเลือกอาการจากรายการ → เริ่มตรวจได้ตามปกติ (ยังไม่มีคะแนน) ยืนยันว่าโค้ดใหม่ไม่ทำให้ของเดิมพัง **ก่อนไปจังหวะ ข**

### ขั้น 4 — เปิดสวิตช์ (จังหวะ ข)
1. Render → Environment: เพิ่ม `SYMPTOM_SEARCH_ENABLED` = `true` (ต้องเป็น `true` เป๊ะๆ) → บริการจะรีสตาร์ต
2. โฟลเดอร์ `backend\` (ให้ยิงเยอะพอจะเห็นแนวโน้ม):
```powershell
node scripts/check-deployed-search.js https://troubleshoot-assistantv2.onrender.com --queries 100 --wait 300
```
3. **จดผล:** เวลาโหลด (`loadMs` และเวลาที่สคริปต์วัด), `memoryRssMb` ก่อนและหลังยิง, เวลาตอบ, และดู Render → Metrics/Logs ว่าไม่มีการรีสตาร์ตเองหรือข้อความ out of memory

### ขั้น 5 — ตัดสินใจ
| ผล | ทำอะไร |
|---|---|
| `state=ready` · `memoryRssMb` ต่ำกว่า ~450 หลังยิง 100 ครั้ง · ไม่มีรีสตาร์ต | เปิดต่อได้ ไปขั้น 6 |
| `memoryRssMb` ≥ ~450 หรือบริการรีสตาร์ตเอง หรือ `state=failed` | **ตั้ง `SYMPTOM_SEARCH_ENABLED` เป็น `false` (หรือลบ)** แล้วแจ้งผล ระบบกลับไปใช้รายการอาการเหมือนเดิม |
| `state=loading` นานมาก | เก็บเวลาไว้ ลองใหม่หลังรอ ถ้าเกินที่รับได้ ให้ปิดสวิตช์ |

เกณฑ์ ~450 MB เป็น **ข้อเสนอ** เพราะเพดานจริง 512 MB ต้องเหลือที่ว่างให้ช่วงพุ่งชั่วคราว ไม่ใช่ค่าที่วัดมาจาก Render

### ขั้น 6 — deploy frontend (ทีหลังสุด)
โฟลเดอร์ `frontend\`:
```powershell
npm test
npm run deploy
```
(`deploy` = build แล้วดัน `dist/` ขึ้นสาขา `gh-pages`) **ต้องทำหลังเปิดสวิตช์และผ่านขั้น 5** เพราะถ้าขึ้นก่อน ผู้ใช้จะเห็นช่องค้นหาที่ล้มทุกครั้ง (หน้าจอแสดงข้อความบอกให้ใช้รายการ แต่ไม่ควรให้เห็น) frontend เก่าใช้กับ backend ใหม่ได้ ไม่ต้องรีบ

**หลัง `npm run deploy` ต้องดูแท็บ Actions ของ repo** ว่ามี "pages build and deployment" รอบใหม่ที่สำเร็จ การ push สาขา `gh-pages` อย่างเดียวไม่รับประกันว่า Pages จะ build (เคยค้างที่ build ของ 2 ก.ย. หลายครั้ง) เทียบไฟล์ที่เว็บเสิร์ฟกับ `frontend/dist/assets/` ว่าชื่อแฮชเดียวกัน (GitHub Pages เก็บแคช 10 นาที หลัง build สำเร็จอาจต้องรอ)

ตรวจหน้าเว็บจริงหลังขึ้น: พิมพ์ "แอร์ไม่เย็น" → เห็น 3 อาการพร้อมคะแนน → กดแถวแรก → หน้าตรวจอาการมีบรรทัดคะแนนความคล้าย (ถ้ารายการอาการโหลดไม่ได้ ดู Console ของเบราว์เซอร์ว่ามีข้อความ CORS ไหม)

## 6. ข้อควรระวังหลังขึ้นจริง

- **Render ฟรีหลับหลังไม่มีคนใช้ ~15 นาที** (ตามที่แผนฟรีกำหนดโดยทั่วไป ผมยืนยันได้แค่ว่าหลับไปจริงหลังนิ่ง ~40 นาที) ทุกครั้งที่ตื่นต้องโหลดโมเดลใหม่ วัดแล้ว: ปลุก ~32–35 วินาที แล้วค้นหาพร้อมอีกราว 5 วินาที (หัวข้อ 8) คำค้นแรกหลังตื่นมีโอกาสได้ "ระบบค้นหากำลังเริ่มทำงาน" ซึ่งเป็นพฤติกรรมที่ออกแบบรองรับไว้แล้ว (503 `SEARCH_NOT_READY`) ไม่ใช่บั๊ก และหน่วยความจำถูกรีเซ็ตทุกครั้งที่ตื่น ตัวเลขที่เห็นจึงเป็นของช่วงที่ตื่นอยู่เท่านั้น
- **คะแนนความคล้ายไม่ใช่ความน่าจะเป็น** และเกณฑ์ 0.55 ยังไม่ผ่านชุดรายงานผล ห้ามอ้างความแม่นยำ (เอกสาร 11)
- **อย่าเอา `.env` ขึ้น git** ค่าจริง (รหัสฐานข้อมูล ใบรับรอง) ตั้งใน dashboard เท่านั้น

## 7. หลัง deploy: เอกสารที่ต้องอัปเดต

เมื่อมีผลจริงจากขั้น 3–4 ให้ส่งให้ผู้ช่วย แล้วจะ (1) กรอกหัวข้อ 8 ข้างล่าง (2) อัปเดต `README.md` / `Overview.md` / `PROJECT_CONTEXT.md` (คอลัมน์ `confidence`, endpoint ใหม่ `POST /symptom-search` และ `GET /symptom-search/status`, ตัวแปร `SYMPTOM_SEARCH_ENABLED`, จำนวนเทส 155/55, `tsconfig.json`)

**ข้อจำกัดของตัวเลขชุดนี้ (ต้องบอกตรงๆ ถ้าอ้าง):**

- คำค้น 100 ครั้งวนจาก **ประโยคเดิม 10 ประโยค** ไม่หลากหลาย ในเครื่องซ้อม หน่วยความจำขึ้นช่วงคำค้นหลากหลายราว 750 ข้อความแรกแล้วนิ่ง (~292 MB เฉพาะส่วน embedding) จึง **ยังไม่ได้พิสูจน์ว่านิ่งแล้วบน Render** ถ้าต้องการ ยิงเพิ่ม (`--queries 500` ขึ้นไป) หรือดูค่าอีกครั้งหลังมีผู้ใช้จริงสักพัก
- Render ฟรีหลับหลังไม่มีคนใช้ ทุกครั้งที่ตื่นต้องโหลดโมเดลใหม่ (~10 วินาทีตามที่วัด) หน่วยความจำจึงถูกรีเซ็ตเสมอ ตัวเลขข้างบนเป็นของช่วงที่ตื่นอยู่เท่านั้น
- `max` 3,449 ms ของการยิง 100 ครั้งเป็นค่าสูงสุดครั้งเดียว ไม่ทราบสาเหตุ (อาจเป็นเครือข่ายหรือ CPU 0.1 ของ Render) ไม่ได้ตรวจซ้ำ
- วัดจากเครื่องผู้พัฒนาไปยัง Render จึงรวมเวลาเครือข่ายไว้ด้วย ไม่ใช่เวลาคำนวณล้วน
- **ผล cold start วัดแบบควบคุมเพียง 1 ครั้ง** (อีก 2 ค่าที่เคยเห็นไม่ได้วัดแบบควบคุม) เวลาปลุกของ Render ฟรีผันแปรได้ ช่วง `loading` สั้นมาก (~5 วินาที) จึงได้ตัวอย่างต่อ endpoint แค่ 2 ตัว ตัวเลข "ช้าลง 2–3 เท่า" เป็นแนวโน้มที่เห็น ไม่ใช่ค่าที่เชื่อถือทางสถิติ และสคริปต์ติดป้าย state ตามตอนอ่านสถานะต้นรอบ ตัวอย่างที่คาบเกี่ยวตอนโหลดเสร็จจึงอาจติดป้าย `loading` ทั้งที่โหลดเสร็จแล้ว (เช่น ค้นหารอบที่สองได้ 200 ทั้งที่ติดป้าย `loading`)
- `/health` ตอนเสถียร (~467 ms) ช้ากว่า `GET /traversal/graphs` (~228 ms) ประมาณ 230 ms ซึ่งสอดคล้องกับที่ `/health` ต้องถามฐานข้อมูล (`database: ok`) ส่วน graphs อ่านจากหน่วยความจำ ใช้เป็นข้อบ่งชี้ว่าไปกลับ Render ↔ Aiven ราว 0.2 วินาที ไม่ได้วัดตรง
- ผู้ใช้จริงมักเจอ `SEARCH_NOT_READY` น้อยกว่าที่คิด: หน้าเว็บโหลดรายการอาการก่อน (ต้องรอเซิร์ฟเวอร์ตื่น ~35 วินาที) กว่าจะพิมพ์ค้นหา โมเดลมักโหลดเสร็จแล้ว (ใช้เวลาอีกราว 5 วินาทีหลังเซิร์ฟเวอร์เริ่มตอบ) แต่ถ้ารีสตาร์ตขณะมีคนใช้อยู่ก็เจอได้ (ข้อนี้เป็นข้อสรุปจากตัวเลขข้างบน ยังไม่ได้ทดสอบกับผู้ใช้จริง)
