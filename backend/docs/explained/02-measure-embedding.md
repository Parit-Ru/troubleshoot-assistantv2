# อธิบายโค้ด: `backend/scripts/measure-embedding.mjs`

ขั้น 1.1 ของงานค้นหาอาการด้วยภาษาธรรมชาติ (แผน A)

## 1. สคริปต์นี้ทำอะไร และทำไม

**คำถามที่ต้องตอบ:** โมเดล `paraphrase-multilingual-MiniLM-L12-v2` แบบ quantized รันใน Node บน Render free (RAM 512 MB, CPU 0.1) ได้หรือไม่

สคริปต์นี้ **ไม่ได้เป็นส่วนของระบบ** เป็นเครื่องมือวัดครั้งเดียว ผลที่ได้ใช้ตัดสินว่าจะเดินหน้าแผน A ต่อ หรือกลับไปเลือกตัวเลือก B/C

ที่ต้องวัดก่อนเพราะ Render จะฆ่าโปรเซสถ้าหน่วยความจำเกิน 512 MB และค่าที่อันตรายคือ **ค่าสูงสุดตอนโหลดโมเดล** ไม่ใช่ค่าหลังโหลดเสร็จ

## 2. วิธีรัน (PowerShell)

ยืนที่โฟลเดอร์ `backend/` ทุกคำสั่ง

```powershell
cd backend
npm install @huggingface/transformers
node scripts/measure-embedding.mjs
```

- คำสั่ง `npm install` จะแก้ `package.json` และ `package-lock.json` ของ backend (เป็นการเพิ่มไลบรารีที่คุณเลือกในแผน A) อย่าลืม commit ภายหลัง
- **ต้องต่ออินเทอร์เน็ตในการรันครั้งแรก** เพื่อดาวน์โหลดไฟล์โมเดลจาก Hugging Face หลังจากนั้นจะใช้แคชในเครื่อง
- ถ้าอยากดูความต่างของโมเดลเต็ม (เปลืองแรมมาก อาจช้า): `node scripts/measure-embedding.mjs fp32`

## 3. โค้ดแบ่งเป็นส่วนอะไรบ้าง

| ส่วน | ทำอะไร |
|---|---|
| ค่าคงที่ด้านบน | ชื่อโมเดล, dtype (`q8` = quantized 8 บิต), เกณฑ์ตัดสิน 350/450 MB, ประโยคตัวอย่าง |
| `toMb`, `currentRssMb`, `peakRssMb` | แปลงหน่วยความจำเป็น MB. `peakRssMb` ใช้ `process.resourceUsage().maxRSS` ซึ่งเป็นค่าสูงสุดตลอดอายุโปรเซส |
| `cosine(a, b)` | สูตร cosine similarity เขียนเอง: ผลคูณจุดหารด้วยผลคูณความยาวเวกเตอร์ (คือสูตรที่จะใช้ในระบบจริง) |
| `import('@huggingface/transformers')` | ใช้ dynamic import เพราะไลบรารีเป็น ESM ตอนใช้ใน NestJS (คอมไพล์เป็น CommonJS) ก็ต้องใช้รูปแบบนี้ |
| `pipeline('feature-extraction', ...)` | โหลดโมเดลสำหรับแปลงข้อความเป็นเวกเตอร์ |
| `embed(text)` | แปลงข้อความเป็นเวกเตอร์ 384 มิติ ด้วย mean pooling + normalize ตามที่ MiniLM ถูกเทรนมา |
| ลูป query | จับเวลาแต่ละ query และหาผู้สมัครที่ cosine สูงสุด |
| ส่วนสรุป | รายงานเวลาโหลด, เวลาต่อ query, RSS สูงสุด และผลผ่าน/เสี่ยง/ไม่ผ่าน |

## 4. วิธีอ่านผล

| ตัวเลข | ความหมาย | เกณฑ์ |
|---|---|---|
| **RSS สูงสุด (peak)** | ตัวชี้ขาดหลัก | ≤ 350 MB ผ่าน · 350–450 เสี่ยง · > 450 ไม่ผ่าน |
| เวลาโหลดโมเดล | ผลกระทบต่อ cold start ตอนตื่นจากหลับ | ยิ่งสั้นยิ่งดี (รันครั้งที่ 2 ขึ้นไปจึงจะไม่รวมเวลาดาวน์โหลด) |
| query ถัดไป (เฉลี่ย) | ความเร็วต่อคำค้น | หลักสิบถึงหลักร้อย ms ถือว่าใช้ได้ |
| จำนวนมิติ | ต้องเป็น 384 | ถ้าไม่ใช่แปลว่าโหลดโมเดลผิดตัว |
| คะแนนของ query ข้อ 1–4 | ควรตรงกับผู้สมัครข้อที่คาด | ดูว่าภาษาไทยและอังกฤษข้ามภาษาได้หรือไม่ |
| **คะแนนของ query ข้อ 5 (เครื่องซักผ้า)** | คะแนนของคำค้นที่ไม่ควรตรงกับอะไร | จดไว้ใช้ตั้งเกณฑ์ "ความมั่นใจต่ำ → ส่งต่อศูนย์บริการ" ในขั้นถัดไป |

## 5. ข้อจำกัดที่ต้องรู้

- ตัวเลขวัดบน **Windows ของคุณ** ส่วน Render เป็น Linux ค่า RSS อาจต่างกันเล็กน้อย จึงกำหนดเกณฑ์ผ่านไว้ที่ 350 MB เผื่อที่ไว้
- Render free มี **CPU 0.1** ช้ากว่าเครื่องคุณมาก เวลาโหลดและเวลาต่อ query บน Render จะนานกว่าที่วัดได้ที่นี่ (วัดจริงบน Render ได้ในขั้นหลัง)
- ประโยคตัวอย่างในสคริปต์ **ไม่ใช่ข้อมูลจริงของระบบ** เขียนขึ้นเพื่อทดสอบเบื้องต้นเท่านั้น คะแนนของ 13 อาการจริงจะวัดในขั้นถัดไป
- ผมยังไม่ยืนยันว่า repo `Xenova/paraphrase-multilingual-MiniLM-L12-v2` มีไฟล์ quantized สำหรับ `q8` ครบ ถ้าโหลดไม่สำเร็จ สคริปต์จะแจ้งข้อผิดพลาดและแนะนำให้ลอง `int8` หรือ `uint8`
- ผมรันสคริปต์นี้เองไม่ได้ (เครือข่ายฝั่งผมเข้าถึง Hugging Face ไม่ได้) จึงยังไม่ได้ทดสอบ คุณเป็นคนรันครั้งแรก
